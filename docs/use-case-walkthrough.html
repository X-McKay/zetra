08 / A continuous worked example · Developers · Platform teams · Reviewers

Incident triage, from package to a reviewed action

A synthetic checkout-service alert arrives. The agent reads one approved runbook, calls one reviewed status tool, and prepares a precise investigation ticket. An independent reviewer approves that exact payload. The receiver creates one ticket; a duplicate delivery returns the same receipt. A stop between review and commit prevents the next local invocation. This chapter follows one incident and one run through those steps so the contracts, evidence and enforcement responsibilities remain connected.

What is executable here. examples/incident-triage/ is a deterministic offline reference. It uses the real Zetra runtime interfaces and Gateway MCP protocol parser, a self-contained MCP wire fixture with no network connections, and a temporary SQLite receiver. It calls no language model and creates no production ticket. Local actor strings and grants are demonstration controls. The production signed approval service, durable write bridge, receiver fencing and distributed revocation described below are target interfaces that still need implementation and qualification.

8.1 Define one useful outcome and its authority envelope

The useful outcome is a reviewable incident record containing the alert, observed service status and approved investigation guidance. The agent may propose and, after approval, create an investigation ticket. It may not restart a service, change configuration, modify customer records, page a human, or obtain broader permissions. The reference deliberately supports checkout-api only. Adding another service means changing the reviewed service/tool contract and testing its resource authorization; an event field cannot select an arbitrary backend.

RoleDecision or responsibilityEvidence to inspect
Service ownerOwn the runbook, alert interpretation, ticket destination and maximum acceptable consequence.Reviewed source, approved knowledge provenance, risk assessment and escalation policy.
Agent developerImplement typed inputs, bounded planning, exact proposals and the stable business-operation identity.Factory/models, executable scenario map, source-bound results and denied-path assertions.
Incident reviewerApprove the exact ticket title/body and allowed destination for a limited lifetime.Canonical payload digest, incident/resource, release, policy revision and authenticated reviewer identity in production.
Platform teamBind the package to qualified identity, sandbox, gateway, receiver and telemetry controls.Signed deployment tuple, effective policies, positive/negative qualification, admission and revocation acknowledgements.
Risk ownerRatify inherent/residual risk and decide whether outstanding controls permit the stated operating scope.Internal-data, supervised write-capability assessment; accountable ownership; exceptions with expiry.

The manifest establishes a T2 candidate floor: it handles internal operational data and can create an external record under supervision. That floor is not a completed business-impact assessment or a production approval. Incident summaries could contain sensitive data; the synthetic fixture contains none. A real intake needs approved field handling, minimization and redaction. The placeholder owner must be replaced by a real accountable owner before organizational use.

In the executable fixture, success means: zero writes during planning, exactly one ticket after valid approval, the same receipt after retry, zero extra tickets when a consumed approval is reused, and a denied invocation after the STOP marker. Those are directly asserted invariants. Production success adds task usefulness, false or unnecessary ticket rate, time to review, cost per useful outcome, replay safety, authority freshness and measured disable convergence. A single deterministic run cannot estimate model-quality distributions or certify those production measures.

8.2 Keep the package and its contracts inspectable

examples/incident-triage/
├── agent.yaml
├── demo.py                         # external LOCAL controller and trace
├── src/incident_triage/
│   ├── __init__.py
│   ├── models.py                   # strict Incident and Proposal contracts
│   ├── factory.py                  # plan / approved commit, via dependencies
│   └── fixture.py                  # no-network MCP wire fixture
├── evals/scenarios.json            # stable IDs → executed unittest selectors
└── tests/test_cases.py             # positive and forbidden paths

The factory receives RuntimeDependencies; business code reads a runbook with read_knowledge(), reads status with read_status(), and requests a ticket with create_ticket(). Those three calls consume knowledge.read, mcp.read_status and ticket.write respectively. The case adds no dependency, framework binding or new toolkit schema. Its typed boundary accepts exactly a plan request or an approved commit request.

apiVersion: zetra.dev/v1alpha1
kind: Agent
metadata:
  name: incident-triage
  owner: service-operations@example.invalid
  businessFunction: service-operations
spec:
  entrypoint: incident_triage.factory:create_agent
  capabilities: [knowledge.read, mcp.read_status, ticket.write]
  dataClassification: internal
  autonomy: supervised
  execution: local
  budgets:
    maxSteps: 4
    maxSeconds: 30
    maxCostUsd: 0.05

The four local capability invocations cover runbook read, status read, first commit and duplicate delivery. Budgets apply to this runtime instance and use caller-reported cost reservations; they are not trusted billing or aggregate workflow accounting. The independent receiver-reuse test invokes the receiver directly as a negative boundary probe. Its denial cannot consume a new ticket or act as a way around the agent's budget.

These Python helpers are cooperative. Trusted example code uses them consistently, but hostile Python can bypass them or reach a local object directly. Production authority must also be bounded by independently enforced filesystem/network isolation, gateway identity and semantic policy, and the destination receiver. A source review and a capability declaration are inputs to that design, not substitutes for it.

8.3 Reproduce the complete local run

After just bootstrap, run the case from the repository root. The recipe supplies the package import path, and the demonstration cleans up its temporary database when it finishes. Its output includes only synthetic event/payload data and an approval reference; it never prints the approval bearer token or database credentials.

just incident-triage

  .venv/bin/python examples/incident-triage/demo.py

# Execute the case's required scenarios and validate their current binding:
.venv/bin/zetra check examples/incident-triage

  --output build/incident-triage-evidence.json

The ordinary zetra run command intentionally does not inject a write receiver or approval authority. The complete action demonstration therefore uses the explicit local controller in demo.py. That controller is not an unattended production approval service. Passing this local exercise does not grant network access or qualify the write-capable package for Temporal or Kubernetes activation.

The actual reference input is bounded and carries a stable business incident ID:

The run ID is run-INC-2026-0042-001. The demonstration computes releaseId from the current package fingerprint. In this local example that is a source-consistency hash, not a signed deployment image digest. Production joins source, image, policy and evidence through a trusted signed release record. Neither a user-supplied run ID nor an HTTP correlation header establishes identity.

8.4 Read facts, validate them, then propose an exact payload

The factory first retrieves the fixed key checkout-degradation. The fixture's reviewed runbook says to check the health dashboard, preserve correlation IDs, and ask the service owner to investigate; it expressly grants no restart or configuration authority. If the runbook is unavailable, planning stops. Next, read_status() calls the reviewed MCP tool read_status with {}. This initial tool has no arbitrary service-selection argument. The service-specific destination binding belongs to its reviewed route.

The Gateway client performs the pinned MCP 2025-11-25 initialize/initialized/tool-call exchange. In this case an offline OpenerDirector fixture returns the messages directly; no real HTTP connection or JWT verification occurs. The existing live integration reports separately test a native AgentGateway with a controlled receiver. The client limits response size/time, refuses redirects and exposes no generic write-tool escape hatch. The case adds a stronger domain check: the returned text must be exactly status: healthy or status: degraded. Extra instructions in a tool response are rejected.

# Actual factory contract, abbreviated to the consequential boundary:
proposal = agent.run({"phase": "plan", "incident": incident})
assert proposal["operationId"] == "INC-2026-0042:ticket:1"
assert receiver_ticket_count == 0

The exact body for the committed synthetic fixture is:

Incident: INC-2026-0042
Severity: warning
Observed service status: degraded
Untrusted event summary (descriptive data only): Synthetic checkout latency alert exceeded the review threshold.
Approved runbook: Check the health dashboard, preserve correlation IDs, and ask the service owner to investigate. Do not restart or modify production services.
Proposed action: create an investigation ticket. No production configuration change is authorized.

The event summary is descriptive data, not a policy instruction. Even a summary saying “ignore approval” cannot select a different phase, tool or service, issue a grant, or create a ticket. In production, an LLM may help summarize evidence or propose content, but its output still passes deterministic schema, resource, authorization and approval checks. The local fixture exercises those boundary shapes without claiming an LLM benchmark.

8.5 Bind review to the payload and distinguish correlation from authority

The local digest is SHA-256 of zetra.runtime.canonical(ticketPayload).encode(). That implementation uses sorted JSON keys, compact separators, JSON string escaping and no nonfinite numbers. It binds exactly the title and body the receiver will insert. A reviewer must see those exact fields. A production multi-language implementation needs a versioned canonicalization contract and cross-language test vectors; pretty-printed JSON or a Python repr is not the digest input.

# Executable LOCAL controller; never exposed as an agent tool:
approval = receiver.issue(
    proposal["ticketPayload"], actor="reviewer:alice", ttl_seconds=300
)
receipt = agent.run({
    "phase": "commit",
    "proposal": proposal,
    "actor": "reviewer:alice",
    "approval": approval,
})
# {"ticketId": 1, "status": "created"}

The local factory also rejects a proposal whose run/release IDs differ from its injected runtime context, whose operation identity changes shape, or whose action digest no longer matches its payload. These checks make the example coherent but remain cooperative. The SQLite grant itself binds actor string, payload digest, expiry and single use. It does not authenticate the actor, independently bind tenant/resource/release/policy, verify a signer or enforce a distributed authority epoch.

The production operation key is tenant-scoped and derives from business intent, rather than a Temporal attempt number or a new random ID per delivery. A resumed run cannot silently replace a reviewed payload, reassign its tenant, or use a different policy revision. If any of those change, the system creates a new proposal and obtains the appropriate review while reconciling any already committed prior operation.

8.6 Commit once and reconcile duplicate or uncertain delivery

The local receiver begins an immediate SQLite transaction. It first looks for a receipt under INC-2026-0042:ticket:1. An existing receipt is returned only when actor, payload digest and approval token match. For a new operation, the receiver validates the unexpired, unconsumed grant, consumes it, inserts the ticket and records the receipt in the same transaction. A crash before commit rolls the transaction back. A crash after commit leaves both the effect and its receipt recorded.

The demonstration reconstructs ActionStore against the same temporary database after the first commit. Delivering the same request again returns ticketId: 1 and leaves the ticket count at one. A consumed grant under another operation key is denied. The cached receipt is a read of an already committed effect: returning it does not renew authority or create another ticket. Production receipt reads need their own authenticated visibility policy, including behavior after grant expiry or revocation.

first = agent.run(commit_request)
dependencies.action_store = ActionStore(existing_receiver_database)
second = agent.run(commit_request)

assert first == second
assert first["ticketId"] == 1
assert ticket_row_count == 1

A remote ticket service cannot share the workflow worker's SQLite transaction. The production destination must enforce its idempotency key and argument binding atomically with its own effect/receipt ledger. If a network timeout occurs after the destination might have committed, the caller retries or queries using the same business-operation key. It must not infer “no effect” from a timeout or mint a fresh key to bypass uncertainty. If the destination lacks this contract, automatic retries of consequential effects are unsafe and remain an open release gate.

8.8 Add durable execution through a separately qualified approval/write bridge

The existing Temporal AgentActivities worker explicitly rejects ticket.write. Starting it with this manifest fails before polling because the approved production write adapter is absent. This is intentional fail-closed behavior, not a step the local demonstration skips through a configuration flag. The current read-only workflow and its retry/replay evidence can inform a design, but cannot be relabeled as durable write qualification.

A production bridge should separate deterministic orchestration from activities that access models, status services, approval authorities and receivers. A read activity produces an immutable proposal reference. An authenticated approval application publishes a decision referencing that proposal. The workflow waits durably for the reference; a signal carrying an approval reference is a notification, not sufficient authority. A write activity sends the exact proposal and signed grant to the destination. The destination verifies current authority and idempotency at commit time so a separate earlier approval check cannot create a check-to-use gap.

# ARCHITECTURAL PSEUDOCODE: these activities and approval bridge are NOT implemented.
proposal_ref = await execute_activity("AnalyzeIncident", incident_reference)
decision_ref = await wait_for_authenticated_approval_reference(proposal_ref)
receipt_ref = await execute_activity(
    "VerifyCurrentAuthorityAndCommitTicket",
    {
        "proposal_ref": proposal_ref,
        "decision_ref": decision_ref,
        "operation_id": "service-operations:INC-2026-0042:ticket:1",
    },
)
# The receiver atomically applies authority/idempotency rules with the effect.
# Store large/sensitive evidence outside history; pass controlled references.

The bridge needs explicit activity timeouts and retry policies, cancellation/stop semantics, a persistent receiver ledger, policy/epoch freshness behavior, protected payload storage and tested recovery after worker loss or lost acknowledgements. Replay tests prove deterministic orchestration compatibility; they do not execute or reauthorize old external effects. Never put ordinary network calls, untrusted wall-clock access or random operation-key generation in workflow code.

8.9 Stop the run without confusing containment with rollback

The local stop test writes the configured STOP marker after a proposal has been approved and before commit. The next require() denies the capability invocation, leaving zero tickets. The demonstration also stops after one committed ticket; that ticket remains committed and a later invocation is denied. Local STOP checks occur at cooperative capability boundaries. They cannot interrupt arbitrary Python, authenticate a stop decision, revoke an already issued remote token or guarantee the termination of in-flight I/O.

The production stop decision needs an authenticated actor, explicit scope and a monotonic authority epoch. Intake refuses new work; the workflow receives cancellation/disable state; the gateway denies the relevant model/tool permissions and expires cached leases; the receiver rejects stale epochs before committing; and the workload/sandbox is contained if necessary. Each layer acknowledges the effective epoch. A missing acknowledgement is an escalation condition, not evidence that the stop succeeded.

For this incident, an approval issued at epoch 19 must not create a new ticket after the receiver observes disable epoch 20, even if Temporal resumes an old activity. An already committed ticket requires reconciliation or a separately approved compensating business action; disable cannot undo it. Restart requires remediation, current policy/evidence, a new authorized epoch and an explicit decision about queued proposals. Removing a STOP file or recreating a pod alone does not authorize production restart.
