Risk, Governance, and Oversight Playbook

Govern an agent through its authority, evidence, and current operating state. Automate evidence collection and conservative classification; keep accountable approval, exceptions, incident command, and restart decisions explicit.

4.1 Risk is a property of the deployed system

Assess the agent with its tools, data, identities, users, destinations, workflow, and runtime controls. A harmless prompt can drive a powerful tool. A read-only tool can disclose restricted data. A technically reversible action can create reputational or operational harm before it is reversed. The assessment must therefore state a concrete failure scenario and consequence, then identify which controls reduce its likelihood or impact.

Maintain a risk profile with separate dimensions: data sensitivity, action authority, autonomy, blast radius, external exposure, recoverability, dependency trust, and evidence completeness. Do not reduce these dimensions to a weighted average that allows low cost or good task quality to offset unauthorized production writes. Record inherent risk from the proposed authority, control requirements, verified controls, and residual risk. Preserve both inherent and residual views so reviewers can see what depends on runtime enforcement.

The tiers below are a proposed enterprise method to ratify. They are not a regulatory classification. Assign the highest triggered tier, then apply uncertainty and exceptional-consequence escalation. A business function may impose tighter requirements. Central policy establishes a minimum that local teams cannot weaken by changing labels.

TierTypical triggersMinimum operating posture
T0 · Restricted experimentSynthetic or public data, no external side effects, isolated non-production use, no consequential downstream decision.Named owner, bounded resources, local evidence, no production credentials. T0 is not automatic production eligibility.
T1 · Bounded assistanceApproved internal read-only access, bounded output audience, no independent consequential action.Tenant/resource authorization, data handling, negative tests, gateway/sandbox qualification, monitored deployment.
T2 · Supervised executionLimited reversible writes, authenticated human approval for consequential actions, narrow resource and transaction limits.T1 controls plus exact approval binding, receiver idempotency, revocation checks, change evidence, staffed recovery procedure.
T3 · Elevated authorityAutonomous consequential writes; restricted data; external disclosure; broad multi-agent delegation; high blast radius; privileged code execution.Independent security/risk review, strong destination authorization, verified isolation, stricter freshness, live failure drills, controlled rollout and independent restart authority.
T4 · Exceptional or prohibited pending reviewIrreversible high-impact actions, unrestricted privilege, unbounded public interaction with consequential authority, or policy-prohibited use.No automatic promotion. Explicit authority determines prohibition or an exceptional operating envelope with specific controls and review.

Risk is not settled once at launch. A model switch, new tool schema, broader document corpus, changed audience, gateway bypass, lost sandbox capability, or increased transaction limit changes the system. Reassess when the operating envelope changes and on a defined review cadence. An incident can invalidate a control assumption without any code change; the catalog must support suspending affected releases across business functions.

4.2 Conservative automated classification

Combine four sources: developer declarations, static findings, observed behavior in a qualified test environment, and destination/tool metadata. Declarations express intended authority. Static analysis identifies likely I/O and dynamic behavior. Telemetry identifies actual exercised actions. Receiver metadata describes the real business effects and scopes. None is sufficient alone. Reconcile mismatches and retain the original evidence so a reviewer can see why classification changed.

Use deterministic classification rules for known attributes and evidence-based flags for uncertainty. A scanner finding subprocess should add a code-execution investigation and relevant tests, not claim to know its maximum business consequence. HTTP method, field names, and SQL keywords are hints. Imported code, generated tools, runtime plugins, reflective calls, and remote servers can hide behavior. Missing metadata, unresolved call targets, incomplete traces, or unsupported transports require an unknown finding with a named owner and resolution requirement.

# Target classification logic: conservative maxima, never averaged risk.
tier = max(triggered_tiers(declared_capabilities, data, autonomy, blast_radius))
findings = reconcile(declarations, static_findings, observed_actions, tool_metadata)
if findings.unresolved_authority or findings.unknown_data_destination:
    promotion = "blocked-pending-review"
if findings.observed_action_outside_declared_scope:
    promotion = "blocked-capability-mismatch"
if any(required_control.status != "verified" for required_control in controls[tier]):
    promotion = "blocked-control-evidence"
if evidence.expired or evidence.inputs_do_not_match_release:
    promotion = "blocked-stale-evidence"

The v0.1 toolkit demonstrates local capability checking and a conservative report. It does not implement a complete semantic capability graph, IDE language server, business impact classifier, or enterprise risk approval service. Treat its outputs as evidence inputs. The supplied AEIE draft motivates an inference engine, but production adoption requires validated detection rules, false-negative analysis, explicit unknowns, and an independent review process for material risks.

Attach stable scenario IDs such as R-AUTH-001, R-APPROVAL-001, R-DATA-001, R-DURABILITY-001, and R-REVOKE-001 to required controls and evidence. The required set is the union of declared-capability requirements, observed-capability requirements, central minimums, and assessed domain risks. A declaration cannot remove a scenario demanded by evidence. A reviewer can retire a scenario only through an explained change to the threat model and policy mapping.

4.3 Policy proposals do not become authority by observation

Profiling can suggest the destinations, binaries, files, models, and remote tools needed by a package. Build candidates from a clean test environment with known workload identity and a recorded image digest. Filter out test harness activity and identify incomplete or dropped telemetry. Compare candidates with the manifest’s business intent, approved tool definitions, and central constraints. Test permitted and forbidden actions after applying the candidate; a successful trace alone does not show that forbidden actions are blocked.

Policy review must consider combinations of authority. A tool with production read access plus external posting can create an exfiltration path even when each rule looks reasonable separately. Delegation can combine privileges across agents. A generic code runner can bypass a narrow tool interface. Review data flows, identity propagation, and destination authorization, not only each YAML rule in isolation.

Automated invariant checks should reject broad wildcards, unknown destinations, unsupported policy features, raw credential exposure, unreviewed write authority, and bypassable egress. If a formal proof engine is introduced, document its modeled semantics, assumptions, unsupported features, and linkage to the actual deployed evaluator. A proof about a policy model does not establish that a runtime implements that model correctly. The OpenShell draft’s “propose-prove-enforce” idea is a target concept; use verified tooling and precise assurance claims.

Control owners approve effective policy, not only source templates. Rendered artifacts must bind agent identity, image digest, policy revision, framework/runtime adapter version, destination scope, and environment. Publish a human-readable diff showing expansion and contraction of authority. Applying a policy and deploying a workload are coordinated changes: startup must not enable execution while the necessary runtime policy is missing or stale.

4.4 Multi-layer kill switches and revocation

A kill switch is a coordinated containment protocol. Stopping a Python loop is insufficient when requests are queued, workflows are sleeping, credentials remain valid, or destinations accept already-issued authority. Provide disable scopes for one run, one agent release, an agent identity, a capability, a destination, a business function, and a tenant. Responders must select the scope and reason, and the system must report acknowledgments from each affected layer.

LayerDisable actionWhat it must verifyLimit
Ingress and schedulerReject new runs and stop scheduling new work.Queue items carry release and authority revision; consumers recheck revocation.Already running activities may remain active.

Runtime and networkBlock egress, quarantine or terminate workload, remove restart authorization.Effective sandbox/network state and workload identity, including restarted pods.Deleting a pod does not revoke remote credentials or erase durable work.

Use a monotonic authority epoch or equivalent fencing mechanism. An approved grant binds agent identity, release, capability, tenant/resource, operation, policy revision, epoch, and expiry. A destination compares the current epoch before committing. This closes the gap in which a workflow resumes using an old approval after disable. The exact mechanism must be implemented by a qualified authority and receiver adapter; the local demonstration cannot supply enterprise enforcement.

Specify freshness windows as measurable contracts. The following values are illustrative engineering objectives to ratify in live qualification, not verified platform guarantees. Security owners may require tighter limits for elevated authority. Authorization systems should use trustworthy clocks, bounded skew handling, and measured cache behavior. Short token lifetimes alone cannot establish prompt revocation.

Distinguish fail-closed execution from useful degraded assistance. An agent may prepare a local draft while authority is unavailable if the operating envelope allows it and no sensitive data leaves approved boundaries. It may not execute a consequential action based on stale policy. Test partitions, dropped messages, process restarts, duplicate disable events, old workflow replay, and a destination that receives a request during revocation. Measure the last newly authorized action rather than relying on a dashboard turning red.

Disabling and restarting have different permissions. Responders may need rapid disable authority across a broad scope. Restart requires documented remediation, current evidence, owner approval, and validation that queued or sleeping work cannot execute stale intent. Restart with a new epoch; do not clear an incident by restoring an old cached grant. Keep the disable drill and recovery drill as separate release-readiness evidence.

4.5 A centrally governed catalog published through CD

The catalog is the authoritative inventory of approved agent releases and their operational envelope. It should contain logical agent ID, release digest, source revision, image digest, owner and on-call group, business function, purpose, data class, autonomy mode, inherent/residual tier, declared and verified capabilities, dependency versions, policy digests, runtime qualification, evidence links, approvals, exceptions, environments, lifecycle state, and last review. Avoid embedding secrets or unrestricted prompt content in the catalog.

Separate a desired release record from actual deployment state. Desired records move through draft, candidate, approved, deployed, suspended, retired, and archived. Deployment observations report active workloads, identities, runtime versions, loaded policies, health, and enforcement readiness. Reconcile them continuously. An approved release that is not deployed differs from an unknown workload using an approved name. A copied manifest must not confer the identity of an approved artifact.

# v0.1 writes a local catalog record for review.
zetra catalog examples/knowledge \
  --evidence /tmp/eval.json --output /tmp/catalog-record.json

# Target CD sequence, implemented by approved pipeline adapters:
# verify immutable inputs and evidence freshness
# approve capability/risk/policy diff under tier-specific authority
# publish signed immutable release record
# deploy withheld plan only after runtime qualification
# reconcile effective policy and discovered workload back to catalog

CD should verify evidence provenance, expiration, and input digests; apply tier-specific approvals; and publish an immutable release record signed by an approved pipeline identity. The local toolkit’s timestamps and hashes are useful consistency checks, but a file a developer can rewrite is not a trusted approval. Protect approval records and signing identities separately from agent source modification. Use content-addressed artifacts and retain an auditable chain from intent through effective policy to deployed identity.

Policy promotion needs staged rollout and rollback semantics. A stricter policy may break active workflows; a broader policy increases authority. Test both on representative histories and workloads. Reverting code does not automatically revert a destination mutation or a changed identity grant. The catalog should record which versions can safely coexist and which require draining, migration, or recovery. Retire an agent by denying new work, resolving active effects, revoking identity, and preserving evidence under the retention policy.

4.6 Central and business-function oversight

Emit consistent semantic metadata across agent, workflow, activity, gateway, sandbox, and destination: agent ID, release digest, run ID, workflow/activity identifiers when applicable, business function, tenant, capability, policy revision, risk tier, decision ID, approval reference, idempotency key reference, budget counters, and trace linkage. Do not place full secrets, sensitive approval payloads, or raw user content in identifiers. Propagate context using approved interfaces and account for asynchronous boundaries explicitly.

Dashboard access must be enforced by the backend, not only by hiding a filter. Business-function attribution is a billing and oversight field; it is not a sufficient security principal. Tenant and data-owner restrictions continue to apply. Aggregate central metrics should avoid exposing confidential business content. Define retention, deletion, export, and audit rules for traces, workflow histories, artifacts, and approval receipts separately.

Alert on actionable conditions: attempted or completed unauthorized action, critical gate failure, unknown workload, missing enforcement readiness, stale policy or revocation state, gateway bypass, unusual tool use, tenant mismatch, budget exhaustion, exception expiry, or an unexpectedly old workflow. Route high-severity security events to central responders and the owner; route task-quality and cost regressions to business and technical owners. Deduplicate by agent, release, run, and decision ID, and preserve event ordering where practical.

Telemetry delivery loss must itself be visible. Buffer within approved limits, track dropped spans/events, and alert on gaps. Decide by tier whether loss of required audit delivery blocks new consequential actions. Logs provide evidence, while receiver authorization enforces authority; a collector outage should not silently disable enforcement. Prompt content capture should be off or redacted by default and enabled only for a defined, time-limited diagnostic purpose with proper access.

4.7 Exceptions with expiry and compensating controls

An exception request identifies the exact requirement, affected agent releases and environments, business need, maximum consequence, alternatives considered, compensating controls, owner, approver, expiry, and migration plan. Approval must come from the authority responsible for the policy, with data or business owners consulted where their obligations are affected. An exception cannot be self-approved by changing a manifest field or renaming a failed gate.

Bind the exception to immutable artifacts and scopes. An approval for one destination or pilot does not authorize a new tool, greater spend, or production use. Generate alerts before expiry and block new promotion when expired. For active workloads, define the approved expiry transition: drain, disable the capability, or suspend execution. Emergency exceptions require an incident record, narrow duration, independent review as soon as practical, and a documented path back to the standard.

Track exception count, age, renewals, authority expansion, and common causes. Repeated exceptions can reveal a missing platform capability or an inappropriate use case. Resolve them through roadmap work or reduced scope, not indefinite renewal. Preserve superseded approvals and the evidence that justified each decision.

4.8 Incident containment and recovery runbook

  1. Establish the event. Record run, release, identity, affected tenant/resource, observed action, decision IDs, timestamps, and whether an external effect may have committed. Assign an incident commander and classify consequence using the organization’s incident process.
  2. Contain independently. Apply the smallest scope that reliably stops harm, expanding when uncertainty warrants it. Disable ingress, scheduling, gateway/tool authority, credential issuance, destination access, and runtime egress as needed. Collect each acknowledgement; do not assume pod termination is complete containment.
  3. Preserve evidence. Retain policy revisions, approvals, image/source digests, traces, receiver receipts, workflow histories, and relevant artifacts under controlled access. Avoid exporting sensitive payloads into a general incident channel.
  4. Reconcile effects. Query trusted receivers using operation or idempotency references. Distinguish attempted, rejected, committed, unknown, and compensated actions. Stop automated retries for ambiguous effects until state is resolved.
  5. Assess scope and communicate. Search catalog and identity inventories for other affected releases, tools, policies, or shared credentials. Route findings to technical, business, security, and other required authorities through the organization’s existing process.
  6. Remediate and validate. Fix the violated boundary, reduce authority if needed, add a stable regression scenario, regenerate evidence, and test bypass, revocation, restart, and affected workflow histories.
  7. Authorize recovery. Obtain named restart authority, issue a new epoch, inspect pending approvals and queued work, and perform a controlled rollout. Monitor receiver outcomes and policy freshness closely.
  8. Close with improvement. Document root cause, missed signals, containment timing, residual effects, owner actions, and deadlines. Update risk profiles, rules, datasets, platform tests, and playbook decisions.

Run drills before enabling consequential production authority and after material architecture changes. Include control-plane partition, stale gateway policy, compromised tool response, duplicate activity delivery, approval replay, and a workload restarting after disable. Evidence should report what actually blocked the action and when. A tabletop exercise validates roles and communication; a live controlled drill validates enforcement. Both are useful and should be labeled accurately.
