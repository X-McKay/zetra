# Research notes: durable zero-trust agents on PydanticAI and Temporal

Companion to [the SDK proposal](durable-agent-sdk-proposal.md). Research date: 2026-10-11. The rendered documentation sites for Pydantic (`pydantic.dev`, `ai.pydantic.dev`), Temporal (`docs.temporal.io`, `temporal.io`, `learn.temporal.io`), agentskills.io, modelcontextprotocol.io, OWASP, the IETF datatracker and arXiv were blocked by this environment's egress policy. Every claim below was checked against the projects' GitHub sources (documentation repositories, SDK source, release pages) or PyPI instead; items seen only through secondary summaries are flagged. Pins at the time of writing: PydanticAI **v2.55.0** (2026-10-09), `pydantic-ai-harness` 0.x, Temporal Python SDK **1.34.0** (repository pin; releases 1.30.0 Jul 2, 1.31.0 Jul 29, 1.32.0 Aug 24, 1.33.0 Sep 15, 1.34.0 Sep 30 2026).

## 1. PydanticAI v2 durable execution (`pydantic_ai.durable_exec.temporal`)

Sources: `docs/durable_execution/temporal.md`, `docs/deferred-tools.md`, `docs/toolsets.md`, `docs/agent-spec.md`, `docs/capabilities/*.md`, `docs/harness/*.md`, `docs/retries.md`, `docs/version-policy.md`, and `pydantic_ai_slim/pydantic_ai/durable_exec/temporal/` in <https://github.com/pydantic/pydantic-ai>.

- **Versioning.** V2.0 shipped 2026-06-23; v2.55.0 is current. Deprecated APIs are removed no sooner than the next major (v3), at least three months after v2.0. `TemporalAgent` is deprecated in favour of the `TemporalDurability` capability. The `spec` and `temporal` extras are not installed by default.
- **Public API** (`__all__`): `TemporalDurability`, `PydanticAIPlugin`, `AgentPlugin`, `LogfirePlugin`, `TemporalRunContext`, `TemporalWrapperToolset`, `TemporalOperationNamer`, `PydanticAIWorkflow`, `PydanticAIPayloadConverter`, `AgentEventStream`, `WorkflowStreamTopic`, `DurableAgentRunEvents`, `workflow_stream_event_handler`, `stream_agent_events`, plus the deprecated `TemporalAgent`.
- **Canonical shape.** `Agent(..., name='x', capabilities=[TemporalDurability()])`; a `@workflow.defn` class (optionally subclassing `PydanticAIWorkflow`) lists agents in `__pydantic_ai_agents__` and calls `await agent.run(...)` from `@workflow.run`; `Client.connect(..., plugins=[PydanticAIPlugin()])`; `Worker(client, task_queue=..., workflows=[...])`. `PydanticAIPlugin` swaps the payload converter to a Pydantic converter (warning if a non-Pydantic converter was set; custom `payload_codec`, failure converter and `external_storage` are preserved), adds sandbox passthrough modules, registers each agent's activities, and sets `workflow_failure_exception_types=[UserError, PydanticUserError, AgentRunError, UnsupportedEventLoopError, WorkspaceError]` so those fail the workflow with a typed error instead of retrying the workflow task.
- **`TemporalDurability` arguments**: `models` (registry for `agent.run(model=...)`), `event_stream_handler`, `event_stream_topic`, `name`, `deps_type`, `activity_config`, `model_activity_config`, `event_stream_handler_activity_config`, `toolset_activity_config` (keyed by toolset `id`), `run_context_type`. There is **no** `tool_activity_config`; per-tool configuration is tool metadata: `metadata={'temporal': ActivityConfig(...)}`, `metadata={'temporal': False}` to skip wrapping (async function tools only; MCP tools raise), or `SetToolMetadata(tools=[...], temporal=ActivityConfig(...))`. `ActivityConfig` keys are validated at construction.
- **Activities created**: model request (streaming happens inside), `FunctionToolset.call_tool`, `MCPToolset.get_tools`/`call_tool`, `DynamicToolset.get_tools`/call, `validate_args` (tools with an `args_validator`), per-event event-stream-handler activities, workspace calls, `compact_messages`, suspended-turn cancel, and `@durable_operation` capability methods. Names derive from agent `name` and toolset `id`. Defaults: `start_to_close_timeout=60s`; model activities get `heartbeat_timeout=30s`; activities heartbeat in the background. **Temporal's default `RetryPolicy.maximum_attempts=0` is unbounded and PydanticAI does not override it.**
- **Serialization.** `deps`, `model_settings`, `RunContext.metadata`, tool metadata and `ApprovalRequired(metadata=...)` must be Pydantic-serializable and arrive in activities as JSON shapes (re-validate with a `TypeAdapter`). `deps` is copied into every activity payload (issue #6976; claim-check codec is the current answer). Non-serializable clients must be rebuilt in activities from serializable configuration (issue #3573).
- **`TemporalRunContext` in activities** exposes `deps, run_id, conversation_id, metadata, retries, tool_call_id, tool_name, tool_call_approved, tool_call_metadata, retry, max_retries, run_step, partial_output, usage, usage_limits, trace_include_content, instrumentation_version, loaded_capability_ids, discovered_tool_names, capability_active` plus snapshots. Reading `model`, `prompt`, `messages`, `model_settings`, `tracer`, `validation_context`, `capabilities` raises `UserError`; `ctx.emit()`/`ctx.enqueue()` raise (issue #7971); `ctx.usage` mutations are discarded, so delegate-agent usage is lost unless returned explicitly (issue #6886). `run_id`/`conversation_id` are derived from the workflow run since v2.55.0.
- **Refused in workflow code**: `run_sync()`, `run_stream_sync()`, `AgentStream.cancel()`, `RunContext.cancel()`, `CancellationToken`, `agent.run(capabilities=[...])` (except `Instrumentation`), `@agent.toolset` inside a workflow, per-run or overridden executing toolsets, unregistered `Model` instances, `output_type` containing `BinaryImage`. One durability engine per agent.
- **Streaming**: `run_stream()`, `run_stream_events()`, `iter()` work but events are buffered and replayed after the model activity. Live handling: `TemporalDurability(event_stream_handler=...)` (runs in activities, must be idempotent), `ProcessEventStream` (workflow side, deterministic), or Workflow Streams via `event_stream_topic` + `AgentEventStream` + `stream_agent_events()` (duplicates possible on retry; one subscription per run).
- **MCP**: each `get_tools`/`call_tool` activity opens its own `MCPToolset` session and closes it; the workflow keeps the recorded tool list, so discovery costs one activity per run. `MCPToolset(url, auth=<bearer|httpx Auth|'oauth'>, headers=, http_client=<httpx client for private CA/mTLS>, process_tool_call=, tool_error_behavior=, include_instructions=, elicitation_handler=, sampling_model=, client_info=)`; filtering via `FilteredToolset`/`.prefixed()`.
- **Human in the loop**: `requires_approval=True`; `ApprovalRequired(metadata=)`; `CallDeferred`; `ApprovalRequiredToolset`/`.approval_required(fn)`; run ends with `DeferredToolRequests(approvals, calls, metadata)` when it is in `output_type`; resume with `DeferredToolResults(approvals={id: bool | ToolApproved(override_args=) | ToolDenied(message)}, calls=...)` through `agent.run(message_history=..., deferred_tool_results=...)` or `agent.run(conversation=..., deferred_tool_results=...)` (`ConversationTypeAdapter`); inline `HandleDeferredToolCalls(handler)` whose handler "can contain pure resolution logic (e.g. waiting for a signal in a durable execution workflow)". Under Temporal, `args_validator` runs in a `validate_args` activity before approval and again on resume with `tool_call_approved=True`. **No official PydanticAI-plus-Temporal approval sample exists**; open design issue #6580; pitfall #7537 (a queued message at a `DeferredToolRequests` pause discards the pause). The docs state approval is not an authorization boundary.
- **Limits and retries**: `UsageLimits(cost_limit, request_limit=50, tool_calls_limit, input_tokens_limit, output_tokens_limit, total_tokens_limit, per_request_input_tokens_limit, count_tokens_before_request)` is enforced workflow-side and does not see Temporal, SDK or transport retries ("retry multiplication"); guidance is `max_retries=0` on provider clients and a bounded `retry_policy` in `model_activity_config`. `UsageLimitExceeded` is an `AgentRunError` and fails the workflow.
- **Continue-as-new**: not built in (issue #6675, PR #7312 pending). Workaround: a capability `before_model_request` hook raises when `workflow.info().is_continue_as_new_suggested()`; the workflow catches it and calls `workflow.continue_as_new(...)` with the stored conversation. Workflow Streams follow the chain.
- **Pitfalls**: renaming agent `name`, toolset `id`s or `models=` keys breaks in-flight replay; adding an `args_validator` or a workspace changes the activity sequence (use `workflow.patched` or Worker Versioning); payload models are durable contracts; `ProcessEventStream`, `@on_event` listeners, history processors and `ResolveModelId` resolvers run workflow-side and on replay; `logfire.configure()` must precede client/worker creation. Closed issues of note: #5875 (MCP tool cache broke replay), #3702, #3701.
- **Samples**: `temporalio/samples-python` has **no** `pydantic_ai` directory. The official <https://github.com/pydantic/pydantic-ai-temporal-example> (Slack dinner bot: one workflow per thread, `submit_message` signal into an `asyncio.Queue`, `wait_condition`) still uses the deprecated `TemporalAgent` and has no continue-as-new. Temporal's blog post on PydanticAI exists but could not be fetched.

### 1.1 Other PydanticAI v2 primitives relevant to the SDK

- **Agent Spec** (`docs/agent-spec.md`): YAML or JSON; `Agent.from_file`, `AgentSpec.from_file`/`to_file(schema_path=)` (writes a companion JSON Schema), `Agent.from_spec(spec, deps_type=, output_type=, **overrides)`. Fields: `model, name, description, instructions, model_settings, capabilities, deps_schema, output_schema, retries | AgentRetries, end_strategy, tool_timeout, instrument, metadata`. Merge rules: scalars override, `instructions` and `capabilities` merge (spec first), `model_settings` merge additively, `output_type` beats `output_schema`. Capability syntax `Name` / `{Name: value}` / `{Name: {kwargs}}` → `Capability.from_spec`; custom types via `custom_capability_types=[...]` (explicit registration, no entry points). Callable tools and toolsets are not spec-expressible (issues #5266, #5471 open). `output_schema` yields `StructuredDict` with no runtime validation of properties. `{{var}}` templates validated against `deps_schema`/`deps_type` at construction.
- **Capabilities** (`docs/capabilities/overview.md`, `custom.md`): `AbstractCapability` with `id`, `description`, `defer_loading`; configuration methods `get_toolset`, `get_native_tools`, `get_wrapper_toolset`, `get_instructions`, `get_model_settings`, `get_model`, `resolve_model_id`, `get_workspace`, `for_agent`, `for_run`, `get_ordering` (`CapabilityOrdering(position, wraps, wrapped_by, requires)`), `get_serialization_name`, `from_spec`; lifecycle hooks `before_/after_/wrap_/on_*_error` for run, node, model request, tool validate, tool execute, output validate/process; `prepare_tools`, `prepare_output_tools`, `wrap_run_event_stream`, `handle_deferred_tool_calls`; `@on_event`; `@durable_operation(name=)` for engine-dispatched methods (needs a stable `id`). `before_*` run in capability order, `after_*` and error hooks in reverse. Skip exceptions: `SkipModelRequest`, `SkipToolValidation`, `SkipToolExecution`. Declarative `Capability(id, description, instructions, defer_loading)`; on-demand capabilities load through a reserved `load_capability` tool and persist across resume by `id`.
- **Hooks** (`docs/hooks.md`): `Hooks()` capability with `@hooks.on.before_model_request` etc., timeouts, `ApprovalRequired`/`CallDeferred` may be raised from `before_tool_execute`.
- **Harness** (`pydantic-ai-harness`, 0.x, separate package): `Skills`, `Guardrails` (`InputGuardrail`, `OutputGuardrail`, `ToolGuardrail(guard, result_guard)`, `GuardrailResult.allow/block/replace/retry/approve`, detectors `redact_secrets`, `redact_personal_data`, `blocked_keywords`), `SpendLimits(Budget(usd, tokens, window=run|conversation|day|month|total, scope=), store=InMemorySpendStore|RedisSpendStore|custom BatchSpendStore, on_unpriced=, warn_at=)` with post-hoc accounting ("a brake on a runaway loop, not an accounting ledger") and durable-aware dedup, `ToolCallJudge(model, tools, question, on_uncertain='block'|'allow'|'ask', ...)` ("a filter, not a security boundary"), `PromptInjectionDefender` (StackOne detector; pattern-based, optional local ML; `block_high_risk`), `StepPersistence` (snapshots and tool-effect ledger; `InMemory|File|Sqlite|Mongo|Postgres` stores), `Subagents` (`delegate_task` tool; `forward_usage`, `max_depth=3`; not spec-serializable; stopped loading agent files by default in v2.52.0), `AskUser`, `Instrumentation(settings=InstrumentationSettings(...))`.
- **Testing** (`docs/testing.md`): `TestModel`, `FunctionModel` (scripted `ModelResponse` per turn), `agent.override(model=, deps=, toolsets=)`, `models.ALLOW_MODEL_REQUESTS = False`, `capture_run_messages`. **Evals** (`pydantic_evals`): `Dataset`, `Case`, `Evaluator`/`EvaluatorContext`, `EvaluationReport`, LLM-judge and span-based evaluators, optional OpenTelemetry integration.

## 2. Temporal durable-agent practice (Python SDK)

Sources: `github.com/temporalio/documentation` (`.mdx` sources of docs.temporal.io), `temporalio/sdk-python` (code, README, releases), `temporalio/samples-python`, `temporalio/ai-cookbook`, `temporal-community/temporal-ai-agent`; blog posts via search summaries only.

- **Positioning.** The agent loop runs in the Workflow (deterministic; replay never re-asks the model); every model call, tool call and external API call is an Activity. Temporal's reference architecture caps iterations (`MAX_STEPS_PER_TURN = 20`), fails non-retryably at the cap, uses Update validators to reject bad input before it enters history, and trims context because of the 2 MB payload limit. Every first-party integration (OpenAI Agents, Google ADK, Strands, LangGraph, PydanticAI) uses **per model call / per tool call** activities, never per agent run.
- **Heartbeats and timeouts.** `activity.heartbeat(*details)` every ~10–30 s; `heartbeat_timeout` ≈ 2–3× the interval and shorter than `start_to_close_timeout`; resume from `activity.info().heartbeat_details`; cancellation is delivered only through heartbeats. Activities must set `start_to_close_timeout` or `schedule_to_close_timeout`.
- **Side effects.** Activities are at-least-once; recommended idempotency key is workflow run ID + activity ID (`activity.info().workflow_run_id`, `.activity_id`, `.attempt`). Permanent failures: `ApplicationError(msg, type=..., non_retryable=True)` or caller-side `RetryPolicy(non_retryable_error_types=[...])`; workflow sees `ActivityError.cause`. Non-`ApplicationError` exceptions in workflow code fail the workflow task and retry forever. `RetryPolicy` defaults: `initial_interval=1s`, `backoff_coefficient=2.0`, `maximum_interval=None` (100× initial), `maximum_attempts=0` (unlimited).
- **Messages.** Signal (async, no return), Update (synchronous, returns a value, can be rejected; `@workflow.update(name=, dynamic=, unfinished_policy=, description=)`, validator via `@<handler>.validator`, **synchronous, no I/O, cannot call Activities, rejected Updates leave no history event**), Query (read-only). `handle.execute_update()`, `handle.start_update(wait_for_stage=)`, update-with-start (`execute_update_with_start_workflow`, server ≥1.28). Server limits: **10 in-flight Updates, 2,000 total Updates per execution**. `await workflow.wait_condition(fn, timeout=)` raises `asyncio.TimeoutError`; toggling `timeout` between `None` and a value is non-deterministic. Before returning or continue-as-new: `await workflow.wait_condition(workflow.all_handlers_finished)`; never continue-as-new inside a handler.
- **Approval pattern** (`docs/design-patterns/approval.mdx`): record approver, decision, reason and timestamp; verify approver permissions and data completeness before accepting; always set a timeout with defined behaviour; handle late signals; deduplicate duplicate approvals with idempotency keys; expose a Query listing all approval attempts. Validators cannot do directory or IAM lookups, so approver checks inside the workflow are limited to data already in state or to a token verifiable deterministically; anything else runs in an Activity before acceptance. **No Temporal doc or sample binds approval to an action hash**; that is a Zetra design choice (see section 4).
- **Limits** (`docs/production-deployment/self-hosted-guide/defaults.mdx`, `docs/workflow-execution/limits`): history **warn 10,240 events / 10 MB, terminate 51,200 events / 50 MB**; payload **warn 256 KB, error 2 MB** (not configurable on Cloud); 4 MB gRPC message; 2,000 pending activities/children/signals/cancels (≤500 recommended); IDs ≤1,000 characters.
- **Continue-as-new.** `workflow.continue_as_new(arg, *, task_queue=, run_timeout=, retry_policy=, memo=, search_attributes=, initial_versioning_behavior=, ...)`; trigger on `workflow.info().is_continue_as_new_suggested()` plus `get_current_history_length()/size()`; children do not carry over. The community agent uses `MAX_TURNS_BEFORE_CONTINUE=250` with summarization.
- **Large payloads.** Built-in **External Storage** (public preview): `dataclasses.replace(DataConverter.default, external_storage=ExternalStorage(drivers=[S3StorageDriver(...)]))`, default `payload_size_threshold` 256 KiB, custom `StorageDriver`; order is PayloadConverter → PayloadCodec → storage, so encryption precedes externalization. `PayloadCodec.encode/decode` runs outside the sandbox; Codec Server exposes `/encode`, `/decode` (and `/download`), `X-Namespace` header, CORS for the UI, HTTPS and verification of the Cloud access token; failure messages are not encoded by default.
- **Versioning.** `workflow.patched(id)` / `deprecate_patch(id)` three-step process; 1.31 added `patch_activation_callback`. **Worker Versioning is GA (2026-03-30)**: `Worker(deployment_config=WorkerDeploymentConfig(version=WorkerDeploymentVersion(deployment_name, build_id), use_worker_versioning=True, default_versioning_behavior=VersioningBehavior.PINNED|AUTO_UPGRADE))`, per type `@workflow.defn(versioning_behavior=...)`; CLI `temporal worker deployment set-current-version|set-ramping-version`. Decision table: short runs → PINNED; spans deploys without continue-as-new → AUTO_UPGRADE plus patching; long with continue-as-new → **PINNED plus Upgrade-on-Continue-as-New** (`initial_versioning_behavior=ContinueAsNewVersioningBehavior.AUTO_UPGRADE`, detect with `is_target_worker_deployment_version_changed()`), explicitly recommended for agent workflows that wait on humans. The SDK docstring still labels `deployment_config` experimental.
- **Testing.** `WorkflowEnvironment.start_time_skipping()` (timers fast-forward except while activities run; test server not available on Linux/Windows ARM), `start_local()`, `ActivityEnvironment`; `Replayer(workflows=[...]).replay_workflow(WorkflowHistory.from_json(...))` and `replay_workflows(client.list_workflows(q).map_histories())`; CI pattern: download recent histories, replay, fail the build.
- **Security.** Codec on your workers means Cloud cannot read payloads; TLS 1.3 in transit. Cloud auth: `Client.connect(..., api_key=, tls=True)` or `TLSConfig(client_cert, client_private_key, server_root_ca_cert)`; one **namespace-scoped service account per worker deployment**; rotate by swapping `worker.client`. Namespaces are the isolation unit; cross-namespace only via allow-listed Nexus endpoints. Self-hosted: `ClaimMapper` + `Authorizer` (default authorizer is a no-op). **No per-task-queue authorization exists**: per-tenant task queues give routing isolation only; credential boundaries need namespaces. `Client.connect(identity=)` / `Worker(identity=)`. **The workflow sandbox is not a security boundary** (README: "not secure"). Untrusted code needs a real sandbox (OpenAI plugin `SandboxAgent` with remote Daytona/E2B clients is pre-release).
- **Nexus** in Python: `@nexusrpc.handler.service_handler`, `@temporalio.nexus.workflow_run_operation`, `sync_operation`, `workflow.create_nexus_client(...)`; newer APIs labelled pre-release. Standalone Activities GA in 1.33.
- **Observability.** `temporalio.contrib.opentelemetry.TracingInterceptor` (older) vs `OpenTelemetryPlugin(add_temporal_spans=True)` (experimental; deterministic span IDs, nothing exported during replay; `ReplaySafeMeterProvider/LoggerProvider` since 1.32). Metrics via `Runtime(telemetry=TelemetryConfig(metrics=PrometheusConfig(...)))`, low-cardinality tags only. `workflow.logger` adds `temporal_workflow` extras (attempt, namespace, run_id, task_queue, workflow_id, workflow_type); `activity.logger` adds `temporal_activity` extras (activity_id, activity_type, attempt, workflow_id, workflow_run_id, ...). Correlate LLM spans by attaching these IDs and the idempotency key.
- **Integrations.** OpenAI Agents SDK integration is now the standalone `temporalio-openai-agents` (1.1.0, 2026-10-01; `ModelActivityParameters`, `activity_as_tool`, `temporal_mcp_server`); `temporalio.contrib` has `google_adk_agents`, `langgraph`, `strands`, `deepagents`, `langsmith`, `opentelemetry`, `pydantic`, `workflow_streams`, but **no `pydantic_ai`** (PydanticAI ships its own). Reference code: `temporal-community/temporal-ai-agent` (signals `user_prompt`/`confirm`/`end_chat`, queries, confirmation gate, MCP client in activity), `temporalio/ai-cookbook` (`agents/human_in_the_loop_python`, `guardrails_hard_rules_python`, `foundations/claim_check_pattern_python`), sample `openrouter/budget_gate`.
- **Schedules, children, cancellation, local activities.** `client.create_schedule(...)` with `ScheduleOverlapPolicy`; children for separate task queues, own history ceiling or independent lifetime (`ParentClosePolicy`, ≤~1,000 per parent, do not survive parent continue-as-new); Python has **no cancellation-scope API** (asyncio task cancellation; `ActivityCancellationType` TRY_CANCEL | WAIT_CANCELLATION_COMPLETED | ABANDON; activity must re-raise `CancelledError`); local activities for <~5 s idempotent in-memory validation only ("if you haven't measured a latency problem, start with regular Activities").
- **Unverified**: `temporalio.runtime.OpenTelemetryConfig`; exact blog text; Python Nexus GA labelling; PyPI release date of 1.34.0.

## 3. Agent Skills format

Sources: `github.com/agentskills/agentskills` (`docs/specification.mdx`, `skills-ref`), platform.claude.com and code.claude.com docs, `modelcontextprotocol/modelcontextprotocol` (`docs/extensions/skills/`), framework sources.

- **Specification.** Frontmatter: `name` (required; 1–64 chars; lowercase letters, digits, hyphens; no leading/trailing/consecutive hyphens; must match the parent directory), `description` (required; 1–1024 chars; what it does and when to use it), optional `license`, `compatibility` (≤500 chars), `metadata` (string map), `allowed-tools` (space-separated, **experimental**, support varies). Layout: `SKILL.md` plus optional `scripts/`, `references/`, `assets/`. Progressive disclosure: ~100 tokens of metadata per skill at startup, body (<5,000 tokens recommended, under 500 lines) on activation, resources only when needed; references one level deep.
- **Anthropic additions**: names must not contain XML tags or the reserved words "anthropic"/"claude"; descriptions in third person; MCP tool references as `Server:tool`. Claude Code extends frontmatter (`when_to_use`, `argument-hint`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork`, `hooks`, `paths`, `shell`) and keeps 5k tokens per skill through compaction.
- **Skills over MCP** extension `io.modelcontextprotocol/skills` (SEP-2640, Final): `skills/list`, `skills/get`, file bytes via `resources/read`; entries carry frontmatter plus a manifest of file URIs with SHA-256 digests and sizes; hosts must verify size and digest, treat content as untrusted, and require **explicit per-skill approval for `allowed-tools` or code execution**; a changed manifest revokes prior approval.
- **Python tooling.** `skills-ref` (PyPI 0.1.1, 2026-01-10, Python ≥3.11): `validate()`, `read_properties()`, `to_prompt()`; CLI `skills-ref validate|read-properties|to-prompt`; README says "for demonstration purposes only". Zetra's `agentctl skills validate` already enforces the same allowed-key set and can shell out to `skills-ref`.
- **Framework adoption.** PydanticAI Harness `Skills` reads only `name`, `description` and the body; **does not run scripts or read `references/`/`assets/`**; warns once about unsupported fields. Community `pydantic-ai-skills` (DougTrajano) adds `run_skill_script`, `read_skill_resource`, registries and sandboxing. OpenAI Agents SDK has `agents.sandbox.capabilities.skills.Skills` (hand-written frontmatter parser, `load_skill` tool in lazy mode). Microsoft Agent Framework has `SkillsProvider` with a pluggable `SkillScriptRunner`. Google ADK: none found.

## 4. Zero-trust standards a framework should map to

- **OWASP Top 10 for Agentic Applications 2026** (names confirmed via OWASP AISVS and related repos; official PDF unreachable): ASI01 Agent Goal Hijack; ASI02 Tool Misuse and Exploitation; ASI03 Identity and Privilege Abuse; ASI04 Agentic Supply Chain Vulnerabilities; ASI05 Unexpected Code Execution; ASI06 Memory and Context Poisoning; ASI07 Insecure Inter-Agent Communication; ASI08 Cascading Failures; ASI09 Human-Agent Trust Exploitation; ASI10 Rogue Agents. Named patterns: Intent Capsule (signed immutable mandate per execution cycle), Zero-Trust Tooling (strict schema validation before every tool call), Least-Agency. OWASP LLM Top 10 2026 (secondary sources only): Prompt Injection #1, Sensitive Information Disclosure #2, Excessive Agency #3.
- **MCP specification 2026-07-28** (previous 2025-11-25). Authorization: authorization servers MUST implement OAuth 2.1; MCP servers MUST publish RFC 9728 Protected Resource Metadata; clients MUST send RFC 8707 `resource`; servers MUST validate audience and MUST NOT pass tokens through; Client ID Metadata Documents SHOULD be supported, Dynamic Client Registration is deprecated; RFC 9207 `iss` SHOULD; 403 `insufficient_scope` step-up. Tool annotations `readOnlyHint` (default false), `destructiveHint` (default **true**), `idempotentHint`, `openWorldHint` are **untrusted unless the server is trusted**; "there SHOULD always be a human in the loop with the ability to deny tool invocations". Elicitation has form and URL modes (credentials only via URL mode). Other changes: stateless core (no `initialize`, no `Mcp-Session-Id`), Roots/Sampling/Logging deprecated, Tasks moved to an extension, Enterprise-Managed Authorization extension (IdP-issued ID-JAG exchanged for an access token). Zetra's `gateway.py` pins 2025-11-25 and will need a revision for the stateless core.
- **Agent identity.** `draft-klrc-aiagent-auth-03` (2026-07-06, individual Informational draft, not WG-adopted): agent = workload with one WIMSE identifier (may be a SPIFFE ID), short-lived key-bound X.509/JWT SVIDs, Workload Proof Tokens or RFC 9421 HTTP message signatures, OAuth authorization code for user delegation, RFC 8693 token exchange, transaction tokens, static API keys as an anti-pattern, tools must not forward agent tokens, tamper-evident audit logs with agent identity, delegated subject, action and decision. NIST NCCoE concept paper (2026-02-05) anchors OAuth 2.x, OIDC, SCIM, SPIFFE, NGAC, SP 800-207, SP 800-63-4. WG items: `draft-ietf-wimse-workload-creds`, `draft-ietf-oauth-spiffe-client-auth`.
- **Approval bound to the exact action.** *Loopjacking* (arXiv 2609.21081, 2026-09-17, preprint): approval for action A released a materially different B via incomplete representation at review or post-approval state substitution; reproduced on several agent servers; defence is to record the complete canonical operation, rebuild the to-be-executed operation at the last authorization point after all argument resolution, compare, and check expiry and consumption. Microsoft agent-governance-toolkit **ADR-0030** (2026-06-11): `ActionBinding{operation, agent_id, subject_id, target(tool name, tool schema version, resource), parameters}` → **RFC 8785 JCS → SHA-256 `action_digest`**; `require_approval` is a suspended state; the enforcement point recomputes the digest immediately before execution and atomically checks allow, unexpired, unconsumed and policy-version match; hash-linked append-only chain. `draft-schrock-ep-authorization-receipts-06`: signed Authorization Context with `action_hash`, `policy_hash`, nonce ≥128 bits, `issued_at`/`expires_at`, `prev_receipt_hash`, ConsumeOnce state machine. OWASP AISVS 9.4.2 asks for canonical payload hash, previous-record hash, policy decision hash, agent identity and signature per action. Zetra's `canonical()` uses `json.dumps(sort_keys=True)`, which is close to but not RFC 8785.
- **Alignment checklist**: per-agent short-lived workload identity (no shared service accounts or static keys); OAuth 2.1 + RFC 9728 + RFC 8707 + audience validation + no token passthrough for every MCP server; schema-validate every tool call and never trust annotations from untrusted servers; approvals bound to a JCS/SHA-256 digest of the exact executable action with expiry and single use, re-verified at the enforcement point; hash-chained audit records carrying agent identity, delegated principal and policy decision; skills and tool descriptions treated as supply chain with digest-pinned manifests and per-skill approval for `allowed-tools`.

## 5. Prior art for declarative agents with generated guardrails

- **agentgateway** (Rust; Linux Foundation / AAIF project since 2026-06-04): JWT/API-key/OAuth authentication and CEL authorization in YAML (`mcpAuthorization: ['jwt.sub == "..." && mcp.tool.name == "..."']`); unauthorized tools are hidden from `tools/list` and denied on call; AuthZEN external authorization; regex/moderation/webhook guardrails. Borrow: policy as expressions over typed request attributes; tool visibility derived from policy.
- **Microsoft Agent Framework declarative** (`agent-framework-declarative` 1.2.1, 2026-10-08): YAML `kind: Prompt`, `model{id, provider, options}`, `tools[{kind: function | mcp, url, allowedTools, approval}]`, `=Env.VAR` indirection. Borrow: discriminated tool kinds, per-MCP-tool allowlist and approval mode in the manifest, environment indirection for secrets.
- **Google ADK Agent Config**: `root_agent.yaml` with `agent_class`, `tools[name]`, `sub_agents[config_path]`, shipped JSON Schema for editors; experimental. Borrow: shipped schema, composition by file reference.
- **LangGraph `langgraph.json`**: deployment manifest with `module.py:var` graph entrypoints. **Letta Agent File (.af)**: portable export with secrets nulled.
- **Durable engines for PydanticAI**: Temporal (`TemporalDurability`), DBOS (`DBOSAgent`), Prefect, Restate (`RestateAgent`; approvals via suspended handlers), AWS Lambda; Inngest AgentKit is TypeScript-only.
- **PydanticAI's own declarative layer** is the closest prior art: `AgentSpec` with a capability registry resolved by name through `from_spec`, override merge rules, template validation at construction, and `clai -a agent.yml`.
