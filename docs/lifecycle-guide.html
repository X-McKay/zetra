09 / General developer guide

Build, test, release, and maintain an agent

Follow these eight steps for a new agent or a change to an existing one. Start with a predictable project structure, define the job, limit inputs and actions, and test both useful and forbidden outcomes. Use the same process for a read-only assistant, a summarizer, or an agent with approved actions.

Current scope. Zetra provides local scaffolding, checks, evaluations, and deployment candidates. Its starter uses an offline knowledge fixture. Production identities, isolation, service connections, and release approval require separately tested platform integrations.

Step 1 / Define the job and its limits

Do: Write a short purpose statement. Name the owner, users, inputs, expected output, permitted tools/data, and any actions requiring review. Explain what happens when information is missing or a request is outside scope.

DefineExample for a read-only assistant
Purpose and scopeAnswer questions from approved documents; no changes to source systems.
SuccessUseful, supported answers with correct sources; uncertainty reported clearly.
Failure casesInvalid input, missing sources, misleading retrieved text, unavailable tool, exhausted budget, or stop request.

For agents that change records, send messages, or trigger other effects, define review and safe-retry rules too. Required approval depends on the action and risk policy; read-only answers do not automatically need human approval.

Done when: The owner agrees on the useful outcome, permission limits, data handling, and measurable failure cases.

Step 2 / Create the project and organize its files

Do: Choose Nix or mise using the contributor instructions. In this repository, scaffold a new empty directory:

nix develop
just bootstrap
uv run --locked zetra init build/my-agent --name my-agent
uv run --locked zetra check build/my-agent

The commands use ignored build/ for a disposable starter. Put real work in a version-controlled project directory, and replace the sample metadata.owner and metadata.businessFunction.

Keep agent.yaml at the project root; the current CLI reads it there. The starter creates src/knowledge/ and knowledge.factory:create_agent. Its name changes metadata, not the Python package. The recommended layout below uses my_agent; if you rename the starter, update its entrypoint, imports, and tests together.

Done when: The entrypoint works, ownership/dependencies are recorded, and each file has a clear purpose.

Step 3 / Validate inputs and limit actions

Do: Validate input before tools. Build from supplied dependencies without connecting or reading secrets during construction. Keep retrieved text as data; it cannot grant permission or choose arbitrary tools.

# Conceptual factory shape; define MyAgent.run(request) for your purpose.
from zetra.runtime import Agent, RuntimeDependencies

def create_agent(dependencies: RuntimeDependencies) -> Agent:
    return MyAgent(dependencies)
# Supported starter values under spec in agent.yaml:
entrypoint: knowledge.factory:create_agent
capabilities: [knowledge.read]
execution: local
budgets: {maxSteps: 3, maxSeconds: 30, maxCostUsd: 0.05}

The starter accepts {"key":"zetra"} and reads a supplied knowledge fixture. Run it before replacing the behavior:

uv run --locked zetra run build/my-agent --input '{"key":"zetra"}'

For consequential actions, separate proposal from execution and validate required approval at the destination. If work must resume after failure, use predictable workflow ordering and activities for outside calls. Retrying an activity can repeat its calls; the destination needs safe deduplication. The current Temporal worker supports only its reviewed read capabilities and rejects write-capable packages.

Done when: Valid requests work, invalid requests stop clearly, and calls stay within declared authority.

Step 4 / Test the behavior your agent needs

Do: An evaluation compares behavior with expected results. Run the starter's tests, then replace/add cases for your purpose:

uv run --locked zetra eval build/my-agent --output build/my-agent-evidence.json
uv run --locked zetra check build/my-agent --evidence build/my-agent-evidence.json

The CLI derives requirements from declarations. It also requests data.redacted for confidential/restricted/unknown data, trajectory.stop for autonomous execution, and workflow.replay for Temporal. Unknown data/autonomy or unclassified capabilities require higher-risk (T3) review; business impact can raise risk further. Static hints are incomplete, so review undeclared behavior too.

Use positive, negative, and exact-boundary cases. For writes, assert no effect without authority and safe retry. Missing required scenarios or critical failures block review. If using a real model, set aside cases you do not use to adjust prompts, repeat runs, and assess useful answers, correct citations, uncertainty, failures, latency, and usage. A model scoring an answer does not replace exact assertions about security rules.

Done when: Required tests run with meaningful assertions and current evidence; real-model quality is measured separately when applicable.

Step 5 / Optimize measured cost and speed

Do: Measure cost per useful task, tokens, calls, retries, latency, and quality. Change one variable at a time—context length, model, or repeated lookups—and compare the same cases.

Illustration, not a benchmark: $1 total spend, including failed attempts/retries, divided by ten useful results = $0.10 per useful result. Lower spend with fewer useful results may be worse.

Cache authorized reads only, with customer/business-unit scope, source version, and a freshness limit. Never reuse another customer's data, approval tokens, or authorization decisions. Keep required human review unchanged. Local budget helpers only work when code calls them; retries may reset counters. They do not measure provider bills or enforce shared spending.

Done when: Measured improvements preserve required quality, permissions, approval rules, and stop behavior.

Step 6 / Review the change and pass CI

Do: Run just check and your agent's evaluations. Review code, instructions, dependency lock, permissions, and evidence together. Regenerate evidence after material changes. Prepare a catalog candidate—a record for review:

uv run --locked zetra catalog build/my-agent \
  --evidence build/my-agent-evidence.json \
  --output build/my-agent-catalog.json

Explain changed behavior, consequences, tests, and remaining risks in the pull request. Continuous integration (CI) means automated checks on changes. The committed GitHub workflow checks dependencies, code/types, tests, docs, and shipped examples on temporary runners without deployment/model credentials. Add your new package to the appropriate CI checks. Inspect the actual GitHub result; local success does not prove it ran.

Done when: CI passes, reviewers understand changed authority, and evidence matches the package.

Step 7 / Hand off a release for controlled rollout

Do: Supply the package, exact image version, risk review, evidence, requested connections, and operating instructions. An immutable image reference uses a content digest to identify exact image bytes.

# Current rendered Deployment: a plan that cannot start the agent.
spec:
  replicas: 0

The renderer does not install integrations, grant permission, or publish the catalog. Continuous delivery (CD) is the proposed platform process for verifying approved artifacts and installing them. Production needs identity and isolation tested on the deployed setup, checks that approved rules are active, relevant destination approval/retry controls, and an exercised stop path.

Platform engineers resolve connections and credentials. Missing mandatory controls block activation. Use a limited reviewed rollout, monitor results, and keep a tested rollback plan.

Done when: The platform and owner approve the actual release/environment, backed by matching installation and enforcement evidence.

Step 8 / Monitor, stop, reconcile, and update

Do: Monitor useful outcomes, refusals, failures, pending reviews, retries, latency, and spend. Record safe release/run/operation identifiers; avoid raw credentials and sensitive prompts. Arrange daily review and owner-defined error/cost/latency alerts. Unauthorized effects or suspected secret leaks need immediate pause/escalation. The toolkit does not supply an alert service.

Before retrying an uncertain action, check what happened and its receipt. Reconciliation means establishing the actual outcome. Reuse the same operation safely rather than creating another effect. Use the approved stop procedure; local STOP files only work when code checks them, and stopping compute does not undo committed effects.

After fixing a failure, add a test for that failure (a regression test), refresh evidence, and repeat review/release. Retest changes to prompts, models, dependencies, tools, permissions, and runtime integrations.

See platform integration details and security boundaries. For a longer worked example involving approved actions, read the incident-triage walkthrough.

Done when: Operators can diagnose failures, stop new effects, reconcile outcomes, and release tested corrections.
