A practical guide for developers

Start with one useful task

Build an agent by defining a useful job, giving it a small set of tools, and checking both its answers and its actions. This guide follows nine steps from an empty project to a maintained release. The illustration is an assistant that answers questions using approved documents. The same steps apply to other agents; the data, tools, and approval rules change with the job.

Runnable example. The accompanying Python starter uses local sample documents and an explicitly named offline answer fixture. It needs no model key or network connection. Its results test code and example behavior, not the quality of a real language model.

Step 1 / Define the problem and objective

Do: Write the job in one sentence, then describe a useful result and the limits around it. For example: “Answer staff questions using the approved handbook, cite the supporting documents, and say when those documents do not answer the question.” Decide whether an agent is needed: a fixed lookup, form, or ordinary function may solve a simpler job with fewer moving parts.

DecisionExampleWrite down
Users and successStaff receive accurate, understandable answers with valid sources.Owner, intended users, representative questions, measurable quality and response-time goals.
Allowed actionsRead approved documents and draft an answer.Permitted tools; forbidden changes, messages, and purchases; actions needing review.
ConnectivityLocal files first; an approved document service later.Services, destinations, credentials, user permissions, timeouts, and offline behavior.
DataPublic/synthetic samples for development; restricted access for real staff material.Inputs, outputs, sensitivity, permitted storage, retention/deletion, user identity, and who may see results.
UncertaintyMissing evidence produces “needs review,” not a guessed policy.Refusal, clarification, escalation, stop, and recovery behavior.

Agree on a small scorecard before building. Illustrative targets are: supported-answer success at least 90% of all assigned evaluation tasks; correct access checks in every listed permission case; 95% of completed requests within eight seconds; and total cost per useful task below an owner-approved budget. These are example targets, not measured results. Compare with the current manual process or a simple search interface: an agent should improve a useful outcome, not merely add a conversational screen.

Consider how data travels. A question, retrieved passage, prompt, answer, and log can each expose information. Decide what may leave the organization before connecting a model or remote tool. Keep secrets out of prompts, source files, sample datasets, and logs. A user who can ask a question is not automatically allowed to read every document.

For an agent that changes records or triggers effects, define the consequence separately from answer quality. Specify who approves, what exact action they approve, how long approval lasts, and what happens after an uncertain response. Read-only answers do not inherently require human approval, but sensitive or consequential decisions may.

Done when: The owner agrees on success, permitted connections/data/actions, and what the agent must do when it cannot safely finish.

Step 2 / Create the repository and files

Do: Put behavior, instructions, tests, and operating notes in a version-controlled project. Start small and separate files when their responsibilities grow. Keep the source files people edit separate from generated reports. The layout below is a suggested Python project, not a universal agent standard.

An empty __init__.py marks a regular Python package. Add workflow/state files if the job needs multiple resumable stages, and deployment files when a hosting environment is chosen. Do not create empty directories just to imply a capability exists.

The starter implements the core reader, typed contracts, offline fixture, instructions, tests, and cases; the broader layout shows extensions to add only when needed. Here are short file examples. Python type hints describe expected shapes; explicit runtime checks must still reject bad input.

This is the starter's own configuration format, not a universal agent manifest. Your code must load and validate it. Additional time, cost, and output limits require implementation rather than extra unrecognized settings. Keep credentials outside it. An operating note can say “pause new requests; inspect failed tool calls; check access before retrying”; a policy record can list “document owner, permitted audience, approval date,” but becomes effective only when the relevant code/service enforces it.

Use Python 3.11 or newer for the starter. It uses the standard library, so no package installation is required. For a larger project, create a virtual environment (python3 -m venv .venv), use its interpreter, and adopt one dependency manager. If using uv, commit pyproject.toml and uv.lock together and use a locked install in automated checks. Review configuration and scripts before executing them.

Done when: Another developer can locate each responsibility, reproduce setup, and identify the exact files that affect a run.

Step 3 / Build skills and tools

Do: Separate a procedure from the operations it uses. A skill explains how to carry out a task; a tool is code that performs an operation. “Find relevant documents, compare evidence, and draft an answer” is a skill. Reading a document is a tool. A skill file does not implement that reader or grant file/network access.

Optional skills/answer-from-documents/SKILL.md, for a host that supports Agent Skills:

---
name: answer-from-documents
description: Answer questions using approved documents and cite supporting evidence.
---
1. Read only documents the caller is permitted to access.
2. Identify evidence that addresses the question.
3. State missing or conflicting evidence.
4. Draft an answer with source IDs; do not invent a source.

The Agent Skills specification defines a skill directory with SKILL.md and optional scripts, references, and assets. Hosts differ in how they load and apply skills. Review included scripts like other executable code; instruction text is not an enforcement boundary.

Make tools narrow and understandable. Prefer read_document(document_id) to unrestricted filesystem access. Define allowed arguments, maximum size, return shape, side effects, failure behavior, and permissions. Give the model only the tools it needs. Do not let it manufacture a trusted user identity by putting a user name into tool arguments.

# Illustrative tool boundary; these service functions are application code.
def read_document(document_id, authenticated_user):
    validate_document_id(document_id)
    authorize_read(authenticated_user, document_id)
    document = repository.read(document_id)
    validate_document_result(document)
    return document

The model may propose an operation, but deterministic code validates arguments and the destination checks access for the authenticated caller. The model's statement that permission exists is not evidence. Retrieved documents and tool results can contain misleading instructions; treat them as data. Validate answer fields and require each cited source to belong to the permitted, actually retrieved set.

For write tools, keep proposal/review/commit separate when policy requires it. Bind approval to the exact action and arguments. A retry after a timeout can repeat an already completed effect. Give each business operation a stable ID and have the receiver return its existing receipt instead of writing again. This safe-repeat behavior is often called idempotency. A new random ID on each retry defeats it.

Done when: Every tool has a clear contract, external permission checks, bounded results, and meaningful refusal behavior; each skill uses only reviewed tools.

Step 4 / Connect MCP only where it helps

Do: Use Model Context Protocol (MCP) when a separate service already exposes the tools or data your application needs. Your application is the host, its client connector communicates with the server, and the server is the code/service that exposes capabilities. A server may provide resources (readable context), prompts (reusable message templates), and tools (callable operations). Choose only what the task needs. A direct function is sufficient for a local reader; adding MCP does not itself improve answer quality or authorize access.

Choose the server, transport, version, and allowed tools deliberately. Local standard-input/output transport launches a process; its dependencies and permissions need review. Streamable HTTP connects to a remote endpoint; it needs explicit network trust and, for protected services, authentication. Use compatible client/server versions. Do not assume every protocol version has the same initialization or session behavior.

The following illustrative MCP 2025-11-25 call comes after that version’s initialization. The selected server must implement and permit search_documents; this is not a built-in reader.

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "search_documents",
    "arguments": {"query": "expense receipt rules", "collection": "staff-handbook"}
  }
}

The example illustrates the pinned 2025-11-25 tool contract; consult the current specification for a new implementation. Review tool descriptions and input/output shapes rather than exposing everything advertised by a server. Tool annotations and returned text are not trustworthy permission decisions. The client must handle errors, bounded response size, deadlines, malformed output, and unexpected tools.

CheckWhat to verify
Identity and scopeThe credential is intended for this server; the receiver authorizes the actual user/resource.
Arguments and outputsReject extra fields, oversized values, unapproved collections, invalid source IDs, and unexpected result shapes.
TransportReview local process permissions or remote TLS/trust; never send an inbound bearer token to arbitrary upstreams.
Failure and retryDeadline and disconnect behavior are defined; retries do not create duplicate consequential effects.

If the selected version uses session IDs, they are not authorization credentials. Keep local stdio protocol messages separate from diagnostic logging. Follow the applicable authorization guidance and security guidance for the version you use. The accompanying offline starter does not run an MCP server or prove live authentication.

Done when: The approved connection works, forbidden calls/resources fail for the right reason, and untrusted server content cannot expand authority.

Step 5 / Test the code and run it locally

Do: Run a complete small request, then test the code around it. A unit test checks one component. An integration test checks components together. A smoke test is a quick check that the application starts and returns a valid result. An end-to-end test starts at the request entry point and checks the final outcome. These names describe scope; they do not guarantee useful coverage.

From the repository root, run the accompanying trusted starter:

python3 examples/developer-starter/run.py \
  --question "What receipt is needed for expense reimbursement?" \
  --document expense-policy

PYTHONPATH=examples/developer-starter/src python3 -m unittest discover \
  -s examples/developer-starter/tests -v

The Python unittest runner discovers and imports test modules; run it only on code you trust. The starter is offline. A passing fixture test does not establish a live model's quality, remote authentication, or protection against hostile code.

TestExample assertion
Valid requestAn approved document is read; output has the accepted fields and cites supplied evidence.
Invalid/boundary inputEmpty question, extra fields, duplicate IDs, oversized question, and too many documents are rejected.
Access and unsafe contentUnapproved document ID and path escape fail; instructions inside a document cannot authorize another read.
Missing evidence/failureNo supporting evidence produces a review outcome; missing files and malformed service output fail clearly.
When external services are addedTimeouts, disconnects, expired credentials, forbidden resources, and response-size limits work on the real connection.
When actions are addedStop prevents new effects; required approval matches the action; repeated attempts return one receipt, not two effects.

Assert the reason for rejection and the resulting state. “An exception occurred” could mean an unrelated bug; also verify that no forbidden read, write, or message happened. Keep tests fast with controlled substitutes, then separately exercise approved real services. For writes, simulate the receiver completing an action before the response is lost: this catches retries that duplicate effects.

Retry only failures classified as temporary, with one explicit attempt/time/budget policy. A permission denial or malformed request should not trigger repeated attempts. Check whether a client library already retries: application retries around those retries can multiply calls. Never blindly repeat a consequential operation after an uncertain result.

Done when: Local startup succeeds, positive and forbidden paths have meaningful assertions, and failures leave the expected state.

Step 6 / Evaluate the agent's results

Do: Evaluate whether the agent does the intended job, beyond whether its code runs. A case defines a task and expected outcome. A trial is one attempt at that case. A grader scores the outcome. Save enough safe information to understand failures, including tool decisions and final results. The agent evaluation guidance distinguishes these parts and emphasizes outcomes rather than the agent's claim that it succeeded.

Give cases stable IDs so changes remain comparable. This is an illustrative case format; the evaluation program must implement its fields:

{"id":"documents.supported-answer","question":"What receipts are required?",
 "document_ids":["expense-policy"],"expected_outcome":"answered",
 "required_sources":["expense-policy"],"forbidden_effects":["write","send"]}
Case groupWhat to measure
Useful workTypical and difficult questions; relevant, understandable answers; evidence supports each material claim.
UncertaintyMissing, conflicting, or out-of-date sources produce clarification/review rather than invented facts.
BoundariesUnauthorized data, misleading instructions, malformed output, exceeded limits, and stop behavior.
Conditional featuresReal MCP authorization, workflow recovery, approvals, and safe-repeat behavior only when the agent uses them.

Separate cases used while improving instructions from a held-out set used for the final comparison. Keep sensitive examples access-controlled or replace them with reviewed synthetic data. Record document revisions, instructions/skills, tool definitions, model/provider version, generation settings, grader version, and environment. Repeat real-model trials because the same task can produce different results. Reset state between independent trials so earlier attempts do not supply answers or approvals.

python3 examples/developer-starter/evaluate.py \
  --output build/developer-starter-evaluation.json

This command evaluates the deterministic offline fixture. It is a reproducible code/behavior check, not a model benchmark. To evaluate an actual model, implement an approved adapter and run reviewed tasks through it; save failures, timeouts, costs, and complete-attempt counts as well as successes.

Use code to grade contracts, permissions, citations belonging to supplied documents, and actual effects. Use reviewed answer rubrics and human sampling for relevance and correctness; a citation can exist without supporting the claim. If a model grades answers, compare its ratings with humans and investigate disagreement. Do not average a forbidden action away with good writing scores. Include all assigned trials in the reported denominator, and report repeats separately from ordinary one-attempt success.

Done when: Results are reproducible, useful-work and safety scores are separate, failure cases are understood, and actual-model evidence is distinguished from offline results.

Step 7 / Optimize without weakening the task

Do: Measure a baseline, change one thing, and repeat the same evaluation. Start with fewer unnecessary calls and smaller relevant inputs before adding complicated optimization. Compare quality, delay, and total cost together. A cheaper attempt that repeatedly fails may cost more per useful task.

ChangeCheck before keeping it
Smaller model or fewer callsRequired quality, difficult cases, refusals, and permission behavior still pass.
Retrieve fewer passagesEvidence remains sufficient; conflicting information is not accidentally excluded.
Shorter instructions/outputRemove repetition while preserving task, review, citation, and uncertainty requirements.
Parallel independent readsAccess scope, load limits, deadlines, and partial-failure behavior remain correct.
CachingReal hit rates and costs improve; freshness, user access, and retention rules are preserved.

Count all model attempts, automatic retries, tool charges, and relevant cache charges. For illustration, $1 spent on ten useful tasks is $0.10 per useful task; $0.80 spent on only five useful tasks is $0.16. These are arithmetic examples, not observed prices. Token counts are tokenizer units, not words; billing may include generated tokens absent from the final answer. Compare provider-reported charges using the selected model's accounting.

Choose models by running the same held-out tasks, repeated trials, rubric, and tool setup for each option. Use a smaller development set to narrow choices, then confirm on the held-out set. This table is entirely hypothetical; its costs are not provider prices:

OptionTask successCost/useful taskCompleted p95Decision
Model A94%$0.087 secondsMeets illustrative quality/time floors.
Model B92%$0.056 secondsLower cost; fails a one-point non-regression gate if Model A is the approved baseline.
Model C84%$0.023 secondsReject: below the 90% usefulness floor.

Choose the cheapest option meeting all agreed gates, with enough trials to support the comparison. Report failure/timeout rates beside latency; faster completed requests alone can hide failures. Recheck model choice after changing tools, instructions, or document handling.

Implement one shared run-budget policy. Illustrative settings below are not accepted by the starter's TOML loader:

maximum elapsed time: 30 seconds
maximum model attempts: 4, including retries
maximum tool calls: 6, including retries
maximum input tokens: 6000 per model request, including tool results
maximum output tokens: 800 per model generation
maximum estimated run cost: owner-approved limit
retry policy: 1 initial attempt + at most 2 retries for temporary failures

Count instructions, tool definitions, conversation history, and tool results in the input budget. Reserve space for output and provider-specific reasoning before reaching the model's context limit. Choose limits from measured typical and difficult cases, then evaluate failures caused by those limits. The retry ceiling is additionally bounded by remaining run attempts/time/spend; it does not grant three attempts for every call indefinitely. Reserve budget before parallel calls and reconcile actual usage afterward. An estimate is not a guaranteed billing cap; use service/account limits where available and handle delayed usage reports.

For large tool outputs, filter irrelevant fields or summarize passages while retaining document IDs, locations, and links to the original evidence. Preserve exceptions and conflicting evidence. Follow pagination until the relevant result is complete, or mark the result incomplete; never silently treat a truncated response as a complete answer. Evaluate compressed versus original results on cases where small qualifications change the answer.

Prompt-prefix caching reuses work for an identical repeated input prefix; it does not cache the final answer or eliminate output generation. Keep stable instructions/tool descriptions unchanged before task-specific data where supported. Enabling behavior, minimum size, lifetime, charges, and privacy terms vary by provider/model: check the applicable prompt caching or context caching documentation, then measure hits and misses.

An answer cache needs a different design: include relevant user/tenant access scope and document/configuration versions, recheck permissions before returning cached data, and expire stale entries. Do not share private results through a broad question-only cache. A per-call output limit does not cap a multi-call run. Track shared attempts, elapsed time, and spend across retries, and stop before starting additional work when limits are exhausted. Keep required human review and safety checks unchanged.

Done when: A measured improvement survives the same evaluation, its cache/budget behavior is understood, and it preserves required controls.

Step 8 / Release with absolute and relative gates

Do: Decide the acceptance rules before seeing results. An absolute gate is a minimum requirement every release must meet. A relative gate limits deterioration compared with the approved baseline. Use both: a release can pass the minimum while making an existing experience worse.

GateIllustrative decision
Required safetyEvery listed access/approval/stop case passes; no forbidden effect or secret exposure is observed. Any failure blocks release.
Absolute usefulnessAt least 90% of all assigned evaluation tasks meet the agreed answer rubric.
Absolute service limitsCompleted-request p95 within eight seconds; total cost per useful task within the agreed budget; failures reported separately.
Relative comparisonNo decrease larger than one percentage point in task success, using comparable tasks/settings and sufficient trials.

For example, moving from 92% to 90% meets the 90% floor but loses two percentage points, failing that illustrative relative gate. It is a 2.17% relative decrease, which is a different calculation. Agree on margins and sample sizes; small differences can be inconclusive. Use same-task comparisons where possible and report uncertainty, following statistical model-evaluation guidance. Zero observed critical failures does not prove zero real failure probability.

Build one exact release version with its source, dependencies, model settings, prompts/instructions, skill files, tool definitions, document revisions, test/evaluation datasets, graders, and reports. Record which changes and versions were tested. An automated check passing locally is different from the release pipeline actually executing, and both differ from testing the deployed environment. Require an owner to review unresolved failures, access changes, and any approved exception.

Give each behavior-changing code, prompt, skill, tool, model, configuration, or document update a new release identifier. For example, record release-1.4, source revision, prompt/skill revisions, model setting digest, and evaluation dataset/report IDs together. Keep the meaning of a version stable; do not quietly replace files beneath an already approved release name.

Automate checks in continuous integration (CI), then deployment in continuous delivery (CD). The following is pipeline pseudocode, not executable library functions; connect each stage to your chosen build/hosting tools:

checkout_reviewed_source_revision()
install_dependencies_from_committed_lockfile()
run_unit_integration_and_end_to_end_tests()
run_actual_model_evaluations_on_versioned_cases()
require_all_absolute_and_relative_gates()
artifact = build_exact_release_with_its_evidence()
publish(artifact)
deploy_to_limited_authorized_audience(artifact)
verify_live_access_limits_monitoring_and_stop()
expand_if_healthy_otherwise_restore_previous_release()

The offline starter tests/evaluation can occupy fast CI checks, but cannot replace the actual-model stage. Publish and deploy the same reviewed artifact rather than rebuilding an unreviewed variation after the gates. Control release credentials and approvals outside model output; record which pipeline stages actually ran.

Start with a limited rollout appropriate to the job: dry-run proposed effects, read-only operation, or a small authorized audience. Verify real credentials, permissions, monitoring, timeouts, and stop behavior before expanding. Compare actual results with evaluation expectations. Keep the previous version and its compatible configuration available; decide in advance what triggers rollback. Rollback does not undo completed effects. Preserve receipts and reconcile pending operations so restarting or changing versions does not duplicate them.

Done when: Both gates pass, evidence names the exact release, the deployed boundaries have been tested, and the owner can pause or roll back safely.

Step 9 / Observe, diagnose, and maintain

Do: Make each run explainable enough to diagnose without collecting unnecessary private content. Logs record events; metrics show rates/distributions; a trace connects stages of one request. Tracing requires instrumentation and passing context between components; merely configuring an export endpoint does not create useful spans.

{"event":"answer.completed","release_id":"release-2026-10-09",
 "run_id":"generated-run-id","outcome":"answered","source_count":1,
 "elapsed_ms":820,"model_calls":1,"retry_count":0}

This is an illustrative safe event shape, not proof that monitoring exists. A production implementation must emit, export, retain, and control access to it. Use opaque generated run/operation IDs to join events; they are not authentication credentials. Avoid raw prompts, document passages, answers, bearer tokens, and personal data by default. If content is needed for a reviewed investigation, restrict collection, access, and retention. Follow sensitive telemetry guidance; a hash of a predictable identifier is not reliable anonymization.

ObserveQuestion it answers
Success/review/failure countsHow many assigned requests produced useful results? Keep failures and timeouts in the denominator.
Latency and attemptsWhere is time spent? Report completed-request latency and timeout rate separately.
Cost and cache outcomesWhat is total spend per useful task, including retries and cache costs?
Tool decisions and effectsWhich authorized operation happened, was denied, or has an uncertain receipt?
Quality feedbackAre sources stale, answers unsupported, or users repeatedly correcting the same behavior?

Keep metric labels bounded: outcome, tool name, and approved release category can be useful. Do not put every run ID, question, document path, or user into metric labels; this creates unbounded series and may expose data. Keep per-run detail in access-controlled events/traces. Document metric numerators, denominators, windows, and exclusions so dashboards do not silently drop unsuccessful requests.

Assign daily review of failed calls, answer feedback, cost changes, and pending human reviews. Define owner-approved latency, error, cost, and backlog alerts. Suspected secret exposure or an unauthorized consequential effect requires immediate pause and escalation. Diagnose with release/configuration versions, caller permission scope, tool outcome, timing, and safe error details; do not copy secrets into tickets.

The stop procedure should prevent new work, revoke relevant access, and handle running operations according to their safety requirements. Confirm at the receiving service that further effects are blocked; a stop flag only works if the code checks it. For uncertain writes, inspect receipts and reconcile before retrying. Keep an incident record of known effects and recovery decisions. Turn fixes and new document/tool/model changes into regression cases, rerun evaluation and release gates, and update the runbook before expanding use again.

Done when: An owner sees meaningful failures, can trace a request safely, can stop new effects, and repeats the evaluation/release process for each behavior-changing update.
