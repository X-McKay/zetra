Agent Strategy

Make governed agent development the easiest way to deliver useful automation. Zetra—ZEro-TRust Agents—provides one package contract, one evidence-driven lifecycle, and a platform that applies controls consistently without hiding the decisions people remain accountable for.

1.1 Purpose, outcomes, and boundaries

An agent is a software system that uses model outputs to select or sequence actions. Its risk comes from the authority those actions carry, the data they touch, their reversibility, and the uncertainty of their decisions. The strategy therefore starts with business outcomes and bounded authority, rather than a preferred model or a large collection of disconnected guardrails. A successful agent solves a defined problem within an agreed operating envelope, produces evidence of its behavior, and can be stopped without waiting for it to cooperate.

The platform should support a progression from assistance to bounded execution. A research assistant might retrieve approved documents and prepare a cited answer. A change-preparation agent might draft an update but require a person to approve its exact content. A service agent might execute a narrow, reversible action under a transaction limit. The same package and release vocabulary should describe all three, while their risk tiers and enforcement differ. “Agent” must never become an exemption from software engineering, identity management, change control, or incident response.

Zetra’s operating objective is a paved road: a starter package, typed capability interfaces, local validation, repeatable evaluations, reviewable policy proposals, immutable release evidence, and deployment adapters. Developers should spend their effort on domain behavior and evaluation cases. Platform teams should own identity, policy distribution, runtime controls, telemetry delivery, and durable execution integration. Business owners should own intended outcomes, authorized use, acceptable consequences, and recovery decisions.

Delivery status. This playbook defines a proposed target operating model. The repository’s v0.1 toolkit is an initial local validation and reference scaffold. A passing local command does not demonstrate production sandbox enforcement, admission control, a live gateway, a durable workflow, signed attestations, or a functioning kill switch. Use the toolkit capability matrix and deployment readiness checklist before describing any environment as governed.

Zero trust here means that an agent’s presence on an internal network, a successful evaluation, or a previously approved conversation does not confer continuing authority. Every request needs an authenticated identity, a current authorization decision, and an appropriate resource boundary. It is an engineering direction, not a certification or a claim that failure is impossible.

1.3 One supported stack with deliberate extension points

Standardize the integration contract before attempting to standardize every library. The chosen baseline is framework-neutral Python interfaces, consistent with the supplied architecture sketch and design drafts. Each approved Python framework adapter should expose typed construction, a bounded invocation interface, tool metadata, trace propagation, cancellation behavior, and test substitution. A framework can be accepted only after its adapter passes those contract tests. Developers should not need to understand several framework-specific deployment models to deliver a simple agent.

The target platform combines a model and tool gateway, a sandbox boundary, cloud-neutral Kubernetes deployment, central telemetry, and Temporal for durable orchestration when required. AgentGateway, OpenShell, and eBPF tooling are proposed integration components from the supplied documents. Each needs a pinned version, a validated deployment topology, and an explicit compatibility test. Product names do not establish that a specific policy syntax, credential exchange, or interception mechanism exists. The deployment playbook separates validated upstream capabilities from Zetra requirements and adapter work.

The platform should publish a support matrix covering Python and adapter versions, container base images, Kubernetes distribution and version, kernel features, sandbox compatibility, gateway transports, model endpoints, and telemetry schemas. A release’s runtime fingerprint must identify the exact combination tested. An unsupported kernel, remote MCP transport, gateway plug-in, or model alias should create a visible compatibility failure, not a silent fallback to weaker controls.

Extensions belong behind named contracts. A new framework should provide an adapter rather than an alternate release process. A new tool should implement a declared capability interface rather than receive a generic credential. A new evaluator should publish its inputs, scoring semantics, failure modes, and reproducibility limits. A new business function should define ownership, data scopes, approved destinations, and decision rights without forking the platform. Exceptions are time-limited decisions with compensating controls and a migration plan.

1.4 Select use cases with an accountable value hypothesis

Before building an agent, document the work being improved, the current baseline, the people affected, and the decisions the agent may make. Compare an agent with a deterministic workflow, a search interface, or a simpler assistant. Choose the agent when uncertainty in inputs or action sequencing provides material value that outweighs evaluation and control costs. Multi-step autonomy adds an obligation to explain termination, escalation, resource consumption, and failure recovery.

A charter should name the business owner, technical owner, on-call team, target users, authorized inputs and outputs, maximum consequence, prohibited actions, and success criteria. State the environment where evidence will be collected and the conditions under which the trial will end. For example, an internal knowledge assistant might aim to reduce supported question resolution time while maintaining citation correctness and tenant isolation. A purchase assistant might initially prepare orders only, with no spend authority. Expansion to execution would be a new capability and risk decision.

Use cases should progress through discovery, bounded pilot, controlled production, and expansion. Each promotion changes an operating envelope and requires updated evidence. A useful prototype with broad developer credentials is not a production candidate until those credentials and capabilities are replaced. A failed pilot may still produce reusable datasets, a tool adapter, or a control test; capture those assets and stop the use case when its value hypothesis fails.

1.5 Measure value, reliability, safety, and adoption separately

A single “agent score” obscures the distinction between useful output and safe authority. Define each metric’s numerator, denominator, population, measurement window, owner, and exclusions. Segment by release, task type, tenant or business function, and risk tier. Set targets after a baseline and risk review; the numbers below define measurement contracts, not universal thresholds.

Track operational service levels independently: request latency, workflow age, tool error rate, queue delay, telemetry delivery lag, policy freshness, and budget exhaustion. Define service-level objectives by use case and risk tier. For example, an interactive assistant and a multi-day workflow need different latency measures. A quality regression can trigger rollback even while infrastructure remains healthy. A stale authorization plane can require blocking new actions even while the model is answering correctly.

Publish scorecards that show denominator size and uncertainty. A safety suite with zero observed failures provides evidence about that suite, not proof of universal safety. Compare paired cases when assessing releases, show important subgroup regressions, and keep critical controls as deterministic pass/fail gates. Treat user acceptance, reviewer agreement, and sampled output quality as complementary evidence with stated bias and confidence limitations.

1.6 Ownership and decision rights

The platform is a product with a roadmap, support boundaries, service levels, and incident ownership. It must not become an invisible dependency maintained informally by each agent team. Central security defines mandatory controls and validates enforcement. Business functions decide what work should be automated and what consequences are acceptable within organizational policy. Developers implement bounded behavior and submit evidence. Operations owns the reliability of the enforcement and execution planes.

Assign real people or staffed groups to these roles in the catalog. Role names alone do not provide operational coverage. Separate the ability to propose a policy expansion from the ability to approve it; separate emergency disable from restart authorization. Where small teams combine roles, document the conflict and add independent review for consequential changes. The RACI is a starting contract to ratify, not a replacement for the organization’s decision process.

Use exit evidence rather than a calendar promise to authorize each stage. Track delivery dates separately, with named dependencies and owners. Do not onboard high-consequence use cases to force a platform deadline. The first production cohort should establish whether the standard improves developer lead time and operational clarity, not merely whether deployment automation can run.

Adoption requires good defaults and helpful feedback. Provide a local “explain” report that links a failed gate to the capability, risk scenario, policy rule, and example remedy. Offer a preview of deployment bindings before submission. Publish how-to guides for common tasks, a migration checklist for existing agents, and an exception path for genuine unsupported needs. Platform support should analyze recurring friction and improve the contract rather than requiring teams to accumulate private workarounds.

1.8 Tradeoffs and strategic constraints

Automatic profiling can reduce policy authoring effort, but observation is incomplete and can include malicious or accidental behavior. Treat generated rules as proposals bounded by declared purpose and central invariants. Static analysis can reveal likely side effects, yet imported libraries, dynamic dispatch, remote tools, and runtime configuration leave uncertainty. The platform must expose that uncertainty and request evidence rather than awarding an unjustified low-risk score.

Automatic injection reduces repetitive setup but can make failure opaque. Prefer explicit, versioned deployment plans and a diagnostic command showing the resolved identity, routes, sandbox profile, model configuration, and telemetry path. Framework adapters should use supported integration interfaces where possible; arbitrary monkey-patching is a compatibility liability. Durable execution helps recover coordination state but does not remove the need for idempotency, business reconciliation, or compensation.

Centralization creates concentration risk. Gateway and policy outages need tested fail-closed behavior at consequential boundaries, appropriate caching and freshness limits, and a clear explanation to users. Telemetry can itself become a sensitive data store. Default to metadata, controlled redaction, and selective content retention. Cost and latency overhead should be measured and attributed so that safe defaults remain sustainable.

The strategy does not claim regulatory compliance. Determine legal or regulatory obligations through the organization’s qualified owners, map applicable obligations to evidence and controls, and preserve those mappings separately from technical capability claims. Organizational risk tolerance, approval thresholds, data classes, and retention rules remain ratification decisions.

1.9 Design inputs and ratification record

The supplied AgentDraft.pdf motivates portable business logic and automated infrastructure binding. temporal_wrapper_for_ai_agents.md motivates a common durable-execution contract. automated_eval_for_ai_agent.md motivates stable risk IDs and inferred evaluation requirements. The eBPF, OpenShell, and AgentGateway drafts motivate layered profiling and policy generation. PXL_20261007_230415496~2.jpg supplies the typed-factory and repository-layout sketch. These are design inputs rather than verified product specifications or instructions to execute their examples.

Maintain a decision register with the approved framework adapter, identity system, gateway topology, sandbox deployment mode, orchestration selection criteria, policy distribution service levels, data handling, risk thresholds, and release authorities. Every decision should identify its evidence, accountable owner, effective date, review trigger, and replacement plan. Version the register with the playbook so teams can distinguish an approved standard from a proposed next capability.
