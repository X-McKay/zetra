07 / Technical leadership · Platform engineering · Security architecture

Integration deep dive: from package to governed runtime

Zetra makes the agent package the unit of development and the independently verified release the unit of deployment. The integration work connects those two units: infer review obligations, execute evaluations, observe a scoped workload, compile a permission candidate, obtain approval, install native controls, verify effective state, and release execution authority. Developers describe what an agent needs in a small portable contract. Platform engineers own how those needs become identities, routes, sandbox boundaries, durable execution, and evidence. Technical leaders can assess the architecture by inspecting the contracts between those stages and the failure behavior at each boundary.

Reading the evidence. The repository contains working local commands, tested native boundary fixtures, an actual ARM64 OCI worker, and a Kubernetes Temporal workflow. It does not yet contain a production release compiler, signed admission service, production credential exchange, distributed revocation ledger, or one qualified composition of every boundary. Proposed contracts below are Zetra design requirements, not vendor APIs or implemented CLI features. The integration index and aggregate report identify the actual scope.

7.1 What the original designs contribute, and what changes

The five supplied Markdown documents establish a coherent ambition: make security and durability part of the normal development path, using evaluations to generate evidence and automation to reduce infrastructure work. This chapter preserves that ambition while replacing broad promises with explicit owners, native configurations, evidence subjects, and acceptance tests. AgentDraft.pdf and the supplied architecture photograph also support the portable package, typed construction, colocated tools, and shared workflow/runtime structure described in the developer chapter. They are design inputs; they do not authorize observed behavior or establish deployed controls.

7.2 The control plane, data plane, and ownership boundary

The proposed control plane is a release service with restricted write authority over the catalog, environment bindings, and native policy resources. It receives immutable CI artifacts and independent approvals. It compiles only capabilities permitted by the organization boundary and the approved agent request. It then asks each adapter to establish and report effective state. The runtime data plane consists of the worker, supervised computation, gateway, receiver, and selected kernel/network controls. It accepts execution authority for one release and environment; it does not decide its own permission expansion.

A developer should not configure kernel probes, production issuers, Kubernetes routes, and credential stores for every agent. The maintained platform profile owns that repetition. The developer does own accurate capabilities, typed inputs and outputs, instructions, risk scenarios, and business consequences. An environment binding resolves a logical capability such as mcp.read_status to a reviewed tool schema, permitted resource scope, workload identity, approved endpoint, credential owner, and enforcement adapter. Missing bindings block activation. A catch-all network rule is not an acceptable resolution mechanism.

The practical deliverable is a single reviewed platform profile per supported compatibility tuple, not a universal wrapper that silently patches any framework. An initial profile can support framework-neutral Python, read-only tools, one Temporal adapter, specific Linux kernels, and a chosen gateway topology. Expanding that profile is platform engineering with its own qualification tests. Developers then consume the expansion through the same manifest and CLI rather than copying infrastructure fragments between repositories.

7.3 Analysis and evaluations become bound evidence

The existing fast path deliberately separates static inspection from execution. zetra check parses source and manifest without importing the agent. zetra eval executes developer-owned unittest selectors in separate processes. Those selectors must cover required stable scenario IDs and actually run tests; skipped or expected-failure results do not count as passes. This is useful scaffolding for a material-scenario gate, but trusted project tests can still contain weak assertions. Independent review and protected platform-negative scenarios remain necessary.

# Current local CLI; run only trusted project code outside a qualified sandbox.
zetra check examples/knowledge
zetra eval examples/knowledge --output /tmp/knowledge-evidence.json
zetra check examples/knowledge --evidence /tmp/knowledge-evidence.json
zetra catalog examples/knowledge \
  --evidence /tmp/knowledge-evidence.json \
  --output /tmp/knowledge-catalog-candidate.json

The implementation fingerprints package contents, including instructions and dependency declarations, while excluding documented generated/cache locations. It records the manifest hash, toolkit/evaluator identity, selected scenario results, and timestamp. Evidence-dependent commands check those bindings, require mandatory scenarios to pass, and reject future-dated or older-than-24-hour local evidence. This 24-hour rule is an implemented developer check, not the production freshness policy. The production service needs an authenticated evidence producer and a trusted clock; copying hashes into editable JSON cannot supply either. See the exact evidence implementation.

The proposed production analysis record also captures unresolved calls and remote tool behavior. An HTTP GET can mutate state, and a POST can perform a read; verbs provide hints rather than business consequence classifications. Indirect imports, native extensions, reflection, generated code, and remote MCP servers require declared contracts and runtime tests. If analysis cannot classify a material path, the result becomes an unknown requiring review. It must not default to low risk or count an absent finding as a successful safety scenario.

Model evaluation adds a separate evidence layer. Pin the model/provider configuration, dataset revision, evaluator revision, seeds where supported, repeated-run count, and cost/latency accounting method. Record distributions and critical failures rather than an average alone. Keep deterministic authorization, schema, approval, and idempotency assertions outside the model judge. The current examples use controlled fixtures and do not measure model quality; that limitation is part of the release subject, not an incidental footnote. The original evaluation-inference proposal becomes actionable when every inferred review obligation has a stable scenario ID and an independent pass condition.

7.4 Scoped profiling produces a delta, never authority

The target profiling job starts from the evaluated image and known scenarios in a dedicated Linux environment. The capture plan declares hooks, process ancestry, pod/container identity, gateway spans, sandbox denials, and event-loss counters. It separates agent processes from the evaluator, node agents, sidecars, and unrelated workloads. The job stores raw events in restricted evidence storage, then a pinned parser normalizes them. Selecting the test-runner PID alone is insufficient when tools create subprocesses or networking occurs in a proxy.

The implemented zetra profile consumes normalized recorded JSON lines; it does not directly parse arbitrary Tetragon or OpenShell output. It requires exact agent, immutable image, and container: agent scope. Explicit denied observations are retained separately and excluded from process, file, and network permission candidates. A missing outcome remains an observation. All output remains review-candidate with authorizes: false. This behavior is inspectable in the normalizer.

# Normalized contract accepted by v0.1, not a raw vendor event.
{"agent":"tetragon-fixture","image":"docker.io/library/alpine@sha256:4b7ce07002c69e8f3d704a9c5d6fd3053be500b7f1c69fc0d80990c2ad8dd412","container":"agent","kind":"file","path":"/tmp/zetra-sensitive","mode":"read","outcome":"denied"}

zetra profile integrations/evidence/tetragon-normalized-events.jsonl \
  --agent tetragon-fixture \
  --image docker.io/library/alpine@sha256:4b7ce07002c69e8f3d704a9c5d6fd3053be500b7f1c69fc0d80990c2ad8dd412 \
  --output /tmp/profile-candidate.json

A useful proposal compares four sets: declared and exercised; declared but unexercised; exercised but undeclared; and denied or unclassified. The first supports compatibility evidence. The second identifies missing coverage or unused authority. The third can reveal a legitimate dependency, an accidental library behavior, or compromise. The fourth supports denial tests and triage. An evaluator's adversarial request belongs in the fourth set even if the process attempted it repeatedly. Denial volume is not a justification for adding access.

Proposed parser contracts preserve the source event ID, native outcome, namespace, pod UID, container runtime ID, process ancestry, collection interval, image identity, scenario association, and any uncertainty. Address observations must not automatically authorize a domain whose IP changes. A path observation must not widen into an entire parent directory without review. Capture gaps invalidate conclusions that depend on completeness. This approach turns the attachments' synthesis step into a reviewable delta with evidence links instead of an opaque allowlist extracted from “everything the tests happened to do.”

7.5 A versioned compiler contract makes the platform reusable

The following is a proposed Zetra adapter contract. It is not implemented by the v0.1 renderer and is not a Kubernetes CRD. The release compiler consumes the approved permission request, organization boundary, environment bindings, evidence subjects, and a platform profile. It emits both native configuration and a plan explaining which requirement each native artifact enforces. The plan is reviewable before CD writes it, and effective-state reports can be compared against the same plan afterward.

# Proposed local adapter-plan document; no vendor resource implied.
schema: zetra.dev/adapter-plan-v1alpha1
release_subject:
  image_digest: <immutable OCI subject>
  source_digest: <evaluated package digest>
  manifest_digest: <canonical manifest digest>
inputs:
  organization_boundary_digest: <approved boundary>
  capability_approval_digest: <independent approval>
  environment_binding_digest: <target-specific routes and identities>
  evaluation_bundle_digest: <trusted CI evidence>
profile:
  name: python-readonly-kubernetes
  compiler_version: <pinned compiler>
  adapter_versions: <explicit tested implementations>
requirements:
  - id: NET-DIRECT-BYPASS
    mandatory: true
    enforcing_adapters: [cilium, openshell]
  - id: TOOL-IDENTITY-SCOPE
    mandatory: true
    enforcing_adapters: [agentgateway, receiver]
outputs:
  native_artifact_digests: <one digest per actual config>
  qualification_scenario_ids: <allowed and forbidden cases>
activation: withheld

Each adapter should expose four operations in its platform implementation: discover reports actual prerequisites; compile produces deterministic native artifacts and unsupported requirements; verify_effective reads the installed authority and compares it to approved intent; qualify executes allowed, forbidden, startup, outage, and revocation probes. These are proposed adapter interfaces, not commands currently available in the CLI. Discovery success cannot satisfy qualification, and a compiler must reject a mandatory control it cannot represent.

Permission intersection is a Zetra semantic operation performed before native translation. It cannot be assumed from stacking vendor policies. The OpenShell effective policy, attached provider contributions, gateway attachment scope, and Kubernetes policy union must each be analyzed according to their real semantics. A compiler is incorrect if its generated YAML looks narrow but additional effective rules permit more. It should report both desired and observed effective permissions, with explicit unknowns, and fail on unexplained widening.

This interface is also the mechanism for a simple developer experience. The package receives one error with the violated requirement, missing evidence, and suggested next action. A developer should see “NET-DIRECT-BYPASS lacks a qualified IPv6 deny probe for this runtime profile,” not a generic Helm failure buried in CI output. Native artifact diffs, source links, and environment details remain available to platform reviewers. The simple front door is supported by detailed adapter contracts and diagnostics, rather than hiding unresolved security requirements.

7.6 Tetragon and Cilium: separate kernel and network duties

The tested Tetragon 1.7.1 fixture selects a namespaced synthetic workload by zetra.dev/agent. It hooks security_file_permission, captures its typed file and integer arguments, and selects a sensitive-file read before requesting Sigkill. The recorded result was exit 137, no returned file bytes, and a correlated kernel event for the selected pod/image. An unrelated file read succeeded, and the unselected pod remained unaffected. This is a qualified response for one hook/path/kernel tuple; it is not a generated universal Python sandbox. See the complete policy and eight-check kernel/network report.

# Actual tested native Tetragon fixture: selected sensitive-file read response.
apiVersion: cilium.io/v1alpha1
kind: TracingPolicyNamespaced
metadata:
  name: zetra-fixture-file-guard
  namespace: zetra-validation
spec:
  podSelector:
    matchLabels: {zetra.dev/agent: tetragon-fixture}
  kprobes:
    - call: security_file_permission
      syscall: false
      return: true
      args:
        - {index: 0, type: file}
        - {index: 1, type: int}
      returnArg: {index: 0, type: int}
      selectors:
        - matchArgs:
            - {index: 0, operator: Equal, values: [/tmp/zetra-sensitive]}
            - {index: 1, operator: Equal, values: ["4"]}
          matchActions:
            - {action: Sigkill}

Hook arguments are defined by the chosen function and capture schema. An argument index is not automatically the Python command-line position. A tcp_connect observation hook is a kernel-function probe, not a syscall merely because a connection eventually originates from one. The original design's three probes therefore cannot establish capture of all system behavior. Interpret native events through a qualified parser and selected policy. Upstream TracingPolicy documentation and hook semantics are the compatibility references.

Cilium 1.20.2 enforces the separate Kubernetes NetworkPolicy fixture. Its selected pod can reach only a reviewed peer on TCP 8080. Baseline reachability is tested first so a failed forbidden request cannot pass simply because every destination is unavailable. The allowed peer succeeds after policy installation; the forbidden direct peer fails. Policies are additive: an empty-egress policy does not cancel access granted by another selecting policy. The release service must inspect all effective selecting policies, including environment-wide ones. See the native network fixture and Kubernetes' NetworkPolicy semantics.

Kernel enforcement and network isolation complement the gateway rather than authenticating business intent. Tetragon does not decide whether a tool may modify a specific tenant record. NetworkPolicy does not inspect MCP arguments. The platform profile assigns those responsibilities to the gateway and receiver while retaining kernel/network controls to contain bypass. Production acceptance separately needs startup-gap closure, node-agent/CNI outage behavior, event loss, descendants, IPv6/DNS behavior, and compatibility across every eligible node. The local tests ran after the synthetic pods existed; they deliberately do not prove first-instruction containment. Upstream runtime-hook integration describes the installation work behind startup filtering.

7.7 OpenShell: an effective supervised package boundary

The OpenShell 0.1.2 test executes the actual knowledge-agent factory and Zetra runtime inside a supervised Python image. It uses the native policy below, not the attachment's conceptual sandbox.filesystem shape. The strict compatibility setting requires the selected Landlock boundary rather than accepting best-effort protection. The supervisor acknowledged the effective policy hash and reported enforcement. That acknowledgement is now a required predicate in the reproduction report, alongside the seven successful probes. Read the OpenShell runbook and effective-boundary report.

# Actual strict local OpenShell 0.1.2 policy; no external route/provider attached.
version: 1
filesystem_policy:
  include_workdir: true
  read_only: [/bin, /usr, /lib, /proc, /dev/urandom, /etc, /var/log]
  read_write: [/sandbox, /tmp, /dev/null]
landlock:
  compatibility: hard_requirement

The probes distinguish sandbox enforcement from ordinary UNIX permissions. The process can write/read approved scratch space, but cannot read a world-readable file outside permitted roots or write into a world-writable excluded directory. An /etc write also fails, although ordinary permissions contribute to that outcome. Unapproved HTTP and direct TCP attempts receive explicit permission errors, independently corroborated by supervisor deny logs. Timeout and DNS failure are not accepted as substitutes for enforcement. The offline agent returns the exact approved answer; no model or provider credential is involved.

The environment is a deliberately limited tuple: Kubernetes compute driver with Agent Sandbox 1.0.6, TLS/mTLS enabled, workload boundary bootstrap injection and a separate supervisor pod, user namespaces disabled, AppArmor profile unconfined, and server.auth.allowUnauthenticatedUsers=true after the mTLS transport. These lab accommodations mean principal authentication, user namespaces, and AppArmor are unqualified. The upstream Kubernetes driver creates separate workload and supervisor pods, connected through the boundary service and network fencing; the supervisor is not an agent-container sidecar in this tested topology. The deployment path requires an explicit upstream maturity decision. Version-qualified chart values, Kubernetes driver source, and the actual bootstrap report record the relevant tuple.

Effective policy is more than the submitted file. The target adapter must include provider attachments, global overrides, middleware support, binary identity, and runtime version in its digest and read-back. It must verify how global policy replacement affects the intended boundary instead of assuming intersection. Filesystem changes can require a fresh sandbox; supported network updates still need propagation and denial tests. The policy prover is useful for supported modeled coverage, but the platform must fail when a mandatory protocol or invariant is unsupported or inconclusive. It does not certify arbitrary request payloads or application correctness. The native schema and prover documentation define the upstream surfaces; the strict offline policy above is the surface actually tested here.

For the pinned containment checker, supported models include filesystem, network L4/REST, process, and Landlock boundaries. MCP, GraphQL, JSON-RPC, network middleware, and credential bindings are unsupported containment domains; runtime protocol enforcement and prover coverage are different capabilities. The checker was not executed by this repository's seven-probe sandbox fixture. A proposed proof stage should accept an understood within_boundary result only when every mandatory modeled domain is covered, retaining JSON status, reason, coverage, checker version, candidate/boundary digests, and timeout outcome. See the pinned containment implementation and checker CLI.

# Upstream checker invocation; separate proposed proof stage, not v0.1 automation.
openshell-prover check candidate.yaml --boundary boundary.yaml --output json

7.8 agentgateway: authenticated identity and semantic tool scope

The tested semantic proxy is standalone agentgateway 1.6.0, running on host loopback. Its configuration validates a synthetic RS256 JWT with a fixed issuer, audience, and public JWKS, then permits only the reviewed subject/tool pair. Authentication establishes the caller identity; the CEL rule establishes this tool permission. Neither the caller's correlation headers nor a Kubernetes label replace that identity check. The actual gateway configuration, 11-check result, and reproduction guide are the concrete baseline.

# Actual standalone v1.6.0 fixture; synthetic identity and loopback MCP target.
mcp:
  port: 18300
  dnsRebindingProtection: true
  policies:
    jwtAuth:
      mode: strict
      issuer: zetra-local-test
      audiences: [zetra-gateway-test]
      jwks:
        file: /Users/al/git/zetra/.tools/gateway-test-state/jwks.json
    mcpAuthorization:
      rules:
        - 'jwt.sub == "knowledge-assistant" && mcp.tool.name == "read_status"'
  targets:
    - name: fixture
      mcp:
        host: http://127.0.0.1:18305/mcp

The test rejects a missing token, wrong issuer, wrong audience, forged signature, and a token expired by one hour. Valid identity initializes an MCP session, sees only read_status in discovery, and receives the expected backend response. A forbidden write and wrong-subject read fail before forwarding; the independent receiver observes zero writes. Discovery filtering is useful ergonomics, but the direct forbidden-call probe is the enforcement test. The upstream JWT authentication and MCP authorization documentation describe these native policy surfaces.

Tool-name authorization is deliberately narrow. The receiver still needs an approved argument schema, tenant/resource authorization, and any action-specific approval. Do not place mcp.tool.arguments into the MCP authorization scope where that variable is unavailable. Choose the appropriate supported policy scope or an independent authorization/receiver adapter for argument-sensitive decisions. The current Python client supports the reviewed read_status operation, validates empty arguments, bounds time/response size, refuses redirects, and uses HTTPS except its explicit numeric-loopback lab mode. It does not become a generic privileged MCP client simply because the remote server exposes more tools. Inspect the restricted adapter.

The original design's conceptual resources are not deployment artifacts. A future Kubernetes controller adapter must pin the controller, chart, installed CRD schemas, policy attachment scope, and equivalent authorization probes. Standalone binary 1.6.0 does not qualify a controller installation merely sharing a version label. Similarly, the gateway is a Rust proxy; an assumed Envoy filter cannot be used as the implementation contract. Publish native configuration only after schema and behavior checks against the chosen product surface.

Measured expiry matters. The real gateway accepted the initial approximately-one-minute-expired token. The initial result is retained. The pinned validator uses library defaults, and this test did not establish a tight revocation bound. Nominal JWT expiry alone therefore cannot implement the proposed emergency authority cutoff. See the exact validator revision.

7.9 Credential hops and the missing composition bridge

The proposed production profile needs a placement decision: run the entire trusted worker under a supervised boundary, or keep coordination in a trusted worker and execute potentially untrusted agent computation through a separate sandbox activity adapter. The second arrangement is a useful target for stronger separation: the worker retains Temporal credentials and dispatch authority; the sandbox receives only the data and capabilities needed for one activity. It requires a new bridge that creates or selects a qualified sandbox, starts the evaluated package, validates the result, and maps cancellation and failures back into the durable activity. That bridge is not implemented in v0.1.

Today AgentActivities.run_agent constructs the factory and calls run inline in the worker's ordinary process. The OpenShell fixture separately uploads and executes copies of the actual reference code in its supervised workload. The gateway fixture separately links a host Temporal worker to the host semantic proxy and cluster collector. An actual OCI worker also executed a controlled knowledge workflow in Kubernetes with a pod-local Temporal development server. These are valuable building blocks, but joining their reports does not prove their combined transport, lifecycle, or credential boundary. See the current worker and the Kubernetes workflow report.

HopProposed credential ownerAcceptance test and current status

Externalizing provider credentials does not mean the agent holds no secrets at all. A workload token is itself a credential and can be visible to the process using it. Its audience, expiry, release scope, and transport must limit the consequences of theft. Provider keys should remain with the chosen upstream owner; they must not enter model context, tool results, workflow history, or audit logs. Bind receiver authorization to authenticated identity rather than trusting an arbitrary actor string supplied by agent code.

OpenShell's gateway manages the sandbox boundary; agentgateway is the semantic MCP/model proxy. These are different hops with different credentials. Avoid assuming two transparent TLS interception layers will compose automatically. The platform profile must specify which component terminates each TLS connection, which roots and client identities each validates, whether inspection is enabled, and what bypasses remain possible. If OpenShell owns a provider binding for one route, agentgateway should not independently inject a conflicting credential on that same upstream hop. A composition probe must demonstrate intended routing and deny direct access to the final receiver.

Supported upstream credential seams do exist: OpenShell has provider placeholders and bound resolution, while agentgateway exposes configured backend authentication and token-exchange options. Their existence is a reason to build and qualify an explicit binding adapter, not to claim credentials automatically stay outside every agent process. Issuer trust, exchange audiences/scopes, tenant mapping, renewal, storage, redaction, and failure behavior remain requirements. The offline sandbox and synthetic MCP receiver exercised no production exchange. See pinned OpenShell credential resolution and agentgateway backend policy schema.

7.10 Temporal: determinism, activity granularity, and retries

Durability begins with a defined workflow/activity boundary. The current workflow records orchestration and calls one zetra.run_agent activity. External I/O and the ordinary Python factory run on the activity side. The workflow uses explicit timeouts and treats contract/security denials as non-retryable. Its orchestration is intentionally small enough to replay. This makes the package portable, but the whole agent run can repeat after an activity failure; internal model/tool steps are not individually durable checkpoints merely because the outer call is an activity.

# Current workflow policy, excerpt from src/zetra/temporal_workflow.py.
result = await workflow.execute_activity(
    "zetra.run_agent",
    request,
    start_to_close_timeout=timedelta(seconds=30),
    schedule_to_close_timeout=timedelta(minutes=2),
    retry_policy=RetryPolicy(
        maximum_attempts=3,
        non_retryable_error_types=["Denied", "ContractError"],
    ),
)

The live host fixture injects failure before the first read, observes attempts 1 and 2, validates the exact result, fetches history, and successfully replays it. A separate OCI worker ran in a hardened Kubernetes pod and its real history replayed with Python SDK 1.34.0. These tests establish actual execution and this history's compatibility, not arbitrary framework durability. Activities may execute more than once; idempotency belongs at the external effect's receiver. Temporal's activity semantics and workflow execution documentation provide the primary model; the fixture histories provide Zetra's measured implementation evidence.

The proposed bridge must distinguish three identities: a stable business operation, a workflow/run, and an activity attempt. Retries keep the operation identity and normalized payload; attempts get separate diagnostic identifiers. A receiver can return a previously committed receipt for an identical operation. It must reject the same operation key with changed payload, resource, actor, release, or approval. A timeout after remote success cannot be interpreted as “nothing happened.” The activity must query or retry the receiver's idempotent operation and reconcile the resulting receipt. The read-only worker intentionally rejects write-capable or unqualified adapters; the local SQLite action example demonstrates a transaction but is not a production remote receiver.

Run-wide budgets require the same separation. Current dependency counters reset when a retry constructs fresh dependencies. A proposed durable budget authority reserves against release/run/operation before a chargeable request, reconciles measured usage, and defines streaming/concurrency overshoot. A gateway's rate limit or a test-derived token estimate is not automatically that authority. The platform must reject a profile that promises a shared dollar ceiling while implementing only per-process counters.

Approvals travel through an authenticated approval service into a workflow, then are independently validated immediately before an effect. A Signal or Update is a transport mechanism, not proof of approver identity. Bind approval to canonical arguments, tenant/resource/action, release/policy epoch, operation ID, expiry, and single-use semantics. The current STOP Signal checks before and after the activity; it does not revoke a request already executing inside that activity. A production bridge needs cancellation/heartbeat handling and independent receiver fencing. Large objects belong in authorized external storage with digest and retention metadata; keep only bounded references in history and never bearer credentials.

7.11 Telemetry joins explain behavior without becoming authority

The gateway exports real spans through OTLP/gRPC to a collector running in the disposable cluster. Its native tracing configuration extracts release, run, and operation headers into diagnostic attributes. The test injects a W3C trace identity, verifies that it survives, joins attributes to the adapter audit event and Temporal run, and observes a denied write. The eight-check telemetry report and actual collector manifest show delivery rather than inferred observability.

# Actual gateway tracing configuration, abbreviated to the join attributes.
frontendPolicies:
  tracing:
    host: 127.0.0.1:14317
    randomSampling: true
    resources:
      service.name: '"zetra-live-gateway"'
      deployment.environment: '"disposable-local-kind"'
    attributes:
      zetra.release.id: '"x-zetra-release-id" in request.headers ? request.headers["x-zetra-release-id"] : ""'
      zetra.run.id: '"x-zetra-run-id" in request.headers ? request.headers["x-zetra-run-id"] : ""'
      zetra.operation.id: '"x-zetra-operation-id" in request.headers ? request.headers["x-zetra-operation-id"] : ""'

The collector fixture has an OTLP receiver, batch processor, and detailed debug exporter. That exporter is for public synthetic qualification, not production prompt capture. Production ingestion should enforce authentication, sensitive-field minimization, restricted business-function access, retention, and alerting on lost exports. Upstream collector configuration and gateway trace configuration define the relevant native surfaces.

The proposed evidence join uses immutable release/image subjects plus runtime identities: namespace, pod UID, container ID, workflow/run, activity attempt, business operation, authenticated principal reference, policy epoch, and receiver receipt. Kernel events join through pod/container identity rather than expecting every syscall to carry a trace header. Workflow replay needs replay-safe instrumentation so it does not manufacture duplicate operational events. A trace attribute can be forged by a caller; enrich it with authenticated workload context or flag it as claimed metadata. A sampled span stream cannot replace the approval ledger, receipt store, or mandatory security audit stream.

A shared trace needs instrumentation and propagation at every execution seam. An exporter endpoint variable alone instruments no code. Temporal SDK 1.34.0 supplies a TracingInterceptor, which must be configured alongside HTTP/framework context propagation, compatible exporters, and the proposed sandbox bridge. The present worker does not configure that complete path. See the pinned interceptor; current evidence verifies gateway export and explicit identifier joins, not a universal cross-runtime span tree.

Central operators should be able to answer which effective policy a workload used and whether a forbidden path was denied. Business operators should see task outcome, pending approvals, cost, escalation, and exceptions within their authorized function. Both views derive from a shared identity join, but access control applies to the views and source telemetry. The captured logs contained no raw synthetic JWT; this is a useful regression assertion, not universal proof that arbitrary prompts and responses cannot leak data.

7.12 Withheld manifests become activation only after effective-state checks

The implemented renderer emits a ServiceAccount, default-deny NetworkPolicy, gateway-egress NetworkPolicy, and Deployment with zero replicas. It requires an immutable image and fresh local evidence. The native candidate has no automatic service-account token, a non-root UID, read-only root filesystem, dropped capabilities, seccomp, bounded resources, and scratch storage. It does not inject production identity, DNS, Temporal, or telemetry connectivity. The server dry-run accepted all four resources and preserved zero replicas. See the renderer and the actual API-server result.

The gateway egress rule selects the namespace and gateway pod together in one peer expression and TCP 8443. That is an intended routing placeholder, not a match to the standalone loopback fixture's port 18300. The environment binding must resolve actual addresses, ports, TLS identities, worker polling routes, and sandbox topology before activation. A worker image's ENTRYPOINT must match the reviewed persistent service contract. The built ARM64 worker passed actual execution and digest-chain checks; that does not turn a generic rendered manifest into the separately qualified Kubernetes workflow fixture.

The target release sequence is staged: verify trusted bundle/approvals; reconcile native boundaries while execution remains withheld; read back their effective versions; run dedicated allowed/forbidden probes; verify runtime-specific startup readiness; issue an environment-bound execution lease; then allow the worker to accept business work. A canary must use the same image, adapters, identities, and effective policies as the intended release. A helper container successfully opening a file does not prove the actual agent's permission set. Catalog publication records desired state, approval, effective state, qualification interval, and current lease separately.

Kubernetes readiness is necessary but insufficient. A pod can be Ready while a policy is not attached, a credential is mis-scoped, or a receiver bypass remains open. The proposed activation verifier therefore checks adapter evidence rather than inferring security from pod phase. An admission controller enforces trusted release predicates and environment constraints; a node/runtime adapter closes the first-instruction gap. Until those controls are implemented and tested as a composition, zero-replica withholding remains the safe output of the developer renderer. No existing zetra render or qualify command grants production activation.

7.13 Startup, outages, and revocation have explicit failure semantics

Every mandatory adapter needs a behavior contract when authority cannot be established. The following are proposed acceptance requirements. The local fixture reports do not establish these distributed outage and cutoff properties. Technical approval should assign an owner and a test to each row, including the time bound and the treatment of in-flight work. “Fail closed” is useful only when it names which new operation is refused, where the refusal happens, and how uncertainty is surfaced.

The proposed revocation record has an authenticated release/environment scope, monotonically increasing policy epoch, reason, issuer, timestamp, and expiry/freshness rules. Every side-effect receiver checks the current epoch or a bounded authorization lease immediately before committing. If its required freshness cannot be met, it refuses new effects. A technical-lead decision must choose that freshness window and test clock skew, cache behavior, issuer outage, and recovery. This chapter does not nominate an unapproved duration as an achieved service level.

The kill path has independent mechanisms: disable new dispatch, revoke identity/tool authorization, fence the receiver, request workflow cancellation, terminate supervised compute when appropriate, and preserve receipts for reconciliation. Stopping a pod cannot undo an already accepted payment or write. A receiver fence can stop a new effect even if a compromised worker ignores a STOP file. Conversely, a receiver unreachable during revocation creates an unknown; the incident record must report it instead of claiming universal completion. The observed gateway token leeway makes this multilayer design especially important.

7.14 A simple path supported by inspectable contracts

The initial repository gives developers a reproducible environment and a small command vocabulary. just bootstrap installs locked dependencies; just check runs the ordinary contributor gate; agent-specific CLI commands create and validate packages. Platform lab recipes are separate and explicitly target the disposable cluster. This separation lets application teams iterate quickly without acquiring cluster-admin authority or interpreting upstream YAML for every feature. The platform team owns the reviewed profile and adapter upgrades.

It isolates Helm state and native CLI downloads under ignored workspace paths. Its actual existing-cluster run skipped release writes. The original readiness report remains available beside the corrected report. The fresh-install path is not yet qualified on a second empty cluster. Readiness is a prerequisite; the subsequent fixtures provide the selected behavioral evidence.

The target front door extends this workflow without making developers approve opaque output: one candidate review shows capability/risk changes, newly required scenarios, policy deltas, unsupported requirements, and exact native artifacts. An independent approval binds those digests. CD verifies the bundle and produces effective-state evidence. The developer sees actionable remediation, while technical reviewers can inspect each boundary. The use-case walkthrough applies these contracts to one end-to-end package and operating flow.

Consensus can therefore be concrete: accept the package contract and development path, select one runtime profile, assign owners to its remaining mandatory controls, and define a bounded pilot with explicit consequences. Confidence comes from replayable histories, independently observed denials, effective-policy read-back, and traceable artifact subjects. Confidence in the full production system requires the missing composition and authority controls to pass their own tests. A polished diagram or the sum of separate passing fixture counts cannot substitute for those contracts.
