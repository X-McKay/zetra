A practical guide for developers

From a useful idea to a reliable agent

An agent uses a model and tools to complete a task. Start with a clear job, check its results, and give it only the access it needs. Follow these nine steps; choose examples and checks that fit your use case.

How to use this path

Build defines the job and its allowed connections. Validate checks software behavior and task results. Operate releases a reviewed version and follows its real outcomes.

Try it: Choose a numbered step to jump to it. Return to tests and evaluations whenever behavior changes.

Keep these three questions in view: Does it do the job well? Does it stay within its permissions? Can someone operate and troubleshoot it?

1. Define the problem and success

Before writing code, agree on what the agent should accomplish and where its responsibilities end.

DefineQuestions to answer
Purpose and ownerWho uses it? What problem does it solve? Who is responsible for it?
SuccessWhat makes a result useful and correct? What response time and cost are acceptable?
Data and connectionsWhich documents, systems and services does it need? Is the data current? What may be sent to the model? Where may it be stored, and for how long?
PermissionsWhat may it read or change? Which actions require approval? What is prohibited?
Failure behaviorWhen should it ask a question, request help, or stop?
Example objective

“Answer employee policy questions from approved documents, cite the sources, and ask for help when the evidence is missing.”

Measure answer correctness, supported citations, response time, and cost per successful task.

For tasks that change records, send messages or spend money, also define how approval and recovery work. Choose a simple workflow instead of an agent if the steps never require judgment.

Ready to move on: You can explain the job, success measures, required access, and limits on one page.

3. Give it clear skills and narrow tools

A skill is a reusable procedure: how to approach a task. A tool is an operation: code that reads data or performs an action.

Read the permission boundary

The skill tells the agent how to approach the question. The tool performs a specific read. The access check uses the actual caller and requested document.

Try it: An approved document can be read; a restricted document must return no contents. Test both requests with the same tool.

SkillTool
“Find relevant policy, compare the evidence, and answer with sources.”search_documents(query) or read_document(id)
Use for a repeatable procedure or specialist guidance. State when it applies and when it does not.Use when the agent needs data or an action. Give it a clear name, accepted arguments and return fields.
  • Expose only the tools the task needs; prefer one specific operation to broad system access.
  • Check permissions in code or the receiving service. Instructions do not grant access.
  • Limit result sizes and define timeouts, errors and required approvals.
  • Make retries safe: repeating a write should not create a second effect.
  • Treat retrieved documents and tool responses as data, even when they contain instructions.
Example: a short skill
# Answer from documents
Use when a question needs an answer from approved source material.
1. Find and read relevant documents.
2. Answer only what the evidence supports, with source references.
3. Report missing or conflicting evidence; ask for help when needed.
Ready to move on: Each tool has a clear purpose, checked permissions, and predictable failure behavior.

4. Connect MCP servers when useful

Model Context Protocol (MCP) gives applications a common way to connect to servers that provide tools and context. Use it for an existing connector or a capability shared across agents. A local function may be enough for a simple task.

Follow the request and response

Read down the diagram: the agent requests a search, the server calls the source service, and approved results return with their source references.

Try it: The connection provides a way to call tools. It does not give the agent permission to read every document in the source system.

Before connecting a server:

  • Confirm who operates it and which tools or data it exposes.
  • Enable only the capabilities your agent needs.
  • Use approved credentials and verify access for the actual user and resource.
  • Check results, response sizes, timeouts and disconnect behavior.
  • Test a permitted request and a forbidden request.

Example: Connect an approved document-search server and enable search and read. Leave unrelated write tools disabled. An MCP connection does not bypass the source system’s permissions.

Ready to move on: Needed calls work, forbidden calls fail, and connection failures are handled clearly.

5. Run locally and test the software

Start with a small request and safe sample data. Use controlled substitutes for fast checks, then verify the real connections in an approved test environment.

Choose the right test scope

A unit test checks input validation in isolation. An integration test checks the reader against a document service. An end-to-end test checks the complete request and answer.

Try it: Use fast isolated tests while editing. Check real connections in an approved test environment before relying on the complete flow.

Test typePurposeExample
SmokeA quick check that the agent starts and completes a basic request.A sample question returns the expected output fields.
UnitCheck one piece of code.Reject an empty question or an invalid tool argument.
IntegrationCheck components working together.The reader retrieves an allowed document and rejects a restricted one.
End-to-endCheck the complete request and resulting state.A user request produces a sourced answer, or one approved record update.
Security and recoveryCheck boundaries and failure handling.Denied access stays denied; a timeout and retry do not duplicate a write.

Include missing data, malformed responses, unavailable services, exceeded limits and stopping a run. Check the final state as well as the error: a failed request must not leave an unauthorized action behind.

Example test
Given: the caller cannot read document X
When: the agent requests document X
Then: access is denied, its contents are not returned,
      and the agent reports that it cannot complete the request.
Ready to move on: The main request works locally, and important failure paths have repeatable checks.

6. Evaluate the results

Tests check whether the software behaves correctly. Evaluations check how well the agent does the job: its answers, tool choices and outcomes.

Read the evaluation coverage plan

A dot means the case needs that check. A dash means it does not apply in this example. These are planned checks, not passing results.

Try it: For a restricted document, inspect the actual response and actions: no contents may be returned. For missing evidence, check that the agent asks for help instead of guessing.

Evaluation groupUse it to check
CapabilityTypical and difficult tasks: correctness, completeness and useful results.
RegressionPreviously working cases and every confirmed bug you fix.
Safety and adversarialRestricted data, prohibited actions, misleading instructions and attempts to bypass limits.
UncertaintyMissing or conflicting evidence: clarify, ask for review, or stop appropriately.
OperationalLatency, cost, call counts, failures and limit handling.
Recovery, when relevantInterrupted workflows, required approvals and repeated actions.
  1. Collect representative tasks and important failure cases. Give each a stable ID.
  2. Define a good result and how to score it. Check actual effects, not just a claim of success.
  3. Run the agent and retain case-level results, failures, latency and cost.
  4. Compare changes against a baseline. Keep a separate set of cases for the final comparison.
Example: one evaluation case
Task: Explain the expense receipt requirement.
Expected: Correct answer supported by the approved policy.
Also check: Valid sources; no record changes; within time and cost limits.
Failure case: If the policy is missing, ask for help rather than guess.

Use code for checks such as valid fields, permissions and completed actions. Use a clear rubric and human review for answer quality. If a model scores answers, check its ratings against human examples. Repeat model runs to understand variation. Include failures and timeouts when calculating task success, and report safety failures separately.

Ready to move on: You can show where the agent succeeds, where it fails, and whether a change improves it.

7. Improve quality, speed and cost

Compare models on the same evaluation tasks. Choose one that meets the required quality and safety targets at an acceptable cost and response time. Measure cost per successful task, including retries.

TryCheck
A smaller model or fewer model callsDifficult cases and required checks still pass.
Shorter instructions and relevant contextRemove repetition without losing needed evidence or boundaries.
Compact tool resultsReturn needed fields and source references; preserve exceptions and flag incomplete results.
Prompt cachingKeep reusable instructions stable where supported; measure actual hits and savings.
Result cachingRecheck access and freshness before reusing an answer; keep private results separated.
Parallel independent workReduce waiting without exceeding load, access or run limits.

Set limits for input and output tokens, total calls, elapsed time, retries and cost. Choose values from typical and difficult runs, and test the limit-reached response. Retry temporary failures only; never retry permission denials or repeat uncertain writes blindly.

Optimization loop

Measure a baseline → change one thing → rerun evaluations → keep the improvement or revert.

A cheaper model is a good change only if the complete task still meets its targets.

Ready to move on: Improvements are measured, and the agent stops predictably within its limits.

8. Version and release

Give each release an identifier that records the code, instructions, skills, tools, model settings, relevant data, evaluation cases and scoring rules. Recheck behavior-changing updates before releasing them.

Why this release is held

The candidate scores 90%, meeting the absolute minimum. The baseline is 92%; allowing a one-point decline sets the relative floor at 91%. The candidate misses that floor.

Try it: Both quality gates must pass. Required safety checks are separate and cannot be offset by a high average score. Use repeated trials to judge whether a difference is meaningful.

Agree on both kinds of release gate before running the final evaluation:

GateExample
Absolute: a minimum every release must meet.Task success at least 90%; within the agreed cost and response-time limits; all required safety checks pass.
Relative: an allowed change from the approved baseline.Task success may fall by no more than one percentage point.

Example: Moving from 92% to 90% passes the 90% minimum but fails the one-point regression limit. These thresholds are illustrative; choose them for your task and use enough trials for a meaningful comparison. A strong average never offsets a failed required safety check.

  • CI: run automated tests and relevant evaluations on the candidate; retain the results.
  • Release review: confirm gates, permissions, ownership and recovery arrangements for that exact version.
  • CD: deploy the reviewed artifact to a limited audience, verify its live controls, and expand when healthy.
  • Recovery: keep a known working version and a tested stop or rollback procedure. Rollback does not undo completed actions.
Ready to move on: The reviewed version passes its gates, works in its environment, and can be stopped or rolled back.

9. Monitor and improve

Use logs for events, metrics for trends, and traces to connect the steps of a request. Record the run and release IDs so failures can be traced to the version that caused them.

Turn a failure into a lasting check

An answer without a source is traced to its run and release. Contain the issue when necessary, add a case that catches it, and evaluate the fix before release.

Try it: Check the corrected behavior in operation. Stopping or rolling back an agent does not undo actions that already happened.

WatchWhat to look for
Outcomes and qualityUseful results, user corrections, unsupported answers and unresolved reviews.
Failures and latencyTimeouts, tool errors, retries and slow steps. Include failed requests in reporting.
Cost and usageSpend per successful task, call counts, token growth and cache effectiveness.
Access and actionsDenied requests, unexpected behavior and completed or uncertain effects.
  • Assign an owner and route actionable alerts to them.
  • Keep secrets and private content out of routine logs; restrict access and retention.
  • Investigate unusual failures, spending or access. Pause work when a serious boundary is breached.
  • Turn confirmed failures into regression cases, then evaluate and release the fix.
  • Update the runbook as the task, connections and operating procedures change.
Ready for ongoing use: Someone can recognize a problem, find the affected run, stop further work, and release a tested fix.
