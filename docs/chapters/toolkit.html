05 / Developers · Platform implementers

The Zetra Toolkit

Zetra v0.1 is a runnable foundation for the proposed standard. Its framework-neutral Python contract keeps agent logic portable and makes development checks reproducible. The local runtime demonstrates capability checks, bounded execution and receiver-side approval/idempotency. The Kubernetes renderer withholds activation. Integration fixtures exercise real external components separately; a local passing check is never a production approval.

Working local toolkit

Strict manifests, AST hints, conservative risk floors, executable scenario evaluation, evidence binding, candidate profiles, Kubernetes renders and catalog candidates.

Real integration adapters

Explicit Temporal workflow/worker and replay smoke; Kubernetes discovery; versioned live fixtures with reported positive and negative paths.

Production platform work

Trusted signed attestations, enforced admission, authenticated distributed approval/revocation, enterprise catalog service and operational ownership remain implementation gates.

5.1 Install and run the complete local workflow

Use the locked Nix development shell or the pinned mise toolchain, then just bootstrap. uv manages the committed Python resolution, including Ruff, ty and prek; just exposes the common quality gate. The package supports Python 3.11 or newer. The core dependency is PyYAML. Temporal is optional so basic development and example evaluation do not need a cluster, model key or paid inference. Running eval and run executes project code and is intended for a trusted local project or an appropriately isolated CI runner. check scans source without importing the agent.

Empty datasets and policy directories created by scaffolding are organizational aids, not proof that scenarios or controls exist.

5.2 The implemented manifest contract

The parser rejects unknown fields, duplicate YAML mapping keys, invalid identifiers, duplicate capabilities, invalid execution modes, booleans where a numeric budget is expected, nonfinite costs and unbounded values. This prevents a reviewed value from being silently shadowed or a misspelled policy field from disappearing. Capability names are logical identifiers; the initial toolkit implements only a small set of local behaviors and does not claim every declared capability is enforced.

apiVersion: zetra.dev/v1alpha1

schemas/agent-v1alpha1.schema.json documents the wire contract. The Python parser is the authoritative v0.1 validator; CI should require both schema and behavioral validation when an editor or third-party generator uses the schema. spec.execution records deployment intent. The CLI run remains a local development command; use the explicit Temporal worker to select durable execution rather than monkey-patching arbitrary source. The read-only Temporal worker rejects capabilities outside its qualified set.

Validation and gate failures exit nonzero. An evaluation file contains scenario results and binding metadata; absence of a required scenario, failed test, stale evidence or source drift blocks subsequent evidence-dependent commands. Mutable local JSON cannot establish signer trust. The production release service must consume trusted CI artifacts, verify signatures and approvals, and enforce the same evidence contract independently.

The local step, elapsed-time and cost helpers apply to one injected RuntimeDependencies instance. Cost reservations are caller-reported; they are not provider billing measurements. A Temporal retry constructs fresh dependencies and resets these counters. SDK activity and schedule timeouts impose separate bounds. Enforcing a run-wide budget across retries, parallel activities and delegated agents requires an independent durable reservation ledger; v0.1 does not provide that ledger.

5.4 Three reference implementations with useful failure paths

Knowledge assistant. examples/knowledge demonstrates a read-only factory injected with a small approved knowledge store. It answers a known key and returns a defined missing-data response for unknown keys. The cases exercise basic behavior, capability denial, budget exhaustion and stop behavior without a live model. This makes the example deterministic and suitable for understanding the boundary contract; it is not a benchmark of LLM reasoning quality.

Gateway read agent. examples/gateway-read uses the qualified mcp.read_status capability with an explicit restricted StreamableHTTP MCP client. Production connections require HTTPS; plaintext is permitted only at a numeric loopback lab endpoint. The client validates the reviewed tool name and arguments, bounds time and response size, reads rotating workload credentials without logging them, and emits redacted release/run/operation correlation. Offline conformance scenarios and the actual gateway/Temporal/collector chain exercise this adapter.

Approval-gated action agent. examples/action demonstrates a ticket action backed by a SQLite receiver. An independent demonstration controller issues an approval bound to actor and canonical payload with expiry. The receiver atomically consumes the approval, creates the ticket and records a receipt in one transaction. Retrying the same operation returns the receipt; changing payload, actor or approval under the same operation key fails. Reusing the consumed approval for another operation also fails. The suite covers denial and replay/idempotency behavior.

Demonstration trust boundary. The local controller and agent share a machine and the SQLite file. It demonstrates transaction mechanics, not authenticated human identity or isolation from a compromised process. A production approval service needs external authentication, tenant/resource/release/policy binding, revocation, durable storage and independent authority. A remote side effect requires idempotency at its actual receiver.

5.5 Evaluation inference and evidence limits

The initial analyzer uses Python AST patterns and a capability-to-scenario map. It identifies some subprocess, file-write and network patterns and reports recognized undeclared capabilities. Unknown capabilities and incomplete classifications raise review obligations. Reflection, native extensions, aliases, indirect calls, third-party libraries, generated code and remote tool behavior can escape the scanner; a clean scan is not an exhaustive capability graph.

The implemented analyzer emits T0–T3 declaration-based floors. The governance playbook's target model also includes T4 for exceptional or prohibited uses. Business consequence assessment and independent review must apply that escalation; the local analyzer cannot establish that a package is eligible for production or free of T4 conditions.

Stable scenario IDs map to actual unittest selectors. Evaluation runs the selectors and records outcomes, rather than accepting a file named “safety” as evidence. The fingerprint binds relevant package files and manifest content while excluding documented generated/cache paths. Evidence freshness is bounded; changing instructions, dependency declarations, evaluators or scenario selectors invalidates prior evidence. The exact canonicalization and exclusions live in src/zetra/evidence.py. Local timestamps are not a trusted time source for production approval.

Use these mechanics to extend the harness with repeated model runs, evaluator calibration, protected holdout cases, trajectory checks and real sandbox-negative scenarios. The default examples have no paid model and do not provide statistical assurance. An LLM judge must never be the sole authorization, schema, approval, isolation or idempotency gate. Aggregate quality scores cannot compensate for missing material scenarios or a known critical failure.

5.6 Render, profile and prepare the catalog candidate

# Use a real immutable digest from your built worker image.
ZETRA_IMAGE='registry.example/agents/knowledge@sha256:<64-lowercase-hex>'
.venv/bin/zetra render examples/knowledge \
  --image "$ZETRA_IMAGE" \
  --namespace agent-staging \
  --gateway-namespace agentgateway-system \
  --gateway-label app=agentgateway \
  --evidence build/knowledge-evidence.json \
  --output build/knowledge-deployment.yaml

.venv/bin/zetra catalog examples/knowledge \
  --evidence build/knowledge-evidence.json \
  --output build/catalog-candidate.json

The renderer uses a gateway TCP listener template and deliberately grants no broad DNS, model-provider, Temporal or telemetry access. Add reviewed control-plane egress in the environment binding and test it before activation. The image must provide a qualified persistent worker/service entrypoint. Rendering a one-shot demonstration image does not make a production worker. The zero-replica state is an intentional stop gate; a future release controller owns authenticated promotion, policy readiness and admission checks.

The profile command expects normalized input rather than raw vendor-specific kernel or OpenTelemetry events. Adapter parsers must verify event fields, workload identity, descendants, loss counters and version compatibility. The fixture format is documented in the integration directory; malicious or unrelated observations cannot silently broaden the approved manifest. Catalog preparation stores evidence hashes and unresolved gates but cannot publish or approve a record.

Normalized outcome values are allowed, denied or observed; missing values mean observation only. Denied events appear under deniedObservations and are excluded from process, file and network candidates. Even a successful or unclassified observation remains an unsigned review candidate. The real Tetragon fixture records the denied sensitive path without proposing it as permitted access.

5.8 Extend the toolkit without diluting the standard

Next increments should implement adapter parsers and schema-qualified policy generation, signed release evidence and admission validation, centrally authenticated approval/revocation, budget accounting, catalog publication through CD and business-function access controls. Add a feature only when its failure semantics and negative tests are clear. A generic “security enabled” boolean is too weak to stand in for supported control coverage.

Contributors run python -m unittest discover -s tests -v, all three example scenario suites and the document builder. Changes to a schema or canonical evidence format require migration/version rules; changes to a Temporal workflow require replay evidence. Integration changes need a recorded compatibility tuple and supported/unsupported matrix. Do not accept simulated events, resource discovery or empty stubs as live enforcement proof.
