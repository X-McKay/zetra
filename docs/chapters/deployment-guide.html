1. The automated deployment contract

A developer submits an agent package. The platform tests it, observes its behavior, prepares restricted policies, and deploys one approved release whose image, configuration, and evidence remain linked.

The deployment unit is an immutable release bundle, not a container tag. Azure DevOps holds source and deployment intent; Azure Pipelines produces evidence; Azure Container Registry (ACR) stores images and bundles; Argo CD reconciles approved Kubernetes resources. A platform release controller verifies installed controls before granting execution authority.

Two distinct events: publishing an artifact makes it available for testing or deployment. Activating a release authorizes it to process live work. Publication never implies activation.
Scope, ownership, and implementation status

This is the target architecture specification for platform, security, and agent owners. “Must” identifies a release requirement; examples illustrate proposed organization contracts, not vendor APIs. The release controller, policy compiler, catalog service, and authenticated readiness reports are platform components to build or integrate. They are not supplied automatically by Azure Pipelines or Argo CD.

Business owners approve task scope and success criteria. Developers own package correctness and scenario coverage. Platform owners own supported runtime profiles, adapters, and operation. Security owners approve boundaries and material exceptions. The reference repository has tested individual integration fixtures; it has not qualified this complete production composition.

2. Developer push starts validation

A push or pull request in Azure Repos triggers Azure Pipelines. The repository must contain an agent manifest, entrypoint, dependency lock, instructions and skills, tool contracts, requested capabilities, ownership, tests, evaluations, and operational requirements. Missing or invalid required inputs fail validation.

The manifest describes logical needs—such as reading approved documents—not production credentials or unrestricted network access. A platform-owned environment binding resolves each need to an endpoint, identity, resource scope, and enforcement adapter.

Minimum deployment request
# Proposed organization contract; not a vendor schema.
agent: incident-assistant
owner: service-operations
entrypoint: agent-worker
data_classification: internal
capabilities:
  runbooks.read: {scope: operations-library}
  service_status.read: {scope: owned-services}
  tickets.create: {scope: operations-project, approval: required}
acceptance_profile: operations-assistant
runtime_profile: qualified-linux-sandbox
limits_profile: interactive-bounded

Profiles are versioned, reviewed platform defaults. The compiler resolves their exact versions into the release; it must reject missing bindings and unsupported required controls.

Trust separation: pull-request jobs run without production secrets, release-signing authority, or GitOps write access. Protected templates and independent resource checks govern promotion. A developer cannot bypass a required gate by changing their pipeline YAML.

3. CI builds the candidate once

CI validates configuration and tool schemas, runs fast tests and security checks, and builds the container from locked inputs. It generates build provenance and a software bill of materials, scans the image, then pushes it to a restricted candidate repository in ACR. The resulting digest identifies the image used for every later test and deployment.

Integration tests and evaluations run against that image in an isolated qualification environment. Required cases cover task quality, cost, latency, unavailable dependencies, malicious inputs, forbidden actions, approvals, and retry/recovery behavior. Both absolute targets and permitted regression from the approved baseline must pass.

Pipeline stages and isolation
# Logical stages; platform templates implement the actual jobs.
Validate → Build + scan → Publish candidate image
         → Evaluate + profile → Compile policies
         → Qualify candidate controls → Seal release candidate

Privileged eBPF collectors run on dedicated platform-managed Linux nodes, separate from untrusted build execution. Qualification jobs receive bounded test credentials and approved data. Their workload identity, evaluator revision, model configuration, dataset revision, and image digest are recorded. Required access-control outcomes use deterministic assertions, not a model judge.

The same image is promoted; production does not rebuild it. Image publication here is necessary for test-cluster pulls and is not a release approval.

4. Tests and evaluations profile the agent

The qualification job collects selected process, file, and network events through Tetragon; sandbox decisions through OpenShell; visible model and MCP calls through AgentGateway; and task context through application traces. It starts with restricted discovery access, not an unrestricted learner that approves its own requests.

A version-qualified parser correlates the run, scenario, image digest, pod/container identity, and process descendants. It excludes collectors and test runners, records event loss, and preserves attempted, successful, denied, and unknown outcomes separately.

What profiling establishes—and what it does not

The profile answers which operations were exercised by these scenarios on this runtime. It helps find dependencies, missing coverage, and unexpected access. Selected eBPF hooks do not record every syscall, and a finite evaluation suite cannot prove complete behavior.

Denied adversarial attempts never enter permission candidates. A capture gap or unclassified material operation blocks conclusions that depend on it. Raw traces remain in restricted evidence storage; sanitized summaries support review.

5. The compiler prepares native policy candidates

The platform compiler combines the requested capabilities, organization boundary, environment binding, and observed profile. It emits a permission diff, separate native configurations, and a mapping from every required control to its enforcement point.

Tetragon policyScoped kernel observations and responses supported by tested hooks.

Kubernetes resourcesWorkload identity, container restrictions, resource limits, network isolation, and placement.
Release control settingsApproval, budget, task intake, workflow, telemetry, and revocation bindings.

Authority comes from approved intent within organizational limits. Profiling checks sufficiency; it does not grant access. Requested but untested capabilities need coverage. Unexpected operations need investigation. Policy additions require review; routine releases within an already approved boundary can use standing approval rules.

Validate schemas and effective-policy semantics, then rerun allowed and forbidden paths with the final candidate controls. This second pass closes the gap between observing behavior and verifying restrictions. A policy prover may add containment evidence for supported domains; live denial tests remain required.

ACR supports OCI and supply-chain artifacts; the bundle schema and verifier are organization-owned. Evidence links must name immutable versions, not overwriteable “latest” objects. Retention protects releases, attachments, and evidence needed for audit or rollback; referenced artifacts must not be garbage-collected while in use.

Rendered GitOps files are an exact, digest-checked projection of the sealed bundle. A manual edit requires a new qualified bundle. Pipeline job artifacts are convenient downloads, not the long-term release source of truth. See ACR artifact storage.

7. Approval publishes deployment intent

A successful CI run publishes a qualified candidate to the agent catalog and opens a GitOps change. It does not start production CD. The release service verifies evidence, required approvals, exceptions, and the target environment, then records an approval bound to the bundle digest and GitOps content.

Once the approved GitOps change merges, Argo CD detects the new desired revision. The catalog records the version as approved, not active. General user discovery or routing must expose only versions activated for that environment.

Approval and publication are retry-safe

Use a stable release ID plus bundle digest as the idempotency key. Record an immutable approval event before allowing the protected GitOps merge; reconciled catalog projections may lag but cannot supply missing authorization. If any write fails, retry the same operation and keep the release inactive.

Promotion across environments reuses the image. Changed bindings or platform profiles produce a new deployment bundle and affected qualification evidence. Serialize promotions per agent/environment and reject stale updates so an older pipeline cannot overwrite a newer approved release.

Azure resource approvals/checks are controlled outside pipeline YAML. See Azure Pipelines checks.

8. Argo CD installs the approved desired state

Argo CD watches the protected GitOps repository, not ACR pushes or catalog status. It applies the approved environment projection. Shared platform services and CRDs are provisioned and qualified separately; each agent release references supported versions rather than upgrading the platform as a side effect.

2 · Install policiesTetragon loads its CRDs; AgentGateway’s controller reconciles Gateway API / policy / backend resources; a platform OpenShell adapter applies sandbox configuration through its supported lifecycle.Effective policy digest/version reported by each adapter.

Argo CD sync waves provide ordering, not proof of enforcement. The release controller must independently validate authenticated readiness reports against the release, policy version, and target nodes. If any mandatory confirmation is missing, no live task intake or action authority is issued.

For the layer architecture and native configuration flows, see deployment layers, Tetragon, OpenShell, and AgentGateway.

9. Activation grants bounded execution authority

The release controller checks approval, signature trust, freshness, revocation status, installed policy versions, and target-environment probes. Only then does it enable a limited canary: restricted users or task volume, explicit budgets, and an observation window with agreed thresholds.

Admission rejects an unbound image or changed configuration. Sandbox and network controls prevent gateway bypass. Receivers authenticate release/task scope and approval before effects. A “ready” pod is not enough: execution authority is a separate, revocable decision.

Expansion and partial failure

Expand only while quality, latency, cost, failure rates, and boundary health remain acceptable. The catalog’s active state is a projection of confirmed activation, not an authorization switch. Task routing and receivers rely on authenticated authority and current revocation state.

Provisioning may start a trusted supervisor before agent code, but it must not execute agent code before mandatory confinement is established. Argo stages worker replicas at zero where appropriate; the platform lifecycle adapter owns activation, avoiding two controllers writing the same field. For OpenShell-managed workloads, Argo owns the release intent and the adapter owns generated sandbox resources.

10. Observe the release and its controls

OpenTelemetry links task, workflow, gateway, and receiver activity. Kernel and sandbox events correlate through release and workload identity. Record outcomes, latency percentiles, cost per completed task, retry volume, approval waits, denials, collector gaps, and effective-policy drift.

Central teams see fleet and control health; business teams see their agents’ outcomes and spend. Every alert has an owner and response. Required control failure withdraws or blocks authority according to the risk profile; unexpected denials trigger investigation, never automatic permission expansion.

Catalog updates and data handling

The controller reports observed release/policy versions, rollout progress, qualification status, revocation acknowledgements, and incidents to the catalog. Preserve desired state separately from observed state. Protect sensitive traces, redact before export, define retention, and retain approval/effect audit records independently of trace sampling.

Temporal coordinates durable work and approval waits where needed. Receiver-side idempotency prevents duplicate effects; workflow retries alone do not guarantee exactly-once business actions.

11. Change, rollback, and revoke as a linked release

Code, instruction, model, tool schema, policy, or runtime changes restart the affected validation path. Version image and policies together. Rollback selects a still-approved complete bundle; it must not restore old code while retaining unrelated permissions.

A kill switch stops new intake, revokes gateway/receiver authority, cancels workflow work, and isolates or stops workloads. Receivers must reject stale authority after the agreed revocation interval. Reconcile in-flight effects; termination cannot undo an action already committed.

Recovery requirements

Check previous-release availability, policy compatibility, evidence validity, credentials, and workflow-history compatibility before rollback. Revoke independently of GitOps so repository outages or Argo reconciliation delays do not prevent an emergency stop. A safety override is audited and time-limited; self-healing must not reactivate a revoked release.

Retirement removes routes, identities, approvals, schedules, and credentials, drains work, and applies data retention rules. Production incidents become new regression scenarios.

12. Acceptance criteria for the platform

The architecture is ready for an initial controlled rollout when one complete release demonstrates all of the following, on the supported compatibility profile:

  • A developer push produces an image-bound evaluation/profile and a readable native policy diff without manually wiring each product.
  • A failed gate, unsigned bundle, altered policy, stale approval, or revoked release cannot activate.
  • Argo deploys the approved revision; each adapter reports the matching effective policy before live authority is issued.
  • Direct egress, protected-file access, forbidden tools, cross-tenant requests, unapproved actions, and duplicate effects are rejected in live probes.
  • Canary expansion, a failed deployment, controller restart, concurrent promotion, rollback, and revocation have observable, retry-safe outcomes.
  • Operations can trace an effect to the task, agent, image, policy, approval, and release evidence.
Remaining platform work: release compiler and signing policy; OpenShell lifecycle adapter; admission and readiness verification; catalog and authority/revocation service; CI/GitOps templates; composed qualification and operational runbooks.
Design basis and deeper references

The supplied eBPF, OpenShell, AgentGateway, evaluation, and Temporal proposals inform this specification. Their discovery and automation ideas are retained; observed behavior is not treated as authority, formal analysis is bounded by modeled coverage, and native policy installation is separated from tested enforcement.

Detailed configurations and prior test scope are in the Deployment Playbook, integration deep dive, incident walkthrough, and integration evidence index. OpenShell adoption, kernel/CNI coverage, distributed credentials, and revocation require an explicit qualification decision for the selected deployment. This specification does not claim production qualification.

13. Deployment layers and trust boundaries

These technologies operate at different boundaries. An agent runs inside a supervised execution environment; its requests pass through an authenticated gateway; the underlying Linux node provides independent kernel evidence. The receiving service decides whether a specific business effect is authorized.

Layer / technologyWhere it runsPrimary responsibility
Kubernetes + network-policy CNICluster, nodes, and workload networking.Placement, workload identity, container restrictions, resource isolation, and blocking direct routes around approved services.
Tetragon / eBPFPlatform-managed node daemon, outside agent control.Observe selected process/file/network behavior; apply supported, qualified responses at kernel hooks.
OpenShellSandbox runtime and supervisor/proxy; managed through its supported Kubernetes driver.Confine filesystem and network access; supervise the agent’s execution lifecycle.
AgentGatewayShared or tenant-isolated gateway data plane and Kubernetes controller.Authenticate callers and restrict supported model/MCP requests and routes.
Tool / business-service receiverDestination API or dedicated action service.Validate tenant/resource scope, arguments, approval, current authority, and idempotency before effects.
Release controller + admissionRestricted platform control plane.Verify artifact trust, reconcile lifecycle, collect effective-state evidence, activate or revoke.
Temporal + OpenTelemetryWorkflow service/workers and telemetry collectors.Durable coordination and correlated observation; neither replaces access authorization.

One request, several checks: the sandbox permits reaching the gateway; network policy prevents bypass; the gateway validates identity and tool access; the receiver checks the target resource and approval. Tetragon supplies an independent view of selected node activity throughout that execution.

Deployment topology and overlapping controls

Use an explicit AgentGateway endpoint injected into the agent’s runtime configuration. Do not assume encrypted traffic can be semantically inspected by a kernel probe or transparent redirection. TLS trust and protocol termination must be configured at the supported inspection boundary.

OpenShell is provisioned through its driver, not treated as an ordinary library or a sidecar that automatically secures an existing container. Its supervisor and workload may be separate runtime resources. Qualify attribution for this topology: network events can belong to a proxy rather than the agent process.

For this design, OpenShell permits the approved gateway connection; AgentGateway owns upstream model/MCP credentials and semantic authorization. Additional OpenShell provider routes require explicit review. Tenant isolation and gateway availability determine whether gateways are shared, per tenant, or dedicated. Select one supported topology per platform profile.

14. Tetragon: kernel profiling and runtime response

Purpose. Tetragon provides evidence below the application: selected process creation, file operations, connections, and related kernel activity. It can execute supported responses, but it does not understand whether an answer is correct or a ticket is justified.

Platform prerequisite. Install and qualify the node daemon independently of agent releases. Pin image/chart/CRD versions, runtime-hook integration, supported kernels and node classes. Maintain a library of tested probe and response templates; agents never choose arbitrary host-wide hooks.

Automatic configuration

  1. Select observation templates. CI resolves the runtime profile, namespaces, protected workload selectors, intended file/network/process coverage, and image subject.
  2. Capture and normalize. Run scenarios on qualified nodes; collect native events and loss counters; correlate container identity and descendants. Preserve hook, arguments, action, outcome, and uncertainty.
  3. Generate the candidate. Populate versioned templates with reviewed resource scopes. Keep observation requirements separate from enforcement requirements. Do not translate an observed binary list into an untested blanket kill rule.
  4. Qualify, package, and install. Validate against installed CRDs, execute scoped negative probes, store YAML in the signed ACR bundle, and render the identical resource into GitOps. Argo applies it; Tetragon loads it on applicable nodes.
  5. Verify readiness. The platform adapter checks native policy state, workload attribution, supported actions, startup coverage, and collection health, then issues a release-bound readiness report.
Generated observation policy: native configuration shape
# Illustrative template output: selected TCP observation, not a deny rule.
apiVersion: cilium.io/v1alpha1
kind: TracingPolicyNamespaced
metadata:
  name: incident-r42-connect
  namespace: agents-operations
spec:
  podSelector:
    matchLabels:
      platform.example/agent: incident-assistant
      platform.example/release: r42
  kprobes:
    - call: tcp_connect
      syscall: false
      args:
        - index: 0
          type: sock

The compiler fills the namespace and protected selectors from the environment binding. The hook and argument definitions come from the qualified template, not agent-generated code. Kubernetes admission/RBAC prevent arbitrary workloads from copying or changing release selectors. The image binding is checked separately; a label is not authenticated artifact identity.

Validate the emitted fields on the actual node. Socket observations do not directly identify MCP tool names or HTTP authorization decisions. Native schema: Tetragon policy API.

Enforcement, updates, and activation failures

An enforcement template must name the exact operation, hook, selector, action, and expected outcome. Where prevention is required, use a qualified pre-operation mechanism or another preventive boundary. A post-event Sigkill response must not be represented as guaranteed prevention of an already attempted effect.

Require the selected runtime-hook/startup strategy to establish coverage before agent code. New nodes and rescheduled workloads must meet the same condition; an earlier acknowledgement from another node is insufficient. See runtime hooks and policy concepts.

Roll out versioned policy resources without replacing the active release’s rules underneath it. Narrow selectors prevent canary policies from affecting unrelated workloads. Missing policies, unsupported hooks/actions, unqualified nodes, excessive event loss, or unexplained startup gaps withhold the affected release. Runtime failures trigger the risk profile’s containment/stop response.

15. OpenShell: supervised execution and sandbox policy

Purpose. OpenShell constrains the execution environment around the agent. Filesystem restrictions use Linux Landlock; network policy permits supported connections and request patterns through the sandbox proxy. The sandbox lifecycle is a platform operation, not something the agent can approve or widen.

Platform prerequisite. Qualify the selected compute driver, runtime image, kernel protections, authentication, and policy-update behavior. Identify required runtime paths and writable scratch mounts. The agent image must be compatible with supervised execution; an arbitrary container is not automatically a qualified sandbox.

Automatic configuration

  1. Resolve access. Map the approved filesystem request, runtime baseline, gateway endpoint, binary paths, process identity, and scratch limits into a native policy.
  2. Validate effective scope. Account for policy precedence, provider-contributed rules, and baseline paths. The organization boundary is applied by the compiler; a global policy is not assumed to intersect per-agent policy.
  3. Qualify the sandbox. Run the candidate image under that configuration. Confirm approved reads/writes and routes, then test protected-file access, outside-scratch writes, direct egress, and alternate-executable paths.
  4. Create through the lifecycle adapter. After Argo publishes the approved release intent, the adapter verifies the bundle and calls the supported OpenShell lifecycle interface with image, policy, and approved provider/credential references.
  5. Read back and activate. Await loaded policy state, retrieve effective configuration, reconcile it against the approved plan, and record sandbox generation and policy revision. Only then run the agent with the allowed task authority.
Generated sandbox policy: native configuration shape
# Partial template output; resolve all runtime paths before use.
version: 1
filesystem_policy:
  include_workdir: false
  read_only: [/app, /usr, /lib, /etc/ssl/certs]
  read_write: [/tmp/agent-scratch]

  compatibility: hard_requirement

  approved_gateway:
    endpoints:
      - host: gateway.internal.example

Use the image’s actual executable and library paths. This TCP route is a transport permission, not MCP tool authorization. The approved Kubernetes workload definition supplies nonroot identity, bounded scratch storage, and resource limits. Schema and driver behavior: OpenShell policy reference.

Policy composition, updates, and activation failures

Provider attachments can add network rules to the base policy. A configured global policy replaces individual policy rather than acting as an intersecting ceiling. Compare the effective result, including baseline additions, with the approved boundary; block unexpected widening. See policy precedence and composition.

Filesystem and other startup controls require a replacement sandbox when changed. Supported network changes may load live, but this architecture still binds them to an approved release revision. Read back the loaded revision and test required denials after updating; submitted configuration is not proof of activation. See policy lifecycle.

Keep automatic advisor approval disabled. If a prover is used, require conclusive results for the necessary modeled domains. Neither proposals nor proofs replace runtime probes. Missing required Landlock protection, skipped required paths, unsupported inspection, policy mismatch, or failed provider authentication blocks activation.

The adapter uses release/environment as an idempotency key, reconciles existing sandbox generations after restart, propagates cancellation, and cleans up retired generations. These orchestration and readiness obligations are proposed platform functionality.

16. AgentGateway: identity, model routes, and tool authorization

Purpose. AgentGateway provides an explicitly addressed boundary for supported model and MCP traffic. It authenticates the caller, selects approved upstreams, and restricts supported requests. Network and sandbox controls make direct upstream access fail.

Platform prerequisite. Install compatible Gateway API and AgentGateway CRDs/controller/data plane. Configure trusted TLS, workload authentication, backend credential integration, and telemetry. Give tenants and releases explicit route/policy scope; do not permit an agent author to attach policy to another tenant’s route.

Automatic configuration

  1. Resolve semantic capabilities. Map logical model aliases and MCP tools to approved backends, exact tool schemas, authenticated subjects, and resource-authorization owners.
  2. Render native resources. Generate Gateway/route resources, AgentgatewayBackend definitions, and AgentgatewayPolicy for supported authentication, model/tool authorization, and limits. Credentials appear only as approved references.
  3. Check scope and policy interactions. Validate target references, namespaces, TLS, issuer/audience, merge precedence, and any broader inherited rules. Preserve denial by default for the protected route.
  4. Qualify and reconcile. Test allowed calls, invalid/expired identities, forbidden tool calls, model restrictions, cross-tenant paths, and bypass. Seal the configuration in ACR; Argo applies the matching GitOps resources; the controller configures the proxy.
  5. Verify the data plane. Confirm native status and effective behavior, associate the serving gateway configuration with the release, and report readiness. Inject only approved endpoint bindings into the agent runtime.
Generated MCP authorization policy: native configuration shape
# Tool authorization fragment. JWT validation / TLS / routes are separate.
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: incident-r42-tools
  namespace: agentgateway-system
spec:
  targetRefs:
    - group: agentgateway.dev
      kind: AgentgatewayBackend
      name: incident-r42-mcp
  backend:
    mcp:
      authorization:
        action: Allow
        policy:
          matchExpressions:
            - 'jwt.sub == "incident-r42" && mcp.tool.name in ["read_runbook", "read_status", "create_ticket"]'

The backend/route must have separately configured authenticated identity. A caller-supplied sub field is not a trusted JWT claim. Keep the claim and tool check in the same expression: alternative match expressions use OR semantics. Validate this shape against the installed release and test both tool discovery and direct tools/call.

Allowing create_ticket at the gateway does not grant approval to create a particular ticket. The receiver checks project/tenant, exact arguments, approval scope/expiry, revocation, and idempotency before the effect. References: MCP tool authorization and native resource API.

Credentials, limits, updates, and activation failures

For this topology, the gateway integration owns upstream credentials; the agent receives restricted workload identity. Backend key retrieval, rotation, and any token exchange require a qualified integration. Do not assume a Kubernetes token automatically becomes a model or business-service credential.

Enable supported request/token limits, model allowlists, and content checks according to the platform profile. Aggregate financial budgets and action approval may need independent ledger/receiver services. Content filters are supplementary and cannot guarantee that every sensitive disclosure or malicious instruction is detected.

Create release-scoped routes/backends or otherwise qualify isolated policy updates. Wait for convergence and data-plane probes before shifting traffic. Authentication failure, unsupported mandatory policy, rejected target references, unexpected merged permissions, failed credentials, or a successful bypass blocks activation. Revoke receiver/gateway authority independently of eventual GitOps cleanup.

17. The shared automation and readiness contract

The compiler and three adapters share a release identity, but each produces its own native artifact and effective-state report. None of the products natively consumes the organization’s complete release bundle. The platform provides that binding and translates it into supported product interfaces.

Authenticate the reporting adapter and verify its allowed target scope. Effective policy may contain provider/runtime contributions, so its normalized digest is not necessarily identical to the base artifact digest. The verifier checks the approved transformation and additions; it does not accept arbitrary equality asserted by the agent.

The release controller requires current acknowledgements from all mandatory boundaries, with the same bundle, environment, and applicable workload/node scope. Controller restarts, node replacement, provider changes, or policy drift require revalidation. No adapter may silently downgrade an unsupported control to a warning.

During deployment, failures keep the candidate inactive. During operation, risk-specific control failures withdraw affected authority, preserve evidence, and reconcile in-flight effects. Upstream status plus actual probes establishes readiness; labels, timestamps, hashes, and green Kubernetes objects alone do not.
