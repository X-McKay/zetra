01 · Executive sponsors · Product leaders · Platform architects

Agent Strategy

Make governed agent development the easiest way to deliver useful automation. Zetra—ZEro-TRust Agents—provides one package contract, one evidence-driven lifecycle, and a platform that applies controls consistently without hiding the decisions people remain accountable for.

1.1 Purpose, outcomes, and boundaries

An agent is a software system that uses model outputs to select or sequence actions. Its risk comes from the authority those actions carry, the data they touch, their reversibility, and the uncertainty of their decisions. The strategy therefore starts with business outcomes and bounded authority, rather than a preferred model or a large collection of disconnected guardrails. A successful agent solves a defined problem within an agreed operating envelope, produces evidence of its behavior, and can be stopped without waiting for it to cooperate.

The platform should support a progression from assistance to bounded execution. A research assistant might retrieve approved documents and prepare a cited answer. A change-preparation agent might draft an update but require a person to approve its exact content. A service agent might execute a narrow, reversible action under a transaction limit. The same package and release vocabulary should describe all three, while their risk tiers and enforcement differ. “Agent” must never become an exemption from software engineering, identity management, change control, or incident response.

Zetra’s operating objective is a paved road: a starter package, typed capability interfaces, local validation, repeatable evaluations, reviewable policy proposals, immutable release evidence, and deployment adapters. Developers should spend their effort on domain behavior and evaluation cases. Platform teams should own identity, policy distribution, runtime controls, telemetry delivery, and durable execution integration. Business owners should own intended outcomes, authorized use, acceptable consequences, and recovery decisions.

Delivery status. This playbook defines a proposed target operating model. The repository’s v0.1 toolkit is an initial local validation and reference scaffold. A passing local command does not demonstrate production sandbox enforcement, admission control, a live gateway, a durable workflow, signed attestations, or a functioning kill switch. Use the toolkit capability matrix and deployment readiness checklist before describing any environment as governed.

Zero trust here means that an agent’s presence on an internal network, a successful evaluation, or a previously approved conversation does not confer continuing authority. Every request needs an authenticated identity, a current authorization decision, and an appropriate resource boundary. 1.3 One supported stack with deliberate extension points

Standardize the integration contract before attempting to standardize every library. The chosen baseline is framework-neutral Python interfaces, consistent with the supplied architecture sketch and design drafts. Each approved Python framework adapter should expose typed construction, a bounded invocation interface, tool metadata, trace propagation, cancellation behavior, and test substitution. A framework can be accepted only after its adapter passes those contract tests. Developers should not need to understand several framework-specific deployment models to deliver a simple agent.

The target platform combines a model and tool gateway, a sandbox boundary, cloud-neutral Kubernetes deployment, central telemetry, and Temporal for durable orchestration when required. AgentGateway, OpenShell, and eBPF tooling are proposed integration components from the supplied documents. Each needs a pinned version, a validated deployment topology, and an explicit compatibility test. Product names do not establish that a specific policy syntax, credential exchange, or interception mechanism exists. The deployment playbook separates validated upstream capabilities from Zetra requirements and adapter work.

The platform should publish a support matrix covering Python and adapter versions, container base images, Kubernetes distribution and version, kernel features, sandbox compatibility, gateway transports, model endpoints, and telemetry schemas. A release’s runtime fingerprint must identify the exact combination tested. An unsupported kernel, remote MCP transport, gateway plug-in, or model alias should create a visible compatibility failure, not a silent fallback to weaker controls.

Extensions belong behind named contracts. A new framework should provide an adapter rather than an alternate release process. A new tool should implement a declared capability interface rather than receive a generic credential. A new evaluator should publish its inputs, scoring semantics, failure modes, and reproducibility limits. A new business function should define ownership, data scopes, approved destinations, and decision rights without forking the platform. Exceptions are time-limited decisions with compensating controls and a migration plan.

1.4 Select use cases with an accountable value hypothesis

Before building an agent, document the work being improved, the current baseline, the people affected, and the decisions the agent may make. Compare an agent with a deterministic workflow, a search interface, or a simpler assistant. Choose the agent when uncertainty in inputs or action sequencing provides material value that outweighs evaluation and control costs. Multi-step autonomy adds an obligation to explain termination, escalation, resource consumption, and failure recovery.

A charter should name the business owner, technical owner, on-call team, target users, authorized inputs and outputs, maximum consequence, prohibited actions, and success criteria. State the environment where evidence will be collected and the conditions under which the trial will end. For example, an internal knowledge assistant might aim to reduce supported question resolution time while maintaining citation correctness and tenant isolation. A purchase assistant might initially prepare orders only, with no spend authority. Expansion to execution would be a new capability and risk decision.

Use cases should progress through discovery, bounded pilot, controlled production, and expansion. Each promotion changes an operating envelope and requires updated evidence. A useful prototype with broad developer credentials is not a production candidate until those credentials and capabilities are replaced. A failed pilot may still produce reusable datasets, a tool adapter, or a control test; capture those assets and stop the use case when its value hypothesis fails.

Developers implement bounded behavior and submit evidence. Operations owns the reliability of the enforcement and execution planes.

1.8 Tradeoffs and strategic constraints

Automatic profiling can reduce policy authoring effort, but observation is incomplete and can include malicious or accidental behavior. Treat generated rules as proposals bounded by declared purpose and central invariants. Static analysis can reveal likely side effects, yet imported libraries, dynamic dispatch, remote tools, and runtime configuration leave uncertainty. The platform must expose that uncertainty and request evidence rather than awarding an unjustified low-risk score.

Automatic injection reduces repetitive setup but can make failure opaque. Prefer explicit, versioned deployment plans and a diagnostic command showing the resolved identity, routes, sandbox profile, model configuration, and telemetry path. Framework adapters should use supported integration interfaces where possible; arbitrary monkey-patching is a compatibility liability. Durable execution helps recover coordination state but does not remove the need for idempotency, business reconciliation, or compensation.

Centralization creates concentration risk. Gateway and policy outages need tested fail-closed behavior at consequential boundaries, appropriate caching and freshness limits, and a clear explanation to users. Telemetry can itself become a sensitive data store. Default to metadata, controlled redaction, and selective content retention. Cost and latency overhead should be measured and attributed so that safe defaults remain sustainable.

The strategy does not claim regulatory compliance. Determine legal or regulatory obligations through the organization’s qualified owners, map applicable obligations to evidence and controls, and preserve those mappings separately from technical capability claims. Organizational risk tolerance, approval thresholds, data classes, and retention rules remain ratification decisions.

The eBPF, OpenShell, and AgentGateway drafts motivate layered profiling and policy generation. PXL_20261007_230415496~2.jpg supplies the typed-factory and repository-layout sketch. Every decision should identify its evidence, accountable owner, effective date, review trigger, and replacement plan. Version the register with the playbook so teams can distinguish an approved standard from a proposed next capability.

02 · Agent developers · Technical leads · Evaluation engineers

Agent Developer Playbook

Build a small, portable agent package with explicit capabilities, typed dependencies, and evidence that its behavior fits its purpose. Use framework-neutral Python interfaces; use Temporal when durable coordination is required. Platform integrations must be independently qualified before production execution.

2.1 The package is the unit of delivery

A production agent is a governed software package, not a prompt plus a service account. Its package contains the agent entrypoint, typed input and output, instructions, declared tools and capabilities, evaluation cases, policy intent, ownership, and operational documentation. The developer supplies a complete description of what the agent needs; the platform resolves environment-specific bindings under approved policy. Do not store provider keys, cluster addresses, or production authorization decisions inside prompts.

Use the directory layout below as the target standard. The v0.1 scaffold is smaller and demonstrates the contract; teams can adopt the full layout as their agent needs grow. Directory existence does not count as test coverage. A one-shot agent may have no workflow implementation, while a durable agent must carry workflow and replay evidence. Keep generated deployment artifacts separate from developer-authored intent so review can identify which decisions were supplied, inferred, and resolved.

Do not maintain two independent copies of the same intent. An agent image should contain only runtime dependencies and the immutable package; evaluation data or debugging utilities need not enter the production image.

2.2 Declare identity, purpose, capabilities, and limits

The v0.1 manifest is a YAML contract, not a Kubernetes resource to apply. Its apiVersion identifies a Zetra schema. Metadata identifies accountability and business attribution. The specification identifies an importable entrypoint, data class, autonomy mode, execution mode, budgets, and capabilities. Read the shipped examples for the supported capability structure; the following minimal scaffold uses no external authority.

apiVersion: zetra.dev/v1alpha1
kind: Agent

  name: bounded-assistant

  businessFunction: knowledge-operations

The v0.1 capability list uses resource.operation strings such as documents.read; richer scopes belong in a reviewed capability registry and future schema. A capability must describe semantics, not only an HTTP verb. A GET endpoint may trigger a change, a POST may implement a read-only search, and a stored procedure may write regardless of the query text visible to a scanner. For each tool, document its business effect, resource namespace, tenant boundary, data read and emitted, reversibility, required approval, idempotency mechanism, and destination. Register a versioned capability ID so a policy and an evaluation can refer to the same action.

Do not mark data public because the source is reachable without credentials: proprietary outputs, user-provided inputs, and joins may change sensitivity. Use unknown when classification or autonomy has not been established. Unknowns block automated low-risk promotion and require review. Budgets constrain work, not just reporting: define how model calls, tool calls, retries, wall time, and estimated spend are counted. Production cost enforcement needs authoritative accounting and reservation behavior; the local demo’s cooperative checks are not a billing control.

2.3 Construct through typed dependencies

Factories build agents from validated configuration and supplied capabilities. Construction must not make a model request, create a cloud resource, read arbitrary secrets, or register global credentials. A test can construct the same behavior with a fake model and fake tool. A production adapter can provide an identity-aware gateway client. This makes behavior portable without pretending runtime controls are transparent magic.

# Target interface example, independent of an agent framework.
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Question:
    text: str
    tenant: str

@dataclass(frozen=True)
class Answer:
    text: str
    citations: tuple[str, ...]

class DocumentSearch(Protocol):
    async def search(self, *, tenant: str, query: str) -> list[dict]: ...

class ModelAdapter(Protocol):
    async def answer(self, *, question: str, context: list[dict]) -> Answer: ...

@dataclass(frozen=True)
class Dependencies:
    search: DocumentSearch
    model: ModelAdapter

class KnowledgeAgent:
    def __init__(self, deps: Dependencies):
        self.deps = deps

    async def run(self, request: Question) -> Answer:
        # Tenant must also be authorized at the search service boundary.
        docs = await self.deps.search.search(
            tenant=request.tenant, query=request.text)
        return await self.deps.model.answer(
            question=request.text, context=docs)

def create_agent(deps: Dependencies) -> KnowledgeAgent:
    return KnowledgeAgent(deps)

The interface prevents accidental coupling; it does not stop hostile code from importing a network library or accessing the operating system. Authorization remains at the tool receiver and gateway, while sandbox and network controls constrain bypass. Validate tool arguments with bounded length, exact types, permitted enum values, and resource-scope rules. Reject unexpected fields when ambiguity could change an action. Validate the final result before returning it to users or downstream automation.

Keep instructions in versioned files and treat their changes as behavior changes. Instructions should explain purpose, permitted resources, escalation, and stopping conditions. They may remind a model about security, but they cannot grant or revoke a capability. Remote documents, search results, tool output, and messages from other agents remain untrusted input. Delimit their role, preserve provenance, and test what happens when they contain forged system instructions or requests to reveal secrets.

2.4 Work through a repeatable lifecycle

Start with a charter and a bounded package. Implement typed input/output and a deterministic fake before connecting a provider. Declare tools and data flows, then build tests that demonstrate both permitted work and expected denials. Run the local validator and evaluation runner repeatedly. Once behavior stabilizes, generate a candidate deployment plan and an evidence bundle. Platform integration tests, owner review, and tier-specific approvals precede promotion. Monitor the deployed release, and feed discovered failures into the regression set.

# Supported v0.1 local commands; use the included examples first.
zetra init /tmp/my-agent --name my-agent
zetra check /tmp/my-agent
zetra eval /tmp/my-agent --output /tmp/eval.json
zetra check /tmp/my-agent --evidence /tmp/eval.json
zetra run /tmp/my-agent --input '{"key":"zetra"}'

# Render is a withheld plan until runtime adapters are qualified.
zetra render /tmp/my-agent \
  --image registry.example/agents/my-agent@sha256:<digest> \
  --namespace agents-staging \
  --gateway-namespace agent-platform \
  --gateway-label app=agentgateway \
  --evidence /tmp/eval.json --output /tmp/deployment.yaml

Use the shipped scaffold’s documented input schema with run; the knowledge example uses a string key, while other agents define their own schema. check performs local structural and capability checks. eval executes the included deterministic scenarios and produces evidence. Neither substitutes for external service integration tests or model-quality evaluations. The render command emits replicas zero where production adapter qualification has not been established. Do not edit the generated workload to activate it without satisfying the deployment playbook.

When a change adds a tool, changes a destination, raises a budget, alters data classification, or changes approval behavior, update its risk map and negative cases before review. A prompt, model, dependency, remote tool schema, policy, or runtime adapter change can also change behavior without altering the agent’s Python logic. Bind all relevant versions into release evidence and invalidate stale evidence when material inputs change.

2.5 Build evaluations from material risks and task behavior

Maintain stable risk IDs across datasets and releases. An ID names a failure scenario, not a source-code line. Record the capability that introduces the risk, the harm, the preventive control, the evaluator, and the minimum passing criteria. Static analysis proposes requirements from likely capabilities; manifest declarations and observed runtime behavior add evidence. Developers and reviewers reconcile these sources. Unresolved dynamic behavior is an unknown, not evidence of harmlessness.

Add skill activation and non-activation cases for each skill, plus interference cases when multiple skills are available.

Evaluate trajectories when order matters: retrieval before answering, approval before execution, no redundant external mutation, correct retry behavior, and appropriate stopping. Assert properties rather than an exact incidental tool order when several valid plans exist. Keep tool outcome evidence independent from the model’s narrative; “I did not change anything” is not a security assertion. A consequential action test must inspect the receiving system or trusted fixture.

Set release thresholds before running the candidate. Critical authorization, approval, isolation, schema, and revocation scenarios require all mandatory cases to pass with no known critical violation. Quality thresholds are task-specific absolute criteria plus permitted regressions against a baseline. Cost and latency need approved budgets and percentile targets. A failed hard gate blocks promotion even if a composite quality metric rises. Never delete or relabel a failing material risk simply to restore a pass.

2.6 Reproduce evidence without overstating certainty

Store dataset and source digests, manifest hash, instruction versions, evaluator versions, adapter version, Python and dependency lock, model identifier, inference parameters, provider configuration, runtime image digest, policy revision, execution timestamp, and environment identity. Preserve case outcomes, relevant trace IDs, and denial receipts under the data handling rules. Hash evidence or sign an immutable bundle through the approved build identity in the target pipeline. Local v0.1 evidence hashes detect mismatches; they are not a trusted supply-chain signature.

Separate deterministic tests from model-dependent evaluations. A fake model can prove a control denies a forbidden action when requested; it cannot establish real-model answer quality. A live model evaluation measures behavior under a recorded provider configuration; it may not replay identically later. Use repeated runs for nondeterministic behavior, report failures per case and subgroup, and state run count. Keep a held-out set, review judge disagreement, and avoid leaking expected answers into prompts or retrieval content.

An LLM judge may support relevance, style, completeness, or usefulness scoring with a calibrated rubric. It must not be the sole evaluator of authorization, approval, isolation, required schema validity, or duplicate side effects. Use deterministic assertions and trusted receiver outcomes for these properties. A zero-failure sample is finite evidence: preserve sample size and test scope, and do not translate it into a universal safety probability without an appropriate statistical model.

2.7 Test the code and the security boundaries

Unit tests cover argument validation, formatting, budget accounting, factory purity, escalation, and capability selection using fakes. Integration tests exercise the approved model/tool adapters and a representative destination with scoped identity. Security tests bypass the cooperative wrapper: attempt direct egress, access disallowed paths, launch prohibited processes, call an unauthorized remote tool, and use another tenant’s identifier. These tests belong in the qualified runtime environment; a Python exception alone does not show operating-system isolation.

Supply-chain checks should inventory dependencies, pin versions, inspect image contents, scan for secrets and known vulnerabilities, and verify the approved base image and build provenance. Review new or changed remote MCP tools as dependencies with versioned schemas and business semantics. Tool discovery must not automatically expand the permitted set. Validate output size, timeout behavior, deserialization, redirect handling, and destination authorization. A permitted server can still return hostile content or expose dangerous actions.

Approval tests should change one bound property at a time: actor, agent version, action, resource, tenant, payload digest, expiry, and run identity. Test duplicate submission and concurrent consumption. Verify that a human-approved preview matches the receiver’s canonical action. The local reference implementation demonstrates payload binding and single use; production needs authenticated approval issuers, a durable consumption ledger, revocation, and fenced receiver enforcement.

2.8 Durable execution with Temporal

Use Temporal for coordination that must survive worker failure, wait for approvals, or run across a long period. Keep model calls, external network I/O, and business side effects in activities. Keep workflow coordination deterministic and use the approved SDK’s workflow-safe facilities. The supplied wrapper draft’s goal is useful, but arbitrary framework code cannot be made replay-safe merely by changing a launch command. Build and test an explicit adapter boundary. See Temporal’s Python workflow requirements.

For each activity, define timeout, retry policy, cancellation semantics, idempotency key, destination deduplication, and reconciliation procedure. Assume an external effect may commit while the activity appears to fail. Approval waits must retain the action digest and expiration, and revalidate current policy when execution resumes. A workflow saved before revocation must not recover old authority. Determine service-specific payload and history limits during platform qualification rather than copying a fixed limit from an unverified draft.

Replay tests use recorded representative histories after workflow-code changes. Crash tests cover before request, after receiver commit, before result recording, and during approval consumption. Test workflow versioning and worker compatibility before rollout. Define what cancellation accomplishes: it may stop future coordination but cannot undo an already completed external mutation. 3.2 Compile permission from intent, evidence and a boundary

Policy synthesis is a constrained proposal process. Static analysis produces capability hints; SDK/MCP introspection supplies tool schemas; dynamic profiling reveals exercised behavior and denials. None establishes business authorization. The approved capability request states what the agent is allowed to do; the organization boundary states what the platform may permit; the environment binding identifies how that authority is enforced. The target effective permission is their intersection, with explicit deny precedence and time-bounded exceptions.

Normalize events into a schema with agent ID, release/image digest, pod UID, container ID, process ancestry, operation type, destination/resource, outcome and collection timestamp. Reject mismatched workload identity; retain event-loss metrics and collector health. Never append an entire trace to an allowlist. Deduplicate repeated calls, distinguish attempted from successful operations, and retain supporting scenario IDs. A call seen only in an adversarial test is evidence that a denial should work, not a reason to grant it.

Profile delta reports show “declared but unobserved,” “observed and declared,” “observed but undeclared” and “unsupported/unclassified.” The first can indicate missing coverage; the third can indicate an undeclared dependency or compromise. Both require triage. The compiler may scaffold a narrow candidate rule for review; it must never auto-accept permission expansion from an agent or evaluator’s own output. Rollout impact simulation helps discover required behavior without treating denial volume as proof of correctness.

3.3 Kubernetes is the deployment substrate and an enforcement boundary

Build the worker image from pinned dependencies, run a nonroot UID, drop capabilities, disable privilege escalation, use a read-only root filesystem and the runtime-default seccomp profile. Mount bounded temporary scratch space at an approved location. Do not grant host networking, host PID, host paths, arbitrary devices or privileged containers to ordinary agent workloads. The platform’s privileged node agents belong in a separately administered trust domain.

Create a dedicated ServiceAccount and disable automatic token mounting unless an explicit authenticated platform connection requires a projected token. Scope a projected token to the receiving audience and short lifetime; it is a workload credential, not a universal model, database or business-user credential. Kubernetes RBAC should grant no rights by default. Namespace isolation is an organizational aid, not a strong tenant boundary by itself; high-consequence workloads may need separate worker pools or clusters.

Install default-deny ingress and egress, then grant narrowly scoped access to the approved gateway and required control services. Namespace and pod selectors in the same NetworkPolicy peer form a combined condition; use both to avoid matching every pod in a trusted namespace. Port restrictions must match the actual gateway listener. DNS is a deliberate channel: use the approved resolver, deny direct external DNS and test IP-literal, alternate protocol and IPv6 bypasses. NetworkPolicy enforcement depends on the selected CNI and policy model. Native policies are additive and do not authorize HTTP methods or tool names. Validate actual denied connectivity; resource presence alone is insufficient. Kubernetes NetworkPolicy reference.

The v0.1 renderer withholds activation by emitting zero replicas. Its gateway egress template is a starting point, not a complete Temporal/telemetry environment binding. A platform-reviewed binding must add control-plane peers and the correct listener ports before activation. Do not scale the render merely because schema validation passed. The target release controller additionally requires policy-ready acknowledgements from each mandatory adapter and an effective-policy epoch consistent with the release.

3.7 Credential ownership and transport composition

Select one credential authority for each outbound hop. An agent can authenticate to a gateway using a short-lived workload credential; the gateway holds or obtains the provider credential. A gateway calling a tenant-specific tool uses an appropriately scoped delegated credential. A sandbox provider binding must not compete with gateway injection on the same request. Record which component owns TLS termination, header rewriting, refresh, redaction and revocation. The effective route diagram must include every hop and trust root.

Keep raw upstream secrets out of agent environment variables, prompt context, Temporal history and ordinary traces. A provider placeholder is useful only if the upstream exchange and binding endpoints are verified. Some protocols cannot support transparent credential replacement. For those, use a separately governed tool service or a narrowly scoped credential with explicit residual risk. A vault integration is not complete until unauthorized destinations cannot receive a token and responses/errors cannot leak it.

Validate rotation, expiry, revocation during an active stream, backend failure, denied token retrieval and policy cache outage. Audit workload-to-business-user delegation without exposing tokens. For multitenant tools, credential choice must be derived from validated tenant identity, not LLM-supplied arguments. Never create a shared broad backend credential merely to simplify routing.

3.8 Temporal: explicit durable coordination

Temporal coordinates retryable work, approvals, timers and recovery. Keep workflow code deterministic and move network calls, LLM decisions, clock-dependent external operations and side effects into activities. The framework-neutral adapter registers stable activity names, typed payloads and cancellation/heartbeat behavior. It cannot transparently make every arbitrary SDK durable. Treat each adapter as a supported product with replay, serialization and upgrade tests.

Activities can execute more than once. An effect may have committed even when the worker failed before acknowledging it. Use an operation ID stable across retries, a transactional idempotency record at the receiver, and a reconciliation API. Store canonical argument and resource hashes with the operation; reject a retry that reuses the key with changed content. A local SQLite ledger demonstrates this protocol but cannot ensure atomicity with a remote database or payment service. Temporal activity semantics.

# Framework-neutral pattern, not an automatic SDK wrapper.
@workflow.defn
class GovernedWorkflow:
    @workflow.run
    async def run(self, request: Request) -> Result:
        plan = await workflow.execute_activity(
            propose_action, request,
            start_to_close_timeout=timedelta(seconds=30),
        )
        # Approval must bind operation ID + canonical action + tenant + policy.
        approved = await workflow.execute_activity(
            verify_approval, plan,
            start_to_close_timeout=timedelta(seconds=10),
        )
        return await workflow.execute_activity(
            commit_idempotently, approved,
            start_to_close_timeout=timedelta(seconds=30),
        )

Signals or Updates can carry an approval decision but are not approver authentication. Authenticate the approval service and verify authorization at decision time and immediately before effect. Bound approval wait time, credential freshness, maximum attempts, execution duration and budget. Cancellation must propagate to activities and outbound requests, while the backend independently checks revocation for consequential operations. Already committed effects require compensation or reconciliation.

Use external object storage for large payloads with scoped references, checksums and retention. Avoid secrets and sensitive full documents in history. Bound history size, use continue-as-new where appropriate and version workers so running histories remain replayable. A rollout or rollback must account for active histories, activity names and tool schema changes. Replaying a deterministic workflow is a different test from retrying an external effect or resuming after a real worker crash.

3.9 Telemetry: correlated, redacted, useful

Instrument explicit boundaries: intake, workflow, activity, model call, tool proposal, authorization, effect commit, gateway decision and policy change. Propagate trace context through supported transports; use durable run and operation IDs to join events even when replay or sampling creates multiple spans. Emit policy and release digests, workload identity, business function and a normalized decision reason. Redact before export, not only in a dashboard. Auto-instrumentation coverage depends on the chosen adapter.

Use an OpenTelemetry collector as a controlled export point and Phoenix or another approved analysis backend for semantic traces. Export ordinary operational metrics separately from restricted payload evidence. Prompts, responses, tool arguments and retrieved documents stay off by default; opt-in diagnostic capture needs purpose, access control, retention and deletion. Logs should not contain Authorization headers or raw credentials. Kernel events are operational metadata and can still contain sensitive paths or destinations.

Distinguish telemetry availability from security-control availability. During exporter failure, buffer within limits, report dropped data and alert; avoid silently disabling authorization. For high-tier actions whose execution requires an audit record, use a durable authorization/commit journal and fail closed when it cannot persist. Sampling rates and collector capacity must preserve required security decisions and incident reconstruction without claiming complete visibility from sampled traces.

Govern an agent through its authority, evidence, and current operating state. Automate evidence collection and conservative classification; keep accountable approval, exceptions, incident command, and restart decisions explicit.

4.1 Risk is a property of the deployed system

Assess the agent with its tools, data, identities, users, destinations, workflow, and runtime controls. A harmless prompt can drive a powerful tool. A read-only tool can disclose restricted data. A technically reversible action can create reputational or operational harm before it is reversed. The assessment must therefore state a concrete failure scenario and consequence, then identify which controls reduce its likelihood or impact.

Maintain a risk profile with separate dimensions: data sensitivity, action authority, autonomy, blast radius, external exposure, recoverability, dependency trust, and evidence completeness. Do not reduce these dimensions to a weighted average that allows low cost or good task quality to offset unauthorized production writes. Record inherent risk from the proposed authority, control requirements, verified controls, and residual risk. Preserve both inherent and residual views so reviewers can see what depends on runtime enforcement.

The tiers below are a proposed enterprise method to ratify. They are not a regulatory classification. Assign the highest triggered tier, then apply uncertainty and exceptional-consequence escalation. A business function may impose tighter requirements. Central policy establishes a minimum that local teams cannot weaken by changing labels.

Reassess when the operating envelope changes and on a defined review cadence. An incident can invalidate a control assumption without any code change; the catalog must support suspending affected releases across business functions.

4.2 Conservative automated classification

Combine four sources: developer declarations, static findings, observed behavior in a qualified test environment, and destination/tool metadata. Declarations express intended authority. Static analysis identifies likely I/O and dynamic behavior. Telemetry identifies actual exercised actions. Receiver metadata describes the real business effects and scopes. None is sufficient alone. Reconcile mismatches and retain the original evidence so a reviewer can see why classification changed.

Use deterministic classification rules for known attributes and evidence-based flags for uncertainty. A scanner finding subprocess should add a code-execution investigation and relevant tests, not claim to know its maximum business consequence. HTTP method, field names, and SQL keywords are hints. Imported code, generated tools, runtime plugins, reflective calls, and remote servers can hide behavior. Missing metadata, unresolved call targets, incomplete traces, or unsupported transports require an unknown finding with a named owner and resolution requirement.

The v0.1 toolkit demonstrates local capability checking and a conservative report. It does not implement a complete semantic capability graph, IDE language server, business impact classifier, or enterprise risk approval service. Treat its outputs as evidence inputs. The supplied AEIE draft motivates an inference engine, but production adoption requires validated detection rules, false-negative analysis, explicit unknowns, and an independent review process for material risks.

Attach stable scenario IDs such as R-AUTH-001, R-APPROVAL-001, R-DATA-001, R-DURABILITY-001, and R-REVOKE-001 to required controls and evidence. The required set is the union of declared-capability requirements, observed-capability requirements, central minimums, and assessed domain risks. A declaration cannot remove a scenario demanded by evidence. A reviewer can retire a scenario only through an explained change to the threat model and policy mapping.

4.3 Policy proposals do not become authority by observation

Profiling can suggest the destinations, binaries, files, models, and remote tools needed by a package. Build candidates from a clean test environment with known workload identity and a recorded image digest. Filter out test harness activity and identify incomplete or dropped telemetry. Compare candidates with the manifest’s business intent, approved tool definitions, and central constraints. Test permitted and forbidden actions after applying the candidate; a successful trace alone does not show that forbidden actions are blocked.

Policy review must consider combinations of authority. A tool with production read access plus external posting can create an exfiltration path even when each rule looks reasonable separately. Delegation can combine privileges across agents. A generic code runner can bypass a narrow tool interface. Review data flows, identity propagation, and destination authorization, not only each YAML rule in isolation.

Automated invariant checks should reject broad wildcards, unknown destinations, unsupported policy features, raw credential exposure, unreviewed write authority, and bypassable egress. If a formal proof engine is introduced, document its modeled semantics, assumptions, unsupported features, and linkage to the actual deployed evaluator. A proof about a policy model does not establish that a runtime implements that model correctly. The OpenShell draft’s “propose-prove-enforce” idea is a target concept; use verified tooling and precise assurance claims.

Control owners approve effective policy, not only source templates. Rendered artifacts must bind agent identity, image digest, policy revision, framework/runtime adapter version, destination scope, and environment. Publish a human-readable diff showing expansion and contraction of authority. Applying a policy and deploying a workload are coordinated changes: startup must not enable execution while the necessary runtime policy is missing or stale.

4.4 Multi-layer kill switches and revocation

A kill switch is a coordinated containment protocol. Stopping a Python loop is insufficient when requests are queued, workflows are sleeping, credentials remain valid, or destinations accept already-issued authority. Provide disable scopes for one run, one agent release, an agent identity, a capability, a destination, a business function, and a tenant. Responders must select the scope and reason, and the system must report acknowledgments from each affected layer.

Distinguish fail-closed execution from useful degraded assistance. An agent may prepare a local draft while authority is unavailable if the operating envelope allows it and no sensitive data leaves approved boundaries. Restart requires documented remediation, current evidence, owner approval, and validation that queued or sleeping work cannot execute stale intent. 4.5 A centrally governed catalog published through CD

The catalog is the authoritative inventory of approved agent releases and their operational envelope. It should contain logical agent ID, release digest, source revision, image digest, owner and on-call group, business function, purpose, data class, autonomy mode, inherent/residual tier, declared and verified capabilities, dependency versions, policy digests, runtime qualification, evidence links, approvals, exceptions, environments, lifecycle state, and last review. Avoid embedding secrets or unrestricted prompt content in the catalog.

Separate a desired release record from actual deployment state. Desired records move through draft, candidate, approved, deployed, suspended, retired, and archived. Deployment observations report active workloads, identities, runtime versions, loaded policies, health, and enforcement readiness. Reconcile them continuously. An approved release that is not deployed differs from an unknown workload using an approved name. A copied manifest must not confer the identity of an approved artifact.

Policy promotion needs staged rollout and rollback semantics. A stricter policy may break active workflows; a broader policy increases authority. Test both on representative histories and workloads. Emit consistent semantic metadata across agent, workflow, activity, gateway, sandbox, and destination: agent ID, release digest, run ID, workflow/activity identifiers when applicable, business function, tenant, capability, policy revision, risk tier, decision ID, approval reference, idempotency key reference, budget counters, and trace linkage. 4.7 Exceptions with expiry and compensating controls

An exception request identifies the exact requirement, affected agent releases and environments, business need, maximum consequence, alternatives considered, compensating controls, owner, approver, expiry, and migration plan. Approval must come from the authority responsible for the policy, with data or business owners consulted where their obligations are affected. An exception cannot be self-approved by changing a manifest field or renaming a failed gate.

Bind the exception to immutable artifacts and scopes. An approval for one destination or pilot does not authorize a new tool, greater spend, or production use. Generate alerts before expiry and block new promotion when expired. For active workloads, define the approved expiry transition: drain, disable the capability, or suspend execution. Emergency exceptions require an incident record, narrow duration, independent review as soon as practical, and a documented path back to the standard.

Track exception count, age, renewals, authority expansion, and common causes. Repeated exceptions can reveal a missing platform capability or an inappropriate use case. Resolve them through roadmap work or reduced scope, not indefinite renewal. Preserve superseded approvals and the evidence that justified each decision.

4.8 Incident containment and recovery runbook

  1. Establish the event. Record run, release, identity, affected tenant/resource, observed action, decision IDs, timestamps, and whether an external effect may have committed. Assign an incident commander and classify consequence using the organization’s incident process.
  2. Contain independently. Apply the smallest scope that reliably stops harm, expanding when uncertainty warrants it. Disable ingress, scheduling, gateway/tool authority, credential issuance, destination access, and runtime egress as needed. Collect each acknowledgement; do not assume pod termination is complete containment.
  3. Preserve evidence. Retain policy revisions, approvals, image/source digests, traces, receiver receipts, workflow histories, and relevant artifacts under controlled access. Avoid exporting sensitive payloads into a general incident channel.
  4. Reconcile effects. Query trusted receivers using operation or idempotency references. Distinguish attempted, rejected, committed, unknown, and compensated actions. Stop automated retries for ambiguous effects until state is resolved.
  5. Assess scope and communicate. Search catalog and identity inventories for other affected releases, tools, policies, or shared credentials. Route findings to technical, business, security, and other required authorities through the organization’s existing process.
  6. Remediate and validate. Fix the violated boundary, reduce authority if needed, add a stable regression scenario, regenerate evidence, and test bypass, revocation, restart, and affected workflow histories.
  7. Authorize recovery. Obtain named restart authority, issue a new epoch, inspect pending approvals and queued work, and perform a controlled rollout. Monitor receiver outcomes and policy freshness closely.
  8. Close with improvement. Document root cause, missed signals, containment timing, residual effects, owner actions, and deadlines. Update risk profiles, rules, datasets, platform tests, and playbook decisions.

Run drills before enabling consequential production authority and after material architecture changes. Include control-plane partition, stale gateway policy, compromised tool response, duplicate activity delivery, approval replay, and a workload restarting after disable. Evidence should report what actually blocked the action and when. A tabletop exercise validates roles and communication; a live controlled drill validates enforcement. Both are useful and should be labeled accurately.

5.5 Evaluation inference and evidence limits

The initial analyzer uses Python AST patterns and a capability-to-scenario map. It identifies some subprocess, file-write and network patterns and reports recognized undeclared capabilities. Unknown capabilities and incomplete classifications raise review obligations. Reflection, native extensions, aliases, indirect calls, third-party libraries, generated code and remote tool behavior can escape the scanner; a clean scan is not an exhaustive capability graph.

The implemented analyzer emits T0–T3 declaration-based floors. The governance playbook's target model also includes T4 for exceptional or prohibited uses. Business consequence assessment and independent review must apply that escalation; the local analyzer cannot establish that a package is eligible for production or free of T4 conditions.

Stable scenario IDs map to actual unittest selectors. Evaluation runs the selectors and records outcomes, rather than accepting a file named “safety” as evidence. The fingerprint binds relevant package files and manifest content while excluding documented generated/cache paths. Evidence freshness is bounded; changing instructions, dependency declarations, evaluators or scenario selectors invalidates prior evidence. The exact canonicalization and exclusions live in src/zetra/evidence.py. Local timestamps are not a trusted time source for production approval.

Use these mechanics to extend the harness with repeated model runs, evaluator calibration, protected holdout cases, trajectory checks and real sandbox-negative scenarios. The default examples have no paid model and do not provide statistical assurance. An LLM judge must never be the sole authorization, schema, approval, isolation or idempotency gate. Aggregate quality scores cannot compensate for missing material scenarios or a known critical failure.

7.2 The control plane, data plane, and ownership boundary

7.3 Analysis and evaluations become bound evidence

The existing fast path deliberately separates static inspection from execution. zetra check parses source and manifest without importing the agent. zetra eval executes developer-owned unittest selectors in separate processes. Those selectors must cover required stable scenario IDs and actually run tests; skipped or expected-failure results do not count as passes. This is useful scaffolding for a material-scenario gate, but trusted project tests can still contain weak assertions. Independent review and protected platform-negative scenarios remain necessary.

# Current local CLI; run only trusted project code outside a qualified sandbox.
zetra check examples/knowledge

  --evidence /tmp/knowledge-evidence.json \
  --output /tmp/knowledge-catalog-candidate.json

The implementation fingerprints package contents, including instructions and dependency declarations, while excluding documented generated/cache locations. It records the manifest hash, toolkit/evaluator identity, selected scenario results, and timestamp. Evidence-dependent commands check those bindings, require mandatory scenarios to pass, and reject future-dated or older-than-24-hour local evidence. This 24-hour rule is an implemented developer check, not the production freshness policy. The production service needs an authenticated evidence producer and a trusted clock; copying hashes into editable JSON cannot supply either. See the exact evidence implementation.

The proposed production analysis record also captures unresolved calls and remote tool behavior. An HTTP GET can mutate state, and a POST can perform a read; verbs provide hints rather than business consequence classifications. Indirect imports, native extensions, reflection, generated code, and remote MCP servers require declared contracts and runtime tests. If analysis cannot classify a material path, the result becomes an unknown requiring review. It must not default to low risk or count an absent finding as a successful safety scenario.

Model evaluation adds a separate evidence layer. Pin the model/provider configuration, dataset revision, evaluator revision, seeds where supported, repeated-run count, and cost/latency accounting method. Record distributions and critical failures rather than an average alone. Keep deterministic authorization, schema, approval, and idempotency assertions outside the model judge. The current examples use controlled fixtures and do not measure model quality; that limitation is part of the release subject, not an incidental footnote. The original evaluation-inference proposal becomes actionable when every inferred review obligation has a stable scenario ID and an independent pass condition.

7.4 Scoped profiling produces a delta, never authority

The target profiling job starts from the evaluated image and known scenarios in a dedicated Linux environment. The capture plan declares hooks, process ancestry, pod/container identity, gateway spans, sandbox denials, and event-loss counters. It separates agent processes from the evaluator, node agents, sidecars, and unrelated workloads. The job stores raw events in restricted evidence storage, then a pinned parser normalizes them. Selecting the test-runner PID alone is insufficient when tools create subprocesses or networking occurs in a proxy.

The implemented zetra profile consumes normalized recorded JSON lines; it does not directly parse arbitrary Tetragon or OpenShell output. It requires exact agent, immutable image, and container: agent scope. Explicit denied observations are retained separately and excluded from process, file, and network permission candidates. A missing outcome remains an observation. All output remains review-candidate with authorizes: false. This behavior is inspectable in the normalizer.

A useful proposal compares four sets: declared and exercised; declared but unexercised; exercised but undeclared; and denied or unclassified. The first supports compatibility evidence. The second identifies missing coverage or unused authority. The third can reveal a legitimate dependency, an accidental library behavior, or compromise. The fourth supports denial tests and triage. An evaluator's adversarial request belongs in the fourth set even if the process attempted it repeatedly. Denial volume is not a justification for adding access.

Proposed parser contracts preserve the source event ID, native outcome, namespace, pod UID, container runtime ID, process ancestry, collection interval, image identity, scenario association, and any uncertainty. Address observations must not automatically authorize a domain whose IP changes. A path observation must not widen into an entire parent directory without review. Capture gaps invalidate conclusions that depend on completeness. This approach turns the attachments' synthesis step into a reviewable delta with evidence links instead of an opaque allowlist extracted from “everything the tests happened to do.”

Each adapter should expose four operations in its platform implementation: discover reports actual prerequisites; compile produces deterministic native artifacts and unsupported requirements; verify_effective reads the installed authority and compares it to approved intent; qualify executes allowed, forbidden, startup, outage, and revocation probes. Permission intersection is a Zetra semantic operation performed before native translation. It cannot be assumed from stacking vendor policies. This interface is also the mechanism for a simple developer experience. The package receives one error with the violated requirement, missing evidence, and suggested next action. A developer should see “NET-DIRECT-BYPASS lacks a qualified IPv6 deny probe for this runtime profile,” not a generic Helm failure buried in CI output. Native artifact diffs, source links, and environment details remain available to platform reviewers. The simple front door is supported by detailed adapter contracts and diagnostics, rather than hiding unresolved security requirements.

7.9 Credential hops and the missing composition bridge

The proposed production profile needs a placement decision: run the entire trusted worker under a supervised boundary, or keep coordination in a trusted worker and execute potentially untrusted agent computation through a separate sandbox activity adapter. The second arrangement is a useful target for stronger separation: the worker retains Temporal credentials and dispatch authority; the sandbox receives only the data and capabilities needed for one activity. It requires a new bridge that creates or selects a qualified sandbox, starts the evaluated package, validates the result, and maps cancellation and failures back into the durable activity. That bridge is not implemented in v0.1.

Today AgentActivities.run_agent constructs the factory and calls run inline in the worker's ordinary process. The OpenShell fixture separately uploads and executes copies of the actual reference code in its supervised workload. The gateway fixture separately links a host Temporal worker to the host semantic proxy and cluster collector. An actual OCI worker also executed a controlled knowledge workflow in Kubernetes with a pod-local Temporal development server. These are valuable building blocks, but joining their reports does not prove their combined transport, lifecycle, or credential boundary. See the current worker and the Kubernetes workflow report.

7.10 Temporal: determinism, activity granularity, and retries

Durability begins with a defined workflow/activity boundary. The current workflow records orchestration and calls one zetra.run_agent activity. External I/O and the ordinary Python factory run on the activity side. The workflow uses explicit timeouts and treats contract/security denials as non-retryable. Its orchestration is intentionally small enough to replay. This makes the package portable, but the whole agent run can repeat after an activity failure; internal model/tool steps are not individually durable checkpoints merely because the outer call is an activity.

# Current workflow policy, excerpt from src/zetra/temporal_workflow.py.
result = await workflow.execute_activity(
    "zetra.run_agent",
    request,
    start_to_close_timeout=timedelta(seconds=30),
    schedule_to_close_timeout=timedelta(minutes=2),
    retry_policy=RetryPolicy(
        maximum_attempts=3,
        non_retryable_error_types=["Denied", "ContractError"],
    ),
)

The live host fixture injects failure before the first read, observes attempts 1 and 2, validates the exact result, fetches history, and successfully replays it. A separate OCI worker ran in a hardened Kubernetes pod and its real history replayed with Python SDK 1.34.0. These tests establish actual execution and this history's compatibility, not arbitrary framework durability. Activities may execute more than once; idempotency belongs at the external effect's receiver. Temporal's activity semantics and workflow execution documentation provide the primary model; the fixture histories provide Zetra's measured implementation evidence.

The proposed bridge must distinguish three identities: a stable business operation, a workflow/run, and an activity attempt. Retries keep the operation identity and normalized payload; attempts get separate diagnostic identifiers. A receiver can return a previously committed receipt for an identical operation. It must reject the same operation key with changed payload, resource, actor, release, or approval. A timeout after remote success cannot be interpreted as “nothing happened.” The activity must query or retry the receiver's idempotent operation and reconcile the resulting receipt. The read-only worker intentionally rejects write-capable or unqualified adapters; the local SQLite action example demonstrates a transaction but is not a production remote receiver.

Run-wide budgets require the same separation. Current dependency counters reset when a retry constructs fresh dependencies. A proposed durable budget authority reserves against release/run/operation before a chargeable request, reconciles measured usage, and defines streaming/concurrency overshoot. A gateway's rate limit or a test-derived token estimate is not automatically that authority. The platform must reject a profile that promises a shared dollar ceiling while implementing only per-process counters.

Approvals travel through an authenticated approval service into a workflow, then are independently validated immediately before an effect. A Signal or Update is a transport mechanism, not proof of approver identity. Bind approval to canonical arguments, tenant/resource/action, release/policy epoch, operation ID, expiry, and single-use semantics. The current STOP Signal checks before and after the activity; it does not revoke a request already executing inside that activity. A production bridge needs cancellation/heartbeat handling and independent receiver fencing. Large objects belong in authorized external storage with digest and retention metadata; keep only bounded references in history and never bearer credentials.

8.9 Stop the run without confusing containment with rollback

The local stop test writes the configured STOP marker after a proposal has been approved and before commit. The next require() denies the capability invocation, leaving zero tickets. The demonstration also stops after one committed ticket; that ticket remains committed and a later invocation is denied. Local STOP checks occur at cooperative capability boundaries. They cannot interrupt arbitrary Python, authenticate a stop decision, revoke an already issued remote token or guarantee the termination of in-flight I/O.

The production stop decision needs an authenticated actor, explicit scope and a monotonic authority epoch. Intake refuses new work; the workflow receives cancellation/disable state; the gateway denies the relevant model/tool permissions and expires cached leases; the receiver rejects stale epochs before committing; and the workload/sandbox is contained if necessary. Each layer acknowledges the effective epoch. A missing acknowledgement is an escalation condition, not evidence that the stop succeeded.

For this incident, an approval issued at epoch 19 must not create a new ticket after the receiver observes disable epoch 20, even if Temporal resumes an old activity. An already committed ticket requires reconciliation or a separately approved compensating business action; disable cannot undo it. Restart requires remediation, current policy/evidence, a new authorized epoch and an explicit decision about queued proposals. Removing a STOP file or recreating a pod alone does not authorize production restart.

The cilium.io API group in a Tetragon policy identifies its Kubernetes resource type. It is not a universal “Cilium file” that also configures OpenShell or AgentGateway. Each product receives its own native configuration from the reviewed permission plan.

Review permission additions more strictly than removals. Do not widen a file into its parent directory, an IP into unrestricted internet access, or a tool name into all tools on the same server. If a required control has no supported implementation, hold the release or select a separately approved alternative.

6. Assign each control a clear job

The controls protect different parts of execution. The platform owns their installation, compatibility, and effective configuration. Business services retain responsibility for checking which resources and actions the caller may use.

Tetragon: selected kernel observations and tested responses

Tetragon uses eBPF to observe selected kernel activity and can enforce through supported hooks/actions. Generate scoped TracingPolicyNamespaced resources from maintained templates, then validate them against the installed CRD and kernel. A generic “kill everything unobserved” rule is not a reliable policy compiler.

Hook arguments have hook-specific meaning; they are not automatically interpreter command-line arguments. A post-event process kill may occur after a side effect. Where prevention is mandatory, qualify a pre-operation control rather than assuming detection is prevention. Test policy loading and startup behavior on every supported node class.

# Illustrative native observation policy; not an access grant or a blocking rule.
apiVersion: cilium.io/v1alpha1
kind: TracingPolicyNamespaced
metadata:
  name: incident-assistant-connect
  namespace: agent-staging
spec:
  podSelector:
    matchLabels:
      platform.example/agent: incident-assistant
  kprobes:
    - call: tcp_connect
      syscall: false
      args:
        - index: 0

Confirm that this hook exists and that emitted events identify the intended workload. See the Tetragon policy reference and runtime-hook documentation.

OpenShell: restrict the execution environment

OpenShell supplies a supervised sandbox with filesystem and network policy. Resolve the actual runtime paths and supported compute driver. Check the effective policy, including platform and provider contributions, instead of assuming separate configuration files intersect automatically.

# Native policy shape; partial example, not a complete runnable sandbox policy.
version: 1
filesystem_policy:
  include_workdir: false
  read_only: [/app, /usr, /lib]
  read_write: [/tmp/agent-scratch]
network_policies:
  gateway:
    endpoints:
      - host: gateway.internal.example
        port: 443
        protocol: tcp
    binaries:
      - path: /usr/local/bin/python

Use the actual interpreter path in the image. Sharing an interpreter does not establish code identity. Qualify filesystem enforcement and network bypass tests; block startup if required kernel protections are unavailable. Startup filesystem settings and live network settings have different update behavior, so test the selected version’s lifecycle.

Where a policy prover is used, require the relevant modeled domains and a conclusive result. Containment analysis does not prove business correctness or replace live denial tests. Kubernetes support and product maturity need a version-specific adoption decision; earlier repository tests used an experimental deployment path. See the current policy schema and Kubernetes setup.

AgentGateway: authenticate and authorize model and tool traffic

Route supported model and MCP requests explicitly through AgentGateway. Configure TLS, authenticated workload identity, permitted models/tools, and backend credentials. A reachable MCP server does not mean every tool it exposes is permitted.

The native Kubernetes integration uses Gateway API resources plus AgentgatewayPolicy and AgentgatewayBackend. Use their installed schemas; conceptual resource names from early design proposals are not deployable APIs. Test invalid identities, forbidden tools, route bypass, and cross-tenant access.

Tool-name authorization is one layer. The tool receiver must also validate arguments, resource scope, user delegation, and approvals. Rate limits, model allowlists, content filters, and usage accounting should be enabled only where supported and qualified. A distributed budget service may be needed for hard financial caps. See the AgentGateway API reference.

Kubernetes: isolate the workload and block bypass

Use nonroot containers, a read-only root filesystem, bounded scratch storage, dropped capabilities, resource limits, and an approved seccomp profile. Deny privileged containers, host mounts, host networking, and unnecessary Kubernetes API access. Platform node agents have a separate administrative trust boundary.

Apply default-deny networking and narrowly permit the gateway, approved DNS, workflow service, and telemetry collector. The CNI must enforce the policy. Network policies combine additively; review the effective union and test direct IP, DNS, IPv6, and alternate-route bypasses. Network reachability cannot authorize a tool or business resource.

A separate validating admission service should reject missing controls, untrusted images, wrong policy bindings, and revoked releases. Labels are selectors, not authenticated release identities. Restrict who can edit workload labels and verify the complete binding. See Kubernetes network policies and Pod Security Standards.

7. Bind identity, credentials, approvals, and durable execution

Give each workload a restricted identity. Validate issuer, audience, expiry, and agent/release scope at the receiving boundary. Carry user identity separately when access depends on the person requesting the task. Never trust identity supplied only in a prompt or editable request field.

Keep backend credentials outside the agent process where the integration supports it. Assign one credential owner per connection, document any exceptions, and test credential rotation and leakage. A Kubernetes token does not automatically provide a safe exchange for every backend.

Human approval must authorize a specific action

Bind approval to the requester, tenant, agent release, policy version, tool, resource, normalized arguments, and expiry. Changed arguments require new approval. The receiver checks authentication, revocation, and one-time consumption before making the change. “The model says approval was granted” is never sufficient.

Temporal: resume work without repeating unsafe effects

Use Temporal for tasks that need durable progress, waiting for approval, scheduled work, or recovery. Keep external calls in activities and orchestration deterministic. A failed activity may retry and repeat a call; recovery does not guarantee that the external service performed an effect exactly once.

Use receiver-enforced idempotency keys, bounded retries, timeouts, and explicit cancellation behavior. Authenticate approvals before they reach the workflow. Store large or sensitive payloads in protected storage with controlled references. Replay representative histories before changing workflow behavior, and define which worker release may resume existing runs. See Temporal activity semantics.

9. Release through CI and GitOps

Azure DevOps Pipelines creates and checks the candidate. Independent reviewers approve the release bundle and any permission changes. Argo CD reconciles the approved desired state from the deployment repository. Keep deployment authority separate from the agent author’s ability to change source.

  1. Build: immutable image, provenance, scans, tests, evaluations.
  2. Profile and propose: scoped observations, coverage gaps, native policy candidates, readable permission diff.
  3. Qualify and approve: policy validation, live boundary tests, UAT, operational readiness, and risk approval.
  4. Publish: trusted signed release envelope and reviewed GitOps change, bound to the target environment.
  5. Establish controls: routes, identity, sandbox, network and kernel policies; verify effective versions and readiness.
  6. Activate gradually: limited task intake, observed canary, then expansion if release criteria remain satisfied.
Ordering helps; independent readiness checks make it safe

Argo CD sync waves can order resources. A synced or healthy Kubernetes object does not prove that every node loaded its policy or that a gateway is enforcing it. Keep the workload inactive or unable to receive live tasks until the release controller verifies mandatory controls and the matching policy version.

Azure resource approvals/checks should be administered outside the editable pipeline YAML. Verify signer identity, artifact digests, evidence freshness, environment, approval scope, and revocation status. Hashes alone are not trusted signatures. See Azure Pipelines approvals and checks and Argo CD sync waves.

Catalog, privacy, and feedback

Publish agent owner, business function, risk tier, release/image/policy identifiers, evidence links, approvals, data classification, runbook, and active/revoked state in a central catalog. Keep desired and observed state separate. Restrict business views by tenant/function and protect sensitive evidence.

Redact secrets and personal data before export. Define retention, access, sampling, and deletion. Keep reliable audit records for approvals and effects even if ordinary traces are sampled. Turn production failures into regression cases; run periodic holdout evaluations and requalify controls after relevant platform changes.

OpenTelemetry signals provide the observability building blocks; the correlation and governance design belongs to the platform.

11. Stop, recover, and retire the agent

A kill switch withdraws authority to act, not just the running process. Scope it to a task, agent release, tenant, or wider service. Define who may use it and how quickly every relevant boundary must acknowledge revocation.

  1. Stop new task intake and revoke action/approval authority at gateways and receivers.
  2. Cancel workflow work and stop or isolate sandboxes/workloads as appropriate.
  3. Reconcile in-flight requests and effects; record what succeeded, failed, or remains uncertain.
  4. Recover only to a still-approved release and policy set. Confirm resumed workflows remain compatible.
  5. Preserve evidence and add regression cases before reactivation.

Process termination cannot undo a ticket, payment, or message already sent. Define compensation and manual recovery for each meaningful effect. If a revocation service is unavailable, high-consequence receivers should reject new effects rather than accept stale authority indefinitely.

Retirement checklist

Drain or cancel workflows; revoke identities and approvals; remove routes, credentials, and scheduled triggers; retire catalog state; retain required audit evidence; delete data according to retention policy. Verify that the retired agent cannot still reach a backend through an old worker, token, or route.
